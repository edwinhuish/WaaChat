## ADR-0001

**决定**：承载官方网页版，在 Chromium 内核层接管"下载文件"这一个动作。不重实现传输协议。

**状态**：已生效

**背景**：需要为 Linux 提供一个能做到"点击聊天文件即打开"的客户端。可选路径有三条：内核壳 + 内核层接管；用 whatsmoe / Baileys 之类的库重实现多设备协议并自建 UI；用 Waydroid 跑官方 Android 客户端。

**理由**：

1. **可行性已被上游产品形态验证。** 官方 Windows 客户端在 2025-11 从 WinUI/UWP 原生实现退回 WebView2 容器，直接加载网页版。我们要做的事在技术形态上与它相同，只是多了一层媒体接管。
2. **协议重实现的能力缺口是结构性的。** 该路线的库普遍不支持语音/视频通话；应用状态（置顶、静音、归档）只读不写；广播列表不支持；状态消息实验性。这些不是"还没做完"，而是与投入产出比直接冲突。
3. **风险不对称。** 协议级客户端与自动化驱动客户端是被重点识别的一类，且有实证的封号记录；而"官方网页 + 宿主进程"这一类产品多年存在。架构本身不提供豁免，但风险量级不同。
4. **上游维护成本转移。** 走内核壳路线，界面与功能的迭代由上游负责；走协议路线，需要持续跟协议跑。

**被否决的替代方案**：

- **协议重实现（whatsmeow / Baileys）**：媒体控制力最强，但通话永远补不上、应用状态只读、封号风险有实证、投入约为内核壳路线的 10 倍。详见 [`research/feasibility-study.md`](research/feasibility-study.md) 第 3 节。
- **Waydroid 承载 Android 客户端**：在原理上无法产出 AppImage（依赖 binder 内核模块与容器镜像），与分发要求直接冲突。

**影响**：

- 功能集**等于**网页版 —— 通话、频道、社区等随上游走，我们不承诺也不阻断。
- 上游改版会导致接管失效，因此**必须有降级与自检**（见 ADR-0002 的影响与 `architecture.md` 第 5 节）。
- 归档层能拿到的元信息有限（见 `architecture.md` 第 7 节）。

## ADR-0002

**决定**：绝不向被承载的页面注入任何脚本。不使用 `executeJavaScript`、`insertCSS`、让 preload 直连页面世界、或通过调试协议驱动页面。

**状态**：已生效 · 对应 [INV-1](../ai/INVARIANTS.md)

**背景**：最"直接"的实现方式是从页面内部取出媒体对象：注入脚本 hook 出解密后的 `Blob`，或者用自动化库的 `evaluate` 调用页面内部函数。那样能拿到最精确的数据，实现也最短。

**理由**：

1. **合规上不可承受。** 一旦注入，"页面里跑的是上游的代码"这个立论就消失了，产品性质从"宿主"变成"修改过的客户端"。这是本项目最主要的合规资产，不能拿它换实现便利。
2. **技术上也不划算。** 上游已经把内部状态对象从全局作用域收回，内部函数名与选择器随版本变动。依赖它们等于把维护成本绑定在上游最不稳定的一面上。相反，下载事件与 https 请求是**浏览器内核的标准行为**，稳定性高一个数量级。
3. **安全边界。** 任何注入通道都同时是"远程内容触达本地能力"的通道。见 [`security.md`](security.md)。

**被否决的替代方案**：

- **主世界注入 hook `URL.createObjectURL`**：能精确拿到解密后的文件，但需要注入，且强依赖页面实现。否决。
- **CDP / 自动化库驱动页面并调用其内部 API**：部署最省事，但正是风险最高的一类用法。否决，并由 ESLint 守卫。

**影响**：

- 拿不到"媒体消息 ID → 文件"的直接映射，归档元信息的能力受限。
- 缓存必须在**密文层**做，而不能在明文层做（见 ADR-0007 与 `media-capture.md`）。
- 由 `eslint.config.mjs` 强制，违反会直接让 CI 失败。

## ADR-0003

**决定**：媒体文件按内容哈希归档（内容寻址），元数据索引用 SQLite + FTS5。

**状态**：已生效

**背景**：需要支持"同一个文件被转发到多个会话后仍然只存一份"，以及"按文件名找回半年前打开过的附件"。

**理由**：

1. **内容寻址天然解决去重。** 同一份内容哈希相同，无需维护"这两个文件是不是同一个"的判断逻辑。文件名与路径上的差异（`报告.pdf` / `报告 (1).pdf`）不再产生新的存储。
2. **内容寻址让"文件是否已存在"成为一个廉价问题。** 先算哈希再落盘，命中即可丢弃临时文件。
3. **FTS5 是为了"找回来"。** 归档的价值一半在"打开快"，另一半在"找得到"。SQLite 单文件、无服务、可备份，适合桌面场景。
4. **原生依赖可控。** `better-sqlite3` 自带启用了 FTS5 的 SQLite，不需要额外的构建标签或系统库。

**被否决的替代方案**：

- **按 `会话/日期/原文件名` 组织目录**：符合直觉，但去重困难，且文件名冲突要靠加后缀解决，最终产出 `报告 (1).pdf` 这类产物——正是本项目要消灭的东西。
- **纯文件系统 + JSON 索引**：搜索能力不足，且并发写入的原子性要自己保证。
- **`node:sqlite`（Node 内置）**：可以避免原生依赖，但 FTS5 是否可用取决于构建，不确定。若将来验证确认可用，可用一条 ADR 替换（收益：去掉原生依赖 → 打包与跨架构构建显著简化）。
- **PostgreSQL / 外部服务**：桌面应用引入服务依赖不合理。

**影响**：

- 归档目录的人类可读性下降（文件名变成哈希）。因此**必须**提供界面与导出功能把原文件名还原出来 —— 这是一个功能要求，不是可选项。
- `better-sqlite3` 是原生模块，引入打包复杂度（prebuild 可用性、跨架构构建），见 ADR-0004。它是 **Node-API** 模块，因此**没有** ABI 耦合 —— 早期版本在此处把它写成「ABI 耦合」，已被实测推翻，见 `packaging.md` 第 6 节。

## ADR-0004

**决定**：以 `electron-builder` 同时产出 `deb` 与 `AppImage`；AppImage 使用静态 runtime 工具链（`toolsets.appimage: "1.0.3"`）；**不**手写 `deb.depends`。

**状态**：已生效

**背景**：分发要求是 deb 与 AppImage 双格式。

**理由**：

1. **AppImage 的 FUSE2 依赖是个陷阱。** 传统 AppImage 运行需要 `libfuse2`，而它在 Ubuntu 24.04+ 已改名为 `libfuse2t64` 且 FUSE2 自 2017 年起无人维护。静态 runtime 工具链把挂载逻辑内联，**彻底去掉这个依赖**，用户拿到即能跑。electron-builder v27 将默认启用，现在显式固定以免行为静默改变。
2. **不手写 `deb.depends` 是刻意的。** 手工维护的依赖列表会腐坏（Ubuntu 的 time_t 过渡把若干库改名成 `*t64`），而 electron-builder 已内建与所固定 Electron 版本匹配的列表。若确需追加，应使用 `A | B` 的替代写法，并在 `packaging.md` 记录理由。
3. **打包产物必须被自动校验，而不是靠人肉安装验证。** 因此有 `scripts/verify-package.sh`，并被 `pnpm run verify` 与 CI 调用。

**被否决的替代方案**：

- **Flatpak / Snap**：都可以做，但不满足"deb + AppImage"的明确要求。作为后续渠道可以加，不替代。
- **自建 `dpkg-deb` 脚本**：控制力更强，但失去 AppImage 与差分更新，收益不成比例。
- **`tar.zst` + 自写安装器**：用户成本高。

**影响**：

- AppImage **只能在 Linux 上构建**，CI 必须用 Linux runner，不能交叉编译。
- arm64 需要独立的 runner（`ubuntu-24.04-arm` 或 QEMU），当前未启用，见 `roadmap.md`。
- 原生模块（ADR-0003）在打包前会被 electron-builder 检查依赖树并按需 rebuild（`npmRebuild: true`）—— **但本仓库把该默认值显式关掉了**：`electron-builder.yml` 设 `npmRebuild: false`。默认值会**无条件**对原生模块跑 `@electron/rebuild` → `node-gyp` → `make`，即便它已探测到 prebuild、日志里明确写着 `buildFromSource=false` 也照跑，于是打包机被凭空要求具备 gcc / make / python3，且失败信息指不到根因。`better-sqlite3` 是 Node-API 模块，本来就没有 per-ABI 重建的对象，因此也没有单独的 `install-app-deps` 步骤 —— 见 [ADR-0010](#adr-0010) 与 [`packaging.md`](packaging.md) 第 6 节。

## ADR-0005

**决定**：包管理器使用 npm，不使用 pnpm。

**状态**：**已被 [ADR-0010](#adr-0010) 取代**（2026-10-09）。原文保留，是为了让后来者看到"当时的理由是什么、后来为什么不再成立"。

**背景**：开发者的其他项目普遍使用 pnpm。

**理由**：

1. **原生模块 + 打包工具链的摩擦。** `better-sqlite3` 是原生模块，`electron-builder` 在打包时会检查依赖树并按需 rebuild。pnpm 的符号链接结构在这条链路上是已知的摩擦点，通常需要退回 `node-linker=hoisted` —— 那就等于 npm。
2. **这个项目的依赖很少**（2 个运行时依赖），pnpm 的核心收益（磁盘占用、依赖隔离、monorepo）在此几乎没有体现。
3. **减少变量**。该项目已经有足够多的不确定性（原生模块、打包、上游改版），不值得在最基础的依赖安装环节再引入一个。

**被否决的替代方案**：

- **pnpm + `node-linker=hoisted`**：等价于 npm，但多了一层配置。
- **Bun**：生态兼容性风险，且 Electron 工具链对它的验证不足。

**影响**：

- 使用 `package-lock.json`，不使用 `pnpm-lock.yaml`。
- 若将来引入 monorepo 或依赖数量显著增长，应重新评估并追加 ADR。

## ADR-0006

**决定**：仓库、源码、产物、桌面条目中不含任何服务方的商标资产。应用名、可执行文件名、包名、`.desktop` 条目均不使用该名称。

**状态**：**已被 [ADR-0011](#adr-0011) 取代**（2026-10-09）。保留原文是因为它的第 1 条理由（"保护没意识到风险的 fork 者"）仍然适用于 fork 场景 —— 只是不再约束本仓库的命名。

**背景**：这类工具最容易被误改坏的地方。fork 者把包名改成 `whatsapp-desktop` 是常见做法。

**理由**：

1. 商标风险由分发者承担，而分发者往往是没有意识到这一点的 fork 者。
2. 改名成本极低（集中在 `package.json` 的 `desktopName`、`electron-builder.yml`、`src/main/index.ts` 的 `app.setDesktopName()`），收益是长期的法律安全。
3. 文案中提及兼容对象属于指示性使用，**可以**保留。

**被否决的替代方案**：无。这是合规底线，不存在权衡。

**影响**：

- 文档与 UI 中描述功能时需要绕开"某某客户端"的说法，用"网页版"、"上游"等表述。
- 若发现任何提交引入了上游商标资产，应在评审中直接拒绝。

## ADR-0007

**决定**：本项目不解析密钥、不做自己的加解密实现、不修改加密流量。解密只发生在官方网页代码内部。

**状态**：已生效 · 对应 [INV-3](../ai/INVARIANTS.md)

**背景**：媒体在 CDN 上是密文。要在本地得到可交给外部应用打开的文件，似乎"顺手解密"是最自然的做法 —— 算法是公开的（密钥派生后按 CBC 解密，附 MAC 校验）。

**理由**：

1. **性质问题。** "使用公开算法解密自己有权访问的内容"与"实现一个解密器"在代码上是同一件事，在定性上完全不同。后者会让项目从"宿主"变成"工具"，而"工具"对合规风险敞口毫无帮助。
2. **技术上没有必要。** 页面已经解密过了。我们只需要观察下载事件即可拿到明文 —— 由上游代码产生，不是我们产生的。
3. **减少需要维护的加密代码**。任何自己的密码学实现都是负债。

**被否决的替代方案**：

- **自行解密以支持"脱离网页直接查看"**：体验收益有限（归档打开已经足够快），风险与维护成本显著。否决。

**影响**：

- 归档中的明文来自页面产生的下载流，因此**必须先有一次页面解密**。归档不能作为"离线密码学恢复"的手段。
- 研究文档里记录的密钥派生与校验流程仅作为**背景知识**保留，不进入实现。

## ADR-0008

**决定**：登录态（`session/`）、归档（`media/`）、密文缓存（`cache/`）分三个目录存放，且三者的删除策略互不相干。

**状态**：已生效

**背景**：三者都"存在本地",最省事的做法是放在同一个应用数据目录下统一管理。

**理由**：

生命周期完全不同，混放会导致最严重的一类自伤：

| 目录 | 丢了会怎样 | 删除策略 |
|---|---|---|
| `session/` | 需要重新扫码链接设备 | **绝不自动删除**，不提供"清空"入口 |
| `media/` | 用户资产丢失，且 CDN 链接过期后不可恢复 | 只在用户明确要求时删除 |
| `cache/` | 仅影响性能，下次自动重建 | 可随时安全删除 |

一个"清空缓存"按钮误删登录态，会让用户以为账号出问题；误删归档，会丢失不可恢复的数据。物理隔离是最低成本的防线。

**被否决的替代方案**：统一放 `userData/` 下由应用自行区分 —— 依赖代码正确性，而物理隔离依赖文件系统，后者更可靠。

**影响**：

- 归档的默认权限为目录 `0700`、文件 `0600`（见 [`security.md`](security.md)）。
- 界面上的清理功能必须**分别**说明清楚各自删除的是什么。

## ADR-0009

**决定**：文档分为 `docs/`（面向人）与 `ai/`（面向 AI 助手）两套，并在根目录放 `AGENTS.md` 作为 AI 入口。

**状态**：已生效

**背景**：需要同时服务人类贡献者与 AI 编码助手。

**理由**：

1. **两种读者的检索方式不同。** 人按"这是什么、为什么"浏览；AI 需要"禁止什么、怎么做"的清单式表述。混在一份文档里，人会嫌它啰嗦，AI 会漏掉关键约束。
2. **`AGENTS.md` 放根目录**是因为多数工具只会自动读取根目录下的同名文件。它的作用是路由，不是内容。
3. **代价是同步义务。** 因此把同步写进 PR 检查清单（`CONTRIBUTING.md` 第 5 节）与 `docs/README.md` 第 5 节，而不是寄希望于自觉。

**被否决的替代方案**：

- **单一 `AGENTS.md` 包办全部**：会膨胀到没人读，且人侧文档失去组织。
- **全部放 `docs/`，让 AI 自己筛**：AI 会反复读取低相关信息，成本高且易漏。

**影响**：

- 改 `docs/` 必须在同一 PR 同步 `ai/`，反之亦然。
- `docs/README.md` 第 5 节的同步规则表是强制项。

## ADR-0010

**决定**：包管理器改用 **pnpm**；同时移除 `Taskfile.yml`，把全部多步任务收敛到 `package.json` 的 `scripts`。取代 [ADR-0005](#adr-0005)。

**状态**：已生效

**背景**：ADR-0005 选择 npm 的两条理由是"原生模块 + 打包链路的摩擦"和"减少变量"。现在第一条已被实测推翻，而没有采纳 pnpm 的成本开始显现。

**理由**：

1. **ADR-0005 的前提不成立。** `better-sqlite3@13` 是 **Node-API** 模块：Node（ABI 127）与 Electron（ABI 149）加载同一份 `prebuilds/linux-x64.node`（实测可 `require`）。既没有 ABI 耦合，也就没有"pnpm 的符号链接让 rebuild 找不到模块"这条摩擦。
2. **`electron-builder@26` 原生支持 pnpm 的 isolated 布局。** `app-builder-lib/out/node-module-collector/pnpmNodeModulesCollector.js` 按 pnpm 的依赖图决定往 asar 里放什么，并通过 `package.json` 的 `packageManager` 字段探测包管理器（`node-module-collector/packageManager.js`）。因此**不需要**退到 `node-linker=hoisted`。
3. **命令入口原本有两个层级。** Taskfile 包着 npm 脚本，于是"到底跑什么"要跨两个文件阅读，CI 还得额外装一个 `task` 二进制，排障时第一句话常是"你跑的是 task 还是 npm script"。任务并不多，`&&` 串联足够表达。

**决定的具体形状**：

- 安装：`pnpm install`（CI 加 `--frozen-lockfile`）。锁文件是 `pnpm-lock.yaml`。
- 版本钉在 `package.json` 的 `packageManager`（`pnpm@12.10.1`）—— pnpm 自身、corepack、`pnpm/action-setup` 三方都认的单一事实源；`engines.pnpm` 是给不认该字段的工具看的第二道声明。
- 依赖构建脚本白名单在 `pnpm-workspace.yaml` 的 `allowBuilds` 里（pnpm 12 起该字段属于那个文件，写进 `.npmrc` 会被当作未知配置）。实际需要放行的是 `esbuild` 与 `electron-winstaller`；**`electron` 与 `better-sqlite3` 本身就没有安装脚本**，所以不在名单里。
- Electron 二进制不再由 `electron` 包自动下载 —— **Electron 44 已删掉自己的 `postinstall`**（registry 上该版本的 `scripts` 为 `null`），改成名为 `install-electron` 的 bin。因此项目的 `postinstall` 显式调用它，维持"`pnpm install` 之后 `pnpm run dev` 直接可用"。
- 刻意**没有**名为 `install` 的脚本：它与包管理器的生命周期钩子同名，定义它会让 `pnpm install` 递归调用自己。
- 跨平台清理放在 `scripts/clean.mjs`，不用 `rm -rf`（shell 方言，换个 shell 就静默失效）。

**被否决的替代方案**：

- **pnpm + `node-linker=hoisted`**：能规避想象中的打包摩擦，但会丢掉依赖隔离，而所需的摩擦经实测并不存在。
- **保留 Taskfile，只换包管理器**：Taskfile 的 `sources`/`generates` 增量构建能力确实有用，但额外的二进制安装、第二套模板语法与"两个入口"的认知成本更高。
- **用 `just` / `make` 取代 Taskfile**：同样的第二入口问题，`make` 还引入 tab 敏感的语法陷阱。

**影响**：

- `pnpm-lock.yaml` 取代 `package-lock.json`。锁文件格式变更会让所有开放中的依赖 PR 需要重做 —— 一次性成本。
- 贡献者需要 pnpm ≥ 12。低于 12 的 pnpm 不认 `allowBuilds`，`esbuild` 的构建脚本会被拦下 → 构建失败。
- 文档与 CI 里所有 `task xxx` 写法已全部改为 `pnpm run xxx`；`arduino/setup-task` 已从两个 workflow 移除。
- `dependabot.yml` 的 `package-ecosystem` 仍写 `npm`：Dependabot 用它读取 `pnpm-lock.yaml`，这是它的既定用法，不是笔误。

## ADR-0011

**决定**：项目名采用 **`WaaChat`**（npm `name` 为 `waachat`，appId 为 `io.github.edwinhuish.waachat`）；商标基线从"名称与标识资产一律不用"收敛为"**不使用视觉标识资产**"。取代 [ADR-0006](#adr-0006)。

**状态**：已生效 · 同时改写 [INV-4](../ai/INVARIANTS.md)

**背景**：ADR-0006 把"名称里不出现 `whatsapp`"作为底线，理由是保护没意识到风险的 fork 者。项目所有者要求把名称收敛到一个既不失去辨识度、又便于说明用途的形态，并在知情的前提下接受随之而来的商标风险。

**理由**：

1. **风险承担者就是决策者。** ADR-0006 的立论是"分发者往往没意识到风险"，它保护的是第三方 fork 者。在本仓库所有者明确知情并选择接受时，这条理由不再构成约束。
2. **名称的作用是说明用途，而不是主张权利。** 用户需要能从名字看出"这个程序承载的是哪个服务"，否则它就没有辨识度。名称只用于指称对象，不主张任何商标权利 —— 这与 ADR-0006 第 3 条承认的"文案中提及兼容对象属于指示性使用"一致，本次只是把这个承认推广到项目名本身。
3. **真正可避免、也真正危险的是视觉资产。** Logo、图标、字体、官方配色才是最易构成混淆、最易触发平台投诉的部分，而不使用它们的成本几乎为零。因此这次**不是放宽，是重新划线**：把"名称"从禁止项移到"指称性使用 + 强制非官方声明"，把视觉资产明确留在禁止项。

**被否决的替代方案**：

- **保持中性名**：风险最低，但用户无法从名字判断用途；与项目所有者对该仓库的定位不符。
- **名称完全中性、只在文档里提及服务名**：实质上就是旧方案，被明确否决。
- **名称贴近服务方的同时沿用其视觉风格**：收益为零、风险最高。否决。

**影响**：

- **强制项**：`DISCLAIMER.md` 第 1 节必须载明非隶属关系与指称性使用；该声明同时出现在 `README.md` 与安装产物中。删掉它是违反本 ADR，不是编辑自由。
- **强制项**：`ai/INVARIANTS.md` 的 INV-4 改为约束视觉资产，并保留"身份声明必须一致"的可执行断言。
- `build/icon.svg` 是自绘的抽象图形（三条流动的线），不含服务方任何素材 —— 这一点必须保持。图标的视觉理由与名称无关，不依赖任何服务方语义。
- 商标风险现在明确落在仓库所有者身上。这是有意识的取舍，不再有"ADR-0006 会挡下来"这层保护。
- 本地目录：数据目录 `~/.local/share/waachat`、缓存 `~/.cache/waachat`、设置 `~/.config/waachat`、会话分区 `persist:waachat`、AppArmor profile 名 `waachat`。

## ADR-0012

**决定**：发版动作（提升版本号 → 提交 → 打 `v<版本>` 标签 → 推送）由 [`bumpp`](https://github.com/antfu-collective/bumpp) 执行，命令入口是 `pnpm run release`，配置在 `bump.config.ts`。**不为它自写脚本。**

**状态**：已生效

**背景**：发布由推送 `v*` 标签触发（`.github/workflows/release.yml` 的 `on.push.tags`）。在此之前，这一步是文档化的手工两步（`git tag v<版本>` + `git push origin v<版本>`，见 `ai/TASKS.md` T6）。版本号与 `package.json` 的一致性、标签是否重复、工作区是否干净，全靠人记。

**理由**：

1. **这是"版本提升 + 提交 + 打标签 + 推送"的标准动作，不应该由本仓库维护。** 它服务的是一个与产品无关的流程，却需要长期维护与测试。工具已经把这些细节（版本模板、推送顺序、标签类型、git 检查）处理过一遍。
2. **发布路径应当可解释、可参数化。** 提交信息模板（`chore(release): {tag}`）、标签名模板（`v{version}`）、要 bump 的文件都写在 `bump.config.ts` 里，而不是散落在文档的手工步骤中 —— 文档会被跳过，配置不会。
3. **自写脚本要实现的守卫，工具里已经有了。** `noGitCheck: false` 就是"工作区必须干净"；标签重复由 `git tag` 自身报错拦下（`throwOnError`）；"提交是否已推送"由 `push: true` 一并解决（`git push` + `git push --tags`）。
4. **少一次人工换算。** 版本号由 `bumpp` 从 `package.json` 读出并写回，semver 换算（patch / minor / major / 自定义）由它负责，人手不接触版本号字符串。

**被否决的替代方案**：

- **自写 `scripts/release.mjs`（预检 + `git tag -a` + `git push`）**：功能上够用，但这些代码从此成为本仓库的维护面，而我们**无法**把它的行为交代给任何一个熟悉发版流程的人 —— 他得先读那个脚本。工具相反：`bumpp` 的行为有公开文档，`bump.config.ts` 只声明本仓库的取舍。
- **继续手工 `git tag` + `git push`**：最容易发生的错误（标签与 `package.json` 版本不一致）恰好是这里最容易发生、且**没有任何检查会拦住**的 —— 产物文件名用的是 `package.json` 里的版本，标签是手敲的那个，两者不一致时发布本身不会报错。
- **`semantic-release` / `release-please` 这类"提交即发版"的机器人**：它们要求提交历史严格符合约定，并接管 `CHANGELOG.md` 的生成。本仓库的 CHANGELOG 是**人工撰写的中文文档**（Keep a Changelog 格式，含"为什么"而非仅"改了什么"），不接受被生成结果覆盖。
- **停在 bumpp 11.x**：11.x 与 12.x 都能满足需求，但 12.x 是当前主线（具名 token 模板、`--pr` 流程），没有留在旧主版本上的道理。
- **把 `CHANGELOG.md` 放进 `bumpp.files` 让它顺手改**：bumpp 对"已知文件"（package.json 一类）之外的路径做的是**旧版本号的全文替换**。CHANGELOG 里的版本号同时出现在小节标题、底部 `[<版本>]:` 链接与 `[Unreleased]` 的 compare 起点中，全文替换会把已经发布出去的历史改写掉，且不报错。

**影响**：

- 新增**开发依赖** `bumpp`（12.x）。它不进产物：`electron-builder.yml` 的 `files` 只收 `out/**` 与 `package.json`，且 electron-builder 只收集 `dependencies` —— 因此不影响 deb / AppImage 的体积与依赖。
- ⚠️ **`bumpp` 的主版本与 `.nvmrc` 绑定**：12.x 的 `engines` 是 `^22.18.0 || ^24.11.0 || >=26.0.0`。当前 `.nvmrc` 是 24.21.0（落在 `^24.11.0` 区间内），**下调它会让发布命令直接跑不起来**，CI 的 `pnpm install` 也会报引擎不符。
- `.github/dependabot.yml` **不**忽略 `bumpp` 的升级：它是开发依赖，主版本升级只需人工看一眼 `bump.config.ts` 的模板是否仍受支持（12.x 的具名 token 取代了 11.x 的 `%s`）。
- 模板用 12.x 推荐的具名 token（`{version}` / `{tag}` / `{date}` 等）；`%s` 仍然可用但已被上游标记为软弃用。
- 标签是**附注标签**，标签消息与发布提交信息相同（`git tag --annotate --message`）。
- 推送是 `git push` + `git push --tags`：**本地其它尚未推送的标签也会一并推上去**。发布前用 `git tag -l` 确认没有多余的标签。
- 发布提交里**只有** `package.json` 的版本号（`noGitCheck: false` 要求工作区干净）。`CHANGELOG.md` 必须在发布之前单独提交 —— 这符合"一个提交做一件事"：CHANGELOG 是内容改动，版本提升是机械动作。
- `bumpp` 不校验当前分支。从 `main` 发布由流程要求，不由工具保证。
- 自写的 `--dry-run` 没有对应物；替代品是 `bumpp` 的确认提示（`confirm` 默认开启，落盘前会停一次）。

## ADR-0013

**决定**：Release 的创建与发布说明都交给 [release 工作流](../.github/workflows/release.yml) 自动完成。具体形状是三件事配上：`electron-builder.yml` 里设 `publish.releaseType: release`（直接建成**已发布**状态）与 `releaseInfo.releaseNotesFile: release-notes.md`（发布说明的来源）；发布说明由 [`.github/scripts/generate-changelog.sh`](../.github/scripts/generate-changelog.sh) 从提交历史生成；工作流最后一步**断言终态**（Release 非草稿 + 四个产物都在）。全程不需要人工点 Publish。

**状态**：已生效

**背景**：发布由推送 `v*` 标签触发（ADR-0012），产物由 electron-builder 的 GitHub publisher 上传（`--publish always`）。但推完标签之后，Releases 页面上**什么都没有**——而工作流是绿的。两个原因都在 electron-builder 的默认行为里：

1. `releaseType` 默认为 `draft`。草稿 Release 在 Releases 页面上不显示、在 GitHub API 的"最新发布"里也不算数，于是 `electron-updater` 永远看不到新版本 —— 自动更新**静默失效**。
2. 它的 GitHub publisher 在"标签同名 Release 已存在但类型与本次不兼容"或"已发布超过 2 小时"时，**不抛错**，只打一条 warn 就跳过上传（`GitHub release not created` / `skipped publishing`）。构建与工作流都照旧成功。

第 2 条决定了"只把 `releaseType` 改成 `release`"还不够：失败必须被**断言**出来，而不是靠读日志。

**理由**：

1. **默认 draft 与本仓库的发布语义相反。** 这里的发布动作是"推标签"，语义上就该立刻可见、立刻可被自动更新读到。把"让它真的发布出去"这一步留给人工点击，失败面是一次健忘；而健忘的直接后果恰好是最难排查的那类静默失效。
2. **发布说明必须是文件。** electron-builder 没有传 body 的 CLI 参数，它只从 `releaseInfo.releaseNotes` / `releaseInfo.releaseNotesFile` / 项目根的 `release-notes.md` 读。因此让生成的 changelog 落到约定路径，是这条链路上最短的实现 —— 不需要第二次 API 调用。
3. **失败要可见，不能靠"publisher 应该报错"。** 上游对上面第 2 条明确选择了 warn-then-skip，所以工作流结尾断言 Release 的 `isDraft` 与四个文件名。这一步把"静默跳过"变成红灯，也顺带覆盖了"同名标签的 Release 早就是草稿"这种历史遗留状态（`gh release edit --draft=false` 负责把它转正）。
4. **标签与版本必须同源。** electron-builder 只按 `v` + `package.json` 的 `version` 决定发布到哪个标签（`githubTagPrefix + appInfo.version`），与触发工作流的引用无关；两者不一致时它会往另一个标签上发，同样不报错。工作流因此在构建产物之前就断言 `v<version> == 标签`，并断言该标签确实存在。

**被否决的替代方案**：

- **保留默认 draft，人工在 GitHub 上点 Publish**：把发布交给一次容易忘记的点击，而忘记的后果（自动更新静默失效）与成功在 CI 上毫无区别。同一类"人工记得做某事"的守卫，ADR-0012 已经否决过一遍。
- **工作流里用 `gh release create --notes-file` 自己建 Release**：可行，但必须在 electron-builder 之前建好（否则它的 publisher 会另建一个），于是会出现一个"已发布但还没有产物"的窗口 —— 用户可能正好看到空 Release。让创建与上传都归同一个 publisher，再把终态断言出来，失败点更少。
- **建好草稿 → 上传产物 → `gh release edit --draft=false` 转正**：产物齐了才可见，顺序确实更保守；但 electron-builder 对"已存在的草稿"是**无条件复用**且不会转正，于是每次重跑都依赖这条外部命令成立。它多一个隐式耦合，却换不到额外保障 —— 终态断言已经覆盖同样的失败。
- **事后 `gh release edit --notes-file` 刷新发布说明**：创建时就带上不需要第二次调用；而同一标签区间生成的说明是确定的，重跑不需要刷新。
- **让 `semantic-release` / `release-please` 接管**：理由同 ADR-0012 —— `CHANGELOG.md` 是人工撰写的中文文档，不接受被生成结果覆盖。

**影响**：

- Release 页面上自动出现：标签 `v<版本>`、标题为 `package.json` 里的版本号（如 `1.0.0`）、说明为按提交类型分节的变更列表（附对比链接与非官方声明）。
- **Release body ≠ `CHANGELOG.md`**：前者是从提交历史生成的"改了哪些提交"，后者是人工撰写的"为什么这样改"。两者并存，不互为替代。
- `release-notes.md` 是生成物，已加入 `.gitignore`：提交它会让 `bumpp` 的"工作区必须干净"检查（ADR-0012 的 `noGitCheck: false`）误判。
- 工作流新增一步发布后断言，因此"产物没上传成功"现在是**红灯**，而不是一条容易被忽略的 warn。
- `workflow_dispatch` 只对**已存在**的标签重跑：标签不存在、或与 `package.json` 的版本不一致，都会在构建前失败。重跑用 `EP_GH_IGNORE_TIME=true` 关掉上游那个 2 小时时间窗。
- 发布说明的分节只认**约定式提交**（`ai/CONVENTIONS.md` 第 9 节）里的 `feat` / `fix` / `perf` / `refactor` / `docs`，且类型必须在行首。提交信息不合规时该条提交不会出现在说明里 —— 这是有意的，通配匹配会把 `fix the feature list` 同时塞进两节。
- 若将来要改成 `prerelease` 或回到 `draft`，必须同时改本节与 `docs/packaging.md` 第 7 节。

## ADR-0014

**决定**：**不在 `electron-builder.yml` 里设 `releaseInfo.releaseNotesFile`**（该键一个都不出现）；Release 的发布说明由 release 工作流的「写入发布说明并确保已发布」步骤用 `gh release edit "$TAG" --draft=false --notes-file release-notes.md` 显式写入。同时把"解析并校验版本标签"从构建之后**前置**到安装依赖之前，并让发布后的断言同时检查发布说明非空且提到本次标签。

**状态**：已生效（修正 [ADR-0013](#adr-0013) 的实现机制；那条决策的目标——"Release 自动创建并带上发布说明"——不变）

**背景**：ADR-0013 落地成 `releaseInfo: { releaseNotesFile: release-notes.md }` 之后，CI 的「打包 deb / AppImage」作业从该提交起**必红**，报：

```
Error: cannot find specified resource "release-notes.md", nor relative to ".../build",
neither relative to project dir ("...")
    at LinuxPackager.getResource (platformPackager.ts:773)
    at getReleaseInfo (publish/updateInfoBuilder.ts:19)
    at createUpdateInfoTasks (publish/updateInfoBuilder.ts:111)
```

两件事合起来构成这个坑：

1. `getResource(custom, ...names)`（app-builder-lib 26.15.3，`out/platformPackager.js`）有两条分支：`custom === undefined` 时依次试回退名列表、都不命中就返回 `null`；**`custom` 显式给了却找不到就 `throw InvalidConfigurationError`**。
2. 读它的 `getReleaseInfo()` 属于 `createUpdateInfoTasks` —— 生成 `latest*.yml` 时**每次构建都会跑**，与 `--publish never` 无关。因此失败不限于发布：本地 `pnpm run pack` 与 CI 的打包作业一起坏。

同时，这次排障本身也是被掩盖的：`workflow_dispatch` 的标签输入被填成了一个与当前版本不符的历史标签，`checkout` 的 `ref: inputs.tag` 于是把整个运行拉回旧提交，用旧 Node 跑旧测试，最后以 `Worker ... SIGSEGV` 收场；而"标签与版本不一致"的校验当时排在 `check` **之后**，永远没机会报出来。

**理由**：

1. **配置应当描述"这次构建要什么"，而不是"某个生成物必须存在"。** 发布说明是构建产物，本地构建与 CI 打包作业里本来就没有它；把一个缺了就抛错的键指向生成物，等于把"每个开发者都得先跑一遍生成脚本"变成隐含前提。
2. **显式写入比隐式回退更可靠。** electron-builder 确实有隐式回退（`release-notes.md` 在候选列表里，`resolveReleaseBody` 也会读它），但它是**未文档化的**、且只在**创建** Release 时生效 —— 对"重跑/补发/Release 早已存在"这些情况不会刷新 body。工作流自己 `gh release edit --notes-file` 让 body 与本次生成的 notes 一致，与创建路径无关。
3. **失败要早、要指向原因。** 标签校验前置后，填错标签（或填了历史遗留标签）在几十秒内以一句明确的报错结束。原来它排在构建之后，代价是十几分钟的构建 + 一段指向原生崩溃的误导性日志。
4. **发布说明为空也是一种静默失败。** 加了断言之后，"页面上只有产物、没有变更内容"会变成红灯，而不是等人自己发现。

**被否决的替代方案**：

- **保留 `releaseInfo.releaseNotesFile`，在仓库里提交一份 `release-notes.md`**：生成物进版本库会让 `bumpp` 的"工作区必须干净"检查误判；而且它会被嵌进 `latest*.yml` 的 `releaseNotes`，用户更新时看到的是仓库里那份过期内容。
- **只在 `pack:publish` 上用 CLI 覆盖 `-c.releaseInfo.releaseNotesFile=release-notes.md`**：可行，但把同一事实拆到两处（配置 + 命令行），且仍然依赖 electron-builder 的创建时机。
- **让打包脚本 `touch release-notes.md`**：用一个空文件绕过配置校验，等于把"文件必须存在"这条假前提固化下来。
- **只依赖隐式回退（不设配置、也不显式写入）**：技术上能跑通（缺失时安静跳过），但 body 只在创建时写入，重跑不刷新，且依赖一条未文档化的隐式路径 —— 与 ADR-0013 的"终态断言"精神不符。
- **把标签校验留在构建之后**：见理由 3。

**影响**：

- `electron-builder.yml` 里不再有 `releaseInfo`；发布说明的唯一写入点是 release 工作流。
- release 工作流的步骤顺序变为：校验标签与版本 → 安装依赖 → 静态检查 → 构建并校验 → 生成 Changelog → 创建 Release 并上传产物 → **写入发布说明并确保已发布** → 附校验值 → 断言终态 → 归档。
- 发布后的终态断言多了一条：`body` 必须非空且提到本次标签。
- 本地 `pnpm run pack` / `pnpm run verify` 不再依赖任何生成物存在。
- 指向过期提交的标签现在会在构建之前被明确拒绝，不会再以"旧 Node + 旧测试 + SIGSEGV"的形式出现。
- ⚠️ 若将来有人想"顺手"把发布说明写回 `electron-builder.yml`，请先读 `docs/packaging.md` 第 7 节的那条警告。

## ADR-0015

**决定**：密文缓存的接管范围（接管点 B）从"整个 `whatsapp.net` 域"收窄到**媒体 CDN 域**：`*.cdn.whatsapp.net` 后缀，加上已知的裸媒体域 `mmg.whatsapp.net`。判据落在 `src/main/capture/cachekey.ts`，由 `test/unit/cachekey.test.ts` 与 `scripts/check-capture.ts` 锁住。

**状态**：已生效（取代此前只写在代码注释里的"按后缀匹配整个 `whatsapp.net`"）

**背景**：接管点 B 原来的判据是 `hostname.endsWith('.whatsapp.net')`，理由写在 `src/shared/constants.ts` 里："用后缀而非全名匹配，是为了容忍上游在多个 CDN 域名间切换"。理由本身成立，但范围定得太宽 —— 上游把网页自身的资源也放在同一个域下。`test/unit/cachekey.test.ts` 当时把 `static.whatsapp.net` 会被识别断言为 `true`，并在注释里写明"收紧匹配范围属于设计变更 —— 先写 ADR，再改这里的断言"。

一次真实运行留下了数据。同一台机器上 `~/.local/share/waachat/cache/` 共 161 条：

| host | 条数 | 实际内容 |
|---|---|---|
| `static.whatsapp.net` | 96 | 上游页面的 JS / CSS / 字体（`/rsrc.php/...`） |
| `media-hkg{1,4}-{1,2}.cdn.whatsapp.net` | 63 | 媒体密文（`/v/t6{1,2}.../`） |
| `webtp.whatsapp.net` | 1 | 文档预览页 HTML |
| `flows.whatsapp.net` | 1 | 流程页 |

即 61% 的缓存是**明文网页资源**，而 `docs/security.md` 对这个目录的性质声明是"密文缓存……危害较低（仍是密文）"。除了声明与事实不符，还有一个更实际的代价：资源一旦从我们的缓存返回，就**绕过了 Chromium 自己的 HTTP 缓存重校验**，上游发版后页面可能长期加载到旧模块 —— 而这个缓存当时连容量上限与 TTL 都还没有（见 `capture/protocol.ts` 的 `TODO(M3)`）。

**理由**：

1. **"媒体 CDN"是接管点 B 的前提，不是它的结果。** `docs/media-capture.md` 第 3 节把 host 过滤写成"只接管媒体 CDN，不干扰其余流量"；宽匹配让代码与这句话不一致。
2. **两种失败不对称，而只有一种可以容忍。** 漏判的代价是"又下载一次"；误判的代价是往一个承诺只放密文的目录里塞明文，并改变页面的资源加载语义。白名单（宁可漏判）与接管点 B 自己的原则一致。
3. **后缀仍然保留，只是换成了 CDN 那一段。** 实测同一时刻同时存在 `media-hkg1-1` / `media-hkg1-2` / `media-hkg4-1` / `media-hkg4-2`，判据必须覆盖"区域 + 编号"维度上的切换 —— 收窄的是**域**，不是匹配方式。
4. **代价是可见的、可判定的。** 上游若把媒体搬到 `cdn.whatsapp.net` 之外，症状是"二次点击又联网"，判定方法见 `docs/media-capture.md` 第 5 节；`scripts/check-capture.ts` 也会因为断言失败而变红。

**被否决的替代方案**：

- **保持整个 `whatsapp.net`**：就是被取代的现状 —— 61% 的污染，外加绕过 HTTP 缓存重校验。
- **写死 host 全名列表（`mmg` / `media-hkg1-1` …）**：区域与编号会变，列出来的那天就开始腐烂 —— 正是原注释要躲开的问题。
- **按路径形状匹配（`/v/`）**：与"接管逻辑不得依赖上游内部结构"冲突（`docs/media-capture.md` 第 1 节），且路径一变就静默失效。
- **改成按响应 `Content-Type` 判断（只缓存非文本）**：判据落在**响应**上，而缓存键要在**请求**阶段决定，两者会分叉（同一个键在不同时刻可能一个缓存、一个不缓存）；而且要"只缓存二进制"，就得先假定上游给密文发的类型一定不是 `text/*` —— 这是一个我们无法验证的假设。
- **顺手把容量上限与 TTL 一起做掉**：那是 M3 的范围。本 ADR 只回答"哪些请求该进缓存"。

**影响**：

- `static.` / `webtp.` / `flows.` 等域下的请求只走直通，不再落盘（页面重新使用 Chromium 自己的 HTTP 缓存）。
- `src/shared/constants.ts` 不再导出 `MEDIA_HOST_SUFFIX`；判据挪进 `cachekey.ts`（唯一使用方）。它仍是纯函数，单测与自检都能覆盖。
- ⚠️ **已经写进缓存的污染条目不会被自动清理**：容量与淘汰仍属 M3。`cache/` 是纯派生数据（`docs/security.md`），用户可随时手工删除。
- 新增媒体域要同时改 `cachekey.ts`、`test/unit/cachekey.test.ts` 与 `scripts/check-capture.ts` 三处 —— 这是有意的：判据的变化必须留下痕迹。

## ADR-0016

**决定**："缓存条目要带上哪些响应头"是一份显式白名单，落在 `src/main/capture/headers.ts`（`CARRIED_HEADERS` / `carriedHeaders()`），接管点 B 的落盘与回放都只能通过它。白名单内容的变化属于**语义变化**，必须同时提升 `capture/protocol.ts` 的 `CACHE_VERSION`，让按旧语义写下的条目在下一次读取时按未命中处理（重新回源自愈）。

**状态**：已生效

**背景**：接管点 B 原先只回放四个头（`content-type` / `content-length` / `etag` / `last-modified`），其余一律丢弃。这在那份清单只覆盖"媒体密文"时是对的 —— 密文只是一坨字节，页面自己解密。但一次真实运行里，`web.whatsapp.com` 把文档预览放进 `webtp.whatsapp.net` 的 iframe（它自己的 CSP `frame-src` 就列了这个域），而实测 `web.whatsapp.com` 的响应带 `cross-origin-embedder-policy: require-corp` 与 `cross-origin-opener-policy: same-origin`。父文档启用 COEP 时，被嵌的子文档**也必须**带 COEP，否则按"未启用 COEP、不可嵌入"被拦截 —— 症状正是 `ERR_BLOCKED_BY_RESPONSE`，而缓存命中时它才出现（首次点击走回源，一切正常）。这类头漏一个，坏掉的是页面的一部分，且报错指向不了缓存。

**理由**：

1. **"这份响应怎么被处置"和"这份响应的正文"是两件事，而缓存只想过问后者。** 所有会改变浏览器如何处置响应的头（COEP / COOP / CORP / CSP / `x-frame-options` / `x-content-type-options`）都必须与正文一起回来；否则我们回放的是一份**语义上不同**的响应。依据是标准内核行为（响应头语义），不涉及任何上游内部结构，符合 `docs/media-capture.md` 第 1 节。
2. **白名单，而不是"存下来再删几个"。** `cache/` 的性质声明是"里面只有密文"（`docs/security.md` 第 2 节）。黑名单只要漏掉一个 `set-cookie`，凭据就落进了那个目录 —— 这与 `docs/security.md` 的单向承诺冲突。白名单的失败模式是"少带一个头，页面坏掉且看得见"，可接受。
3. **`content-encoding` 必须排除，这是白名单的第二个理由。** 正文来自 `net.fetch`，按 fetch 语义已经是解码后的字节；回放时带上它会让浏览器再解一次。黑名单写法很容易把它当成"描述正文的头"一并存下。
4. **清单变化必须让旧条目失效。** 缓存条目的响应头是按**写入时**的清单固化的。若只改清单不失效旧条目，症状是"只在老用户机器上复现的页面损坏"——新装用户第一次点击就回源、写的是新语义，查不出问题。`CACHE_VERSION` 把这件事变成可判定的：版本不符即按未命中处理，重新回源即可自愈，且不需要用户手工清目录。

**被否决的替代方案**：

- **继续保留四个头的硬编码清单**：就是被取代的现状，等价于 ADR-0015 的 COEP 缺失。
- **黑名单（存下除 `set-cookie` 等以外的全部头）**：一次遗漏就把凭据写进一个承诺只放密文的目录，且没有编译期或运行期的拦截点；`content-encoding` 也容易误存。
- **缓存回放时完全不带头**：`content-type` 缺失会让页面拿到错误类型，`content-length` 缺失影响进度与流式处理。
- **改清单但不提升版本**：老用户那边的坏条目会长期留在盘上，且与新装用户行为不一致。
- **回放前清空整个 `cache/` 目录**：把"缓存格式升级"扩大成"丢掉所有缓存"，且需要一次带副作用的启动步骤；版本字段是就地、增量、可判定的。

**影响**：

- 新增/移除一个携带头 = 改 `capture/headers.ts` **并**提升 `capture/protocol.ts` 的 `CACHE_VERSION`。两处分离是刻意的：前者回答"带什么"，后者回答"什么时候答案变了"。
- `CACHE_VERSION` 从 2 起步（1 是从未写成常量的隐含旧语义）；缺失或不是当前值的条目一律不回放，表现为该次请求重新回源。
- 上游将来新增一个"决定能不能用"的头（`permissions-policy`、`document-policy` …）时，必须补进白名单并再次提升版本。这件事记在 `headers.ts` 的模块注释里，也是 `scripts/check-capture.ts` 关注的类型。

## ADR-0017

**决定**：不再发送"文件已归档"的桌面通知。删除 `src/main/integration/notify.ts`，并从 `Settings` 去掉 `notify` / `notifyIncludeName` 两个字段（连同设置界面的两个开关）。

**状态**：已生效（取代 `notify.ts` 里"默认不显示文件名"的那套折中）

**背景**：接管点 A 在归档完成后会发一条系统通知，标题是"文件已归档"，正文默认只有大小、可选带文件名。`notify.ts` 的模块注释记着它当时的隐私论证：通知会出现在锁屏与通知中心，可能被旁人看到、被同步到手机、被记进系统日志，而文件名往往就包含通信内容本身（"2026Q3合同-某某公司.pdf"）。因此当时的结论是"默认不带文件名，但保留通知"。

**理由**：

1. **通知没有传达用户还不知道的事。** 归档总是紧跟在用户自己的点击之后（这是接管点 A 的唯一触发路径），而默认行为是"归档完直接打开文件"。用户此刻正盯着屏幕，通知在时间与内容上都是冗余的 —— 它是一句"你刚做的事已经做完了"。
2. **少一个功能，就少一个隐私面与一个失效面。** 删掉它，就同时消除了"文件名出现在锁屏上"这一整类风险（不再依赖那个默认关闭的开关），也不再需要维护"通知在无通知守护进程 / 勿扰模式下的行为"这类平台差异。
3. **它唯一不可替代的价值属于界面状态的职责。** 通知真正有用的场景只有一个：**文件没有自动打开**时告知用户。而这正是 `capture/health.ts` 在做的事 —— "接管失效必须可见"（见 `docs/architecture.md` 第 5 节）。把它交给健康状态而不是系统通知更可靠：通知可能被勿扰吞掉、被用户关掉，而健康状态在界面上始终可查。

**被否决的替代方案**：

- **保留开关、改为默认关闭**：一个存在的功能就有一个隐私面与一个失效面要维护；而且默认关闭之后，它对新用户而言已经等于不存在，只是为老用户留着。
- **只在文件未自动打开时通知**：会让"通知"与健康状态两套机制表达同一件事。用户仍会在最不需要打扰的时刻被打扰一次。
- **保留通知但永不显示文件名**：那正是原实现；它保住了安全，却保不住"这条通知有没有用" —— 只显示大小（"已归档 1.2 MB"）的通知对用户几乎没有信息量。

**影响**：

- `src/main/integration/notify.ts` 删除；`docs/README.md` 的目录树、`docs/architecture.md` 与 `ai/CONVENTIONS.md` 里"integration 的职责"描述同步收窄为"交系统打开 / 托盘"。
- `settings.json` 里残留的 `notify` / `notifyIncludeName` 会被 `settings.ts` 的 `coerce()` **静默丢弃**（它按 `DEFAULT_SETTINGS` 的键逐个取值），因此不需要迁移步骤。
- **页面自己的通知不受影响**：上游网页版的消息通知走的是会话权限白名单里的 `notifications`（`src/main/session.ts`），与本 ADR 无关。托盘的存在理由（常驻以维持长连接、让页面通知能到达）也不变。
- 若将来要恢复"归档结果的通知"，必须先推翻本条，并在 ADR 里说明为什么健康状态不足以承担它。

## ADR-0018

**决定**：归档目录改为**用户可配置**，默认 `~/Documents/WhatsApp_files`（此前硬编码为 `~/.local/share/waachat/media`）。设置项是 `Settings.archiveDir`，空串表示"用默认位置"；取值一律经 `paths.normalizeArchiveDir()` 规整，不可用时回落到默认位置。归档索引数据库**随归档目录走**：`<归档目录>/.index.sqlite`。

**状态**：已生效（取代 [ADR-0008](#adr-0008) 里"归档放在 `XDG_DATA_HOME` 下"的具体路径选择；ADR-0008 的核心原则——三类数据分开存放——不变）

**背景**：原路径的理由是"应用数据归 XDG"。但归档不是应用数据 —— 它是**用户自己打开过的文件**。放在 `~/.local/share/waachat/media` 的后果是用户根本找不到它：点开 `~/Downloads` 空空如也，只有点"在文件夹中显示"才会被领到一个他从未见过的、以 `~/.` 开头的隐藏目录。而 `docs/usage.md` 早就在教用户"把归档指向加密卷"、"不要放进云同步盘"——这些建议都要求用户能自己找到并移动这个目录。

**理由**：

1. **归档的性质是"用户的文件"，不是"应用的内部状态"。** `XDG_DATA_HOME` 是给后者用的；前者的正确默认位置是用户自己的文档目录。
2. **用户必须能自助管理它**：备份、挪到加密卷、决定是否纳入自己的同步策略。做不到这一点的目录，等于要求用户依赖文档描述一个他找不到的路径。
3. **索引必须跟着归档走。** 索引描述的就是这个目录里的内容（"跟着归档一起备份或一起删除才是对的"）。两者分离会出现"搜得到但打不开"的悬空状态，而且 `退出时清除归档` 之后索引不会跟着空。放在归档目录内部还有一个附带好处：它以 `.` 开头，`usage()` 与 `sweepTempFiles()` 会自动跳过它，不会被当成一份归档文件统计或清理。
4. **默认值必须可解释、可发现。** `~/Documents/WhatsApp_files` 是一个用户能自己念出来、自己找到、自己删掉的位置。

**被否决的替代方案**：

- **保持 `~/.local/share/...` 但加一个"打开所在目录"按钮**：治标。用户仍然无法自助备份与迁移，而这恰恰是这个目录最需要的两件事。
- **把归档直接铺在 `~/Documents` 下**：哈希名的文件会散落在用户的文档里；更糟的是 `退出时清除归档` 的删除范围会覆盖用户自己的文档。必须有一个专用子目录。
- **可配置但不校验（用户给什么就用什么）**：`退出时清除归档` 会清空用户给的那个目录。用户手改 `settings.json` 写一个 `/` 或家目录就是灾难性的。因此 `normalizeArchiveDir()` 拒绝空值、相对路径、层级不足两段的路径（`/`、`/home`、`/opt`）与家目录本身，并且它是纯函数、被单测与 `scripts/check-capture.ts` 双重覆盖 —— 那是"用户手改配置文件之后"唯一的防线。
- **索引留在 XDG 目录**：会出现"索引里有记录、新目录里没有文件"。换位置本来就该是一次完整的切换。
- **换位置时搬移已有文件**：可能是一个几十 GB 的内容库，跨文件系统还是复制。把它绑在一次点击之后，是拿用户的磁盘赌一把。界面改为明确提示"旧文件仍在原目录"。
  > ⚠️ 这一条已被 [ADR-0019](#adr-0019) 取代：换位置现在**会**迁移数据 —— 但补上了当时缺的东西：确认框、进度、失败回滚。当时真正缺的是这些，而不是"不该搬"。
- **把"保存位置"列为需要重启的设置**：用户换完位置后下一次点击就应该落到新目录，这是他能观察到的最直接的反馈。`RESTART_REQUIRED_SETTINGS` 留给架构上无法热切换的项（协议注册）。

**影响**：

- **默认位置变化会让已有用户的旧归档不再出现在归档界面里**。文件仍在 `~/.local/share/waachat/media`，可以手工搬过去，或在设置里把保存位置指回原目录。项目仍处 M1 阶段、尚未发布，接受这个一次性变化。
- `ensureArchiveDir()` 现在会在目录**已存在**时也把权限收紧到 `0700`：默认位置在用户的文档目录下，用户完全可能自己先建好了那个目录（权限通常是 0755），而 `mkdirSync` 的 `mode` 只对新建生效 —— 那条路径上"目录必须 0700"会静默失效，而里面是解密后的明文。收紧失败会记一条 warn，不阻断启动。
- 索引连接在换位置时会被重开（`archive/store.ts` 的 `applyArchiveDir()`），因此 IPC 层**不能**缓存 `archiveStore()` 的返回值。
- 退出清理（`wipeArchiveOnExit`）在删目录之前必须先 `closeArchiveStore()`，否则 WAL 会把刚被删掉的 `.index.sqlite` 写回来。
- ⚠️ **与 `docs/usage.md` 的"不要把归档放进云同步盘"存在张力**：`~/Documents` 在国内外的桌面环境里都常被同步客户端覆盖。取舍是"可发现性优先"，风险由设置页的提示与使用说明承担；文档里那条警告必须保留。
- ⚠️ **换位置不回退进行中的下载**：下载临时文件在旧目录，而提交时目标路径按新目录计算，跨文件系统的 `rename` 会失败并被记为 `write-failed`（界面上可见）。窗口很小（只有在切换的那一刻恰好在下载时才可能），但没有更好的处理办法 —— 临时文件的位置在下载开始时就已经定下了。
- 归档目录之外的存放位置（登录态、密文缓存、日志）不变，`docs/usage.md` 与 `docs/architecture.md` 的目录图随之更新。

## ADR-0019

**决定**：更换归档保存位置变成一次**带确认与数据迁移**的操作：

```
选目录 → 校验目标并算出迁移计划 → 确认框（从哪、到哪、多少个文件、多大）
      → 迁移（正文 + 索引；派生物不搬）→ 设置落盘 → 切换进程内目录
```

用户在**任一步**取消，存储位置与数据一点都不变。迁移失败时把已搬走的条目搬回原位；搬不回来时明确告知"两侧都可能留有数据，请人工核对"。迁移进度通过 `archive:migration` 单向推送到界面。`setSettings({ archiveDir })` 现在会**抛错** —— 改这一项只能走这条流程。

**状态**：已生效（取代 [ADR-0018](#adr-0018) 里"换位置不搬移已有文件"那一条）

**背景**：ADR-0018 把归档位置交给用户决定，但换位置只切一个指针：数据留在旧目录，用户回到归档界面看到的是一片空白。当时的理由是"搬移一个可能几十 GB 的内容库不该发生在一次点击之后"——这个顾虑成立，但它针对的是**没有确认与回滚的搬移**，而不是搬移本身。

**理由**：

1. **这一步的后果是"我的文件还在不在"，属于不可逆后果。** 它必须由用户在看清"从哪搬到哪、搬多少"之后明确确认，而不是在他选完目录的瞬间静默完成。
2. **真正的风险不是"搬得慢"，而是"搬了一半"**：一部分文件在新位置、一部分还在旧的，而设置只认得其中一边。因此迁移的首要目标不是速度而是"要么全成、要么全不成"。回滚因此**只做搬运，不做删除** —— 在可能持有唯一副本的目录里"顺手删干净"是这类代码里最不可原谅的写法（`archive/migrate.ts` 的注释记着这条）。
3. **索引连接必须先断开。** WAL 模式下可能还有没 checkpoint 的改动，不关连接就搬走的是半个库 —— 症状是"迁移后归档界面少了一部分记录"，归因极难。
4. **进度必须可见。** 跨文件系统时迁移是一次真实的复制（几十 GB），没有进度用户会以为界面死了，然后去杀进程 —— 而杀在复制中途正是最糟的时机。
5. **目标必须为空。** 内容寻址的归档是**一个**库：把两个库合在一起要逐条重写索引，而"哪条记录属于哪份文件"没有可靠判据（同一个哈希在两边的文件名可能不同）。宁可让用户选一个空目录，也不做没有正确性论证的合并。

**被否决的替代方案**：

- **先落设置再搬数据**：失败窗口更大（设置已指向新位置、数据还在旧的），而"回滚设置"本身也要写盘 —— 一次磁盘满就把用户卡在中间状态。现行顺序是"先搬数据、再写设置"，任一边失败都撤销另一边。
- **后台静默搬移**：用户看不到进度，也就无法判断"现在能不能关机"。
- **把派生物也搬过去**（`.open/` 硬链接、`.part-*` 半成品）：硬链接复制后会指向新 inode，在新位置留下一批与正文脱钩的文件；而它们本来就能从正文重建（启动时重建与清扫）。搬它们只有坏处。
- **回滚时清空新位置**：那里可能有并发写入的东西，也可能有我们没搬回来的。唯一允许删除的是最后那个空的、由我们创建的目标目录（`rmdir`，非空时会失败，失败就留着）。
- **目标非空时合并两个归档库**：见理由 5。
- **允许从设置通道直接改 `archiveDir`**：会得到"设置指向新目录、数据还在旧目录"的半截状态，而且要到下次重启才显形。现在这个通道**抛错**而不是静默忽略 —— 静默会让调用方以为改动生效了。
- **用系统通知报告迁移结果**：与 [ADR-0017](#adr-0017) 冲突（通知会落到锁屏与通知中心）。结果由设置页的状态行承担：进程内、即时、不留下痕迹。
- **不许取消（确认框只有一个按钮）**：确认框必须能退出。取消是这条流程里唯一"零后果"的分支，把它抹掉会让用户在选错目录时只能硬着头皮往前。

**影响**：

- 新增三个文件：`archive/migrate.ts`（计划、执行、进度、幂等回滚；不导入 electron 与 store，因此可单测）、`archive/relocate.ts`（编排"搬数据"与"落设置"，失败时双向回滚）、`shared/migration.ts`（主进程对话框与界面状态行**共用**的文案）。
- `archive:pick-dir` 的语义变了（现在还负责迁移），并新增推送通道 `archive:migration`；`bridge` 相应新增 `onArchiveMigration` 并在窗口卸载时取消订阅。
- 迁移**不回退进行中的下载**：临时文件在旧目录，而提交时目标按新目录算，跨文件系统的 `rename` 会失败并被记为 `write-failed`（界面可见）。迁移自身会在收尾时再扫一遍源目录，把并发写入的正文补搬过去（最多三轮）。
- 跨文件系统迁移会真的复制一份，临时名沿用 `.part-` 前缀 —— 进程在复制中途被杀时，残留会被下次启动的 `sweepTempFiles()` 清掉。
- `scripts/check-capture.ts` 增加了"迁移目标不能是自己/子目录/上级"的离线断言（纯字符串判据，不需要文件系统）。

## ADR-0020

**决定**：项目名与全部身份标识统一为 **`WaaChat`**：npm `name` = `waachat`、`productName` = `WaaChat`、appId / `desktopName` / `StartupWMClass` = `io.github.edwinhuish.waachat`、`executableName` = `waachat`、AppArmor profile 名 = `waachat`、会话分区 = `persist:waachat`、preload 暴露的全局名 = `window.waachat`。

名称**不含**服务方名称，因此 [ADR-0011](#adr-0011) 里为名称所做的商标论证不再适用；但**非官方声明的强制义务保留**（[INV-4] 的陈述未变，只是立论换了）。本 ADR 确认名称的最终形态，并收敛 [ADR-0011](#adr-0011) 的名称部分。

**状态**：已生效

**背景**：ADR-0011 的商标基线是"不使用视觉标识资产"，但对项目名本身只给了"指称性使用"这一条较宽松的辩护。所有者要求把名称收敛到一个不含服务方名称、又不失辨识度的形态，并在 `README.md` 顶部等显著位置加强"非官方"声明。

**理由**：

1. **名称里的服务名是风险最集中的一处，而它换来的只是"别人一眼看懂"。** 红线（视觉资产）不能动，功能端点（承载的网址、兼容性说明）必须保留，剩下可调整的只有名称。`WaaChat` 既保留了"用来做什么"的联想，又不再直接使用服务方名称。
2. **但名称与知名服务仍然近似**，而应用本身就是承载该服务网页版的宿主 —— 用户看到 `WaaChat` 完全可能以为是官方客户端。所以声明义务**不能跟着名称一起退休**，反而更该说清楚。这正是本条要把"声明义务"从 ADR-0011 的"指称性使用的补偿"里**拆出来**的原因：它现在是 INV-4 自身的要求，不再依附于名称的商标论证。让声明随名称一起消失，等于把风险留给最不设防的那个人。
3. **身份标识必须一次对齐。** "名字"散落在六处身份声明（`package.json` 的 `name`/`desktopName`、`electron-builder.yml` 的 `productName`/`appId`/`executableName`/`StartupWMClass`、`src/shared/constants.ts` 的 `DESKTOP_FILE_NAME`/`APP_ID`/`SESSION_PARTITION`、AppArmor profile 的文件名与声明名、产物 `.desktop` 条目、preload 暴露的全局名）。漏一处的症状恰好是本仓库最想拦住的那一类：**构建全绿、运行时静默失效**（Dock 占位图标、启动器不合并），而且只有 `pnpm run verify` 抓得到。因此身份标识一旦变动，`verify` 是必跑项。

**被否决的替代方案**：

- **在名称里直接使用服务方名称**：所有者决定不使用它。
- **回到完全中性的名字**：商标上最安全，但失去"这个名字说明了它做什么"的信息量。所有者选的是折中。
- **改名（或改标识）的同时取消非官方声明**：见理由 2。
- **只改文档标题，不改包名与可执行名**：最糟的一种"半改" —— 文档说 `WaaChat`，产物却叫别的，用户装完看到一个与说明不符的包名，而身份四处同源的断言也会被破坏。

**影响**：

- 会话分区是 `persist:waachat`，Electron 的 userData 是 `~/.config/waachat`；密文缓存在 `~/.local/share/waachat/cache`，日志在 `~/.cache/waachat/logs`。
- 归档位置与本 ADR 无关：那是用户的文件，不该因为应用身份标识而移动。
- 仓库 URL 为 `https://github.com/edwinhuish/waachat`（`homepage` / `repository` / `bugs` / `publish.repo` 同源）。⚠️ **这要求 GitHub 上的仓库确实叫这个名字**：名称对不上时 `pnpm run release` 会失败，而 `electron-updater` 的失败是**静默**的（它只是永远找不到新版本）。

## ADR-0021

**决定**：归档的默认位置改为 **`~/Downloads/WaaChat_files`**（此前 `~/Documents/WhatsApp_files`），并在**首次启动时自动创建** —— 包括 `~/Downloads` 本身，如果它还不存在。设置项、迁移流程（ADR-0019）与"索引随归档目录"（ADR-0018）均不变。

**状态**：已生效（取代 [ADR-0018](#adr-0018) 的默认值）

**背景**：ADR-0018 把默认值定在 `~/Documents` 下，理由是"可发现、可解释"。实际使用暴露两点：

1. **`~/Documents` 在很多桌面环境里是同步盘的领地**（Dropbox / OneDrive / iCloud / 坚果云）。ADR-0018 当时就承认了这处张力，并把风险交给文档承担 —— 但默认值本身不该落在一个"常见情况下就是错"的位置上，尤其里面的东西是**解密后的明文**。
2. **它解释了更少的直觉。** 本项目要消灭的行为是"点文件 → 落进 `~/Downloads` → 手工去找"。用户对"我下载的东西在哪"的直觉就建立在 `~/Downloads` 上。把归档放在那里（收在一个子目录里，而不是散落）反而更好懂：**东西还是去了它该去的地方，只是不再有 `报告 (1).pdf`、`报告 (2).pdf`**。

**理由**：

1. 对齐用户已有的直觉，而不是要求他学一个新的默认位置。
2. 默认值不再落在最常见的同步盘目录里。
3. **自动创建必须由应用自己做。** `~/Downloads` 在精简桌面环境里**可能不存在**（服务器、最小 WM、容器），而"默认目录建不出来"会表现为第一次点文件时报一个与路径无关的错误。`mkdirSync(recursive: true, mode: 0o700)` 会把缺失的父目录一起补上，并且在**启动装配时**就完成（`applyArchiveDir()` → `ensureArchiveDir()`），不依赖用户先点一次文件。

**被否决的替代方案**：

- **保持 `~/Documents`**：见背景第 1 点。
- **直接用 `~/Downloads` 根目录**（不套子目录）：哈希名的文件会和用户自己的下载混在一起，而且"退出时清除归档"的删除范围会覆盖用户自己的下载 —— 那是不可原谅的越界。
- **不自动创建，等第一次点文件时再建**：那时失败会被包装成含糊的 `write-failed`，而真正的原因（父目录不存在、不可写）看不到。启动时就建，失败会进日志，界面上的健康状态也查得到。
- **首次运行时弹"请选择保存位置"向导**：把一次性的决定塞进首次启动流程，会挡住"我就是想直接用"的用户。默认值 + 随时可改（ADR-0019 的迁移流程）已经够用。

**影响**：

- 已有用户的归档**不会**自动搬家：用户可配置的位置只有用户自己改才会动。旧目录里的文件仍在原处，想合并过来就用设置里的「更改…」，它会走 ADR-0019 的迁移流程。
- 新装用户第一次启动后即可在 `~/Downloads/WaaChat_files` 看到归档目录，权限 `0700`。
- `docs/usage.md` 里原有一句"文件不会落进 `~/Downloads`"必须改写成"不会**散落**在 `~/Downloads` 根目录里"，否则它与新的默认值自相矛盾。
- `scripts/check-capture.ts` 与 `test/unit/paths.test.ts` 的默认值断言同步更新。

## ADR-0022

**决定**：设置里可以更换应用图标。分工如下：

- **窗口与托盘图标立即生效**（`BrowserWindow.setIcon()` / `Tray.setImage()`）。
- **启动器 / Dock 图标**通过写一份**用户级** `.desktop` 覆盖实现，落在
  `~/.local/share/applications/io.github.edwinhuish.waachat.desktop`，其 `Icon=` 指向
  `~/.config/waachat/custom-icon.png`。
- **解码与裁剪在渲染进程的 canvas 里做**，主进程只接收裁剪好的 512×512 PNG 字节。
- 失败时回滚到原状（要么全成、要么全不成），并保留原图标。

**状态**：已生效

**背景**：需求是"设置里能换图标、PNG / JPG / ICO 都行、改完立刻生效、失败保留原图标、
能恢复默认"。这在 Linux 上不是一件事，而是三件 —— 而且**没有一层能同时满足"改得动"与
"立刻看得见"**：

| 落点 | 由谁决定 | 能否立即改 |
|---|---|---|
| 窗口图标 | `_NET_WM_ICON`（X11） | X11 能；**Wayland 不能**（合成器按 `app_id` 取） |
| 托盘图标 | 应用自己 | 能 |
| 启动器 / Dock 图标 | `.desktop` 的 `Icon=` | 不能 —— 要等桌面刷新或重新登录 |

**理由**：

1. **`nativeImage` 只保证 PNG / JPEG，而需求点名了 ICO。** ICO（以及 WebP、BMP）只有 Chromium
   的图片解码器认得，而那个解码器在渲染进程里。因此"解出像素"这一步必须在渲染进程做 ——
   这不是把能力下放，只是把一次**纯计算**放到有那个库的地方。
2. **但权力不下放。** 渲染进程从主进程收到的是**字节**（主进程用对话框读出来的），送回的是
   **裁剪好的 PNG 字节**。落盘位置、文件名、权限、要不要写启动器条目，全部由主进程决定；
   主进程还会用 `nativeImage` 自己再解一次，确认它确实是一张 512×512 的图。因此
   `ai/INVARIANTS.md` 的 G-1 与 T2 都没有被绕过：界面依然拿不到路径，也构造不出一个路径。
3. **写用户级 `.desktop` 而不是系统目录。** 那本来就是"用户覆盖"这套机制（XDG 的查找顺序里
   用户目录优先），因此不需要 root，卸载时系统那份也仍然完好。
4. **必须能整体回滚。** 写启动器条目失败时把图标文件恢复原样 —— 否则用户得到的是
   "窗口换了、启动器没换"这种解释不清的状态。这与 ADR-0019 对迁移的取舍是同一条原则。
5. **绝不覆盖用户自己写的同名片条。** 判据是文件里的 `X-WaaChat-Managed=true`。没有这个标记
   就说明那是别人的东西：我们报 `desktop-entry-conflict` 并放弃这次修改，而不是把它冲掉。

**被否决的替代方案**：

- **只在主进程用 `nativeImage` 处理**：代码更少（少一次跨进程往返、少一段 canvas 逻辑），但
  ICO 支持变成"看运气"。需求点名了 ICO，不能赌。
- **引入 `sharp` / `jimp`**：能解决格式问题，但要引入原生依赖 —— 打包体积、AppImage 的 glibc
  矩阵、`npmRebuild` 的取舍全都要重来一遍。为一张图标不值得。
- **把"是否启用自定义图标"写进 `settings.json`**：多出"设置说启用了、文件却不在"的分裂状态。
  文件存在与否本身就是开关，图标也没有第二个消费者。
- **写 `~/.local/share/icons/hicolor/`**：要按尺寸铺多档、维护主题缓存，还要与服务方视觉资产
  的边界纠缠。写一份绝对路径，桌面环境自己会缩。
- **不写 `.desktop`，只改窗口与托盘**：在 Wayland（Ubuntu 24.04+ 的默认会话）下用户很可能
  一点变化都看不到 —— 功能看起来就是坏的。因此这一版三层都做，并在界面上**如实说明**
  启动器图标需要重新登录桌面。

**影响**：

- 新增落盘：`~/.config/waachat/custom-icon.png`（0600），以及有条件存在的
  `~/.local/share/applications/<appId>.desktop`。都在用户自己的目录里，「恢复默认」会一起清掉
  （后者仅当带我们的标记）。见 `docs/security.md`。
- **开发模式下不写启动器条目**：那时的 `Exec` 只能指向 `node_modules` 里的 Electron，
  写进启动器只会多出一个点不开的图标（同 `integration/login.ts` 的判断）。
- 界面上必须写明三层各自的生效时机，不能含糊成一句"已更换图标" —— 否则 Wayland 用户会把它
  读成"功能坏了"。
- `pnpm run selfcheck` 增加了一组离线断言（接受的格式、裁剪几何、`Exec` 引号化、启动器条目里的
  非官方声明与 `StartupWMClass`）。**裁剪与解码不在其中**：它依赖 DOM，离线跑不了，只能靠
  一次真实的点击。
- 托盘图标的刷新放在 `ipc/index.ts` 而不是 `integration/appicon.ts` —— 否则会出现
  window → appicon → tray → window 的循环依赖。

## ADR-0023

**决定**：归档的默认位置改为 **`~/Documents/WhatsApp_files`** —— 目录回到文档目录下，名字用
服务方名称。这和 [ADR-0018](#adr-0018) 当初的取值**是同一个位置、同一个名字**，因此可以说是
回到 ADR-0018 的取舍，同时保留 [ADR-0021](#adr-0021) 加上的"首次启动自动创建"。

设置项（`Settings.archiveDir`）、迁移流程（ADR-0019）、"索引随归档目录"（ADR-0018）与
"首次启动自动创建"（ADR-0021）全都不变。

**状态**：已生效（取代 [ADR-0021](#adr-0021) 的位置与名称）

**背景**：ADR-0021 把默认值挪到了 `~/Downloads/WaaChat_files`，理由是"对齐用户对'我下载的
东西在哪'的直觉"。所有者不认同这个权衡，要求回到文档目录、并使用 `WhatsApp_files` 这个名字。

**理由**：

1. **归档是用户自己的文件，不是"一次下载"。** `~/Downloads` 是**浏览器行为**的产物，而本项目的
   整个卖点恰恰是"不再需要走一遍下载"。把归档放进下载目录，等于用位置再次暗示"这是一次下载" ——
   与产品定位相反。
2. **文档目录才是用户主动管理的地方。** 备份、挪进加密卷、决定要不要纳入自己的同步策略，
   这些动作都发生在 `~/Documents` 下。ADR-0021 没有推翻 ADR-0018 的这条理由，只是拿"直觉"换掉了它。
3. **目录名要回答的是"这些是谁的文件"。** 用户在自己文件管理器里的上下文是"哪个聊天服务"，
   不是"哪个程序写的" —— `WhatsApp_files` 一眼就说清了。这与代码里出现 `web.whatsapp.com`
   同类：**指示性使用**，指称对象而不主张权利，也不涉及任何视觉标识素材（[INV-4](../ai/INVARIANTS.md)
   约束的是后者）。[ADR-0020](#adr-0020) 收敛的是**应用自身的身份标识**（包名、可执行名、appId、
   图标、桌面条目），不覆盖"数据目录叫什么"这类功能命名。
4. **`~/Documents` 的同步盘风险由文档承担，而不是靠换位置回避。** 这条风险是真实的
   （Dropbox / OneDrive / iCloud / 坚果云 都可能盖住 `~/Documents`），但它不该由"把默认值放到
   一个用户想不到的地方"来解决 —— 那只是把问题藏起来。`docs/usage.md` 第 4 节明确写了
   **不要把归档目录放进云同步盘**，并说明默认位置落在同步范围内时该怎么办。所有者接受这个取舍。

**被否决的替代方案**：

- **`~/Documents/WaaChat_files`**（只改位置、保留项目名）：与项目自身命名一致，但在用户的文件
  管理器里不如 `WhatsApp_files` 说得清"这些是什么"。那个界面的上下文是聊天服务，不是程序名。
- **保持 `~/Downloads/WaaChat_files`**：见背景。
- **`~/Documents/WaaChat`**：与配置目录 `~/.config/waachat` 只差大小写与位置，口头描述时容易混淆。
- **改默认值的同时自动把旧默认目录搬过来**：见影响第 1 条 —— 未经用户确认就搬动他的数据，
  违反 [ADR-0019](#adr-0019) 的迁移原则。

**影响**：

- **从未改过设置的用户会跟着默认值移动。** `archiveDir` 的空串语义是"用默认位置"，因此这次
  改动对他们是**生效的**：应用会去创建并使用 `~/Documents/WhatsApp_files`，而旧默认目录里的
  文件仍在原处、只是在界面里看不见了。两条出路：用设置里的「更改…」指回旧目录，或手工把文件
  搬过来。**不写自动搬迁逻辑** —— 迁移必须先经用户确认（[ADR-0019](#adr-0019)），在用户没有
  动过任何设置的情况下替他搬文件，正是那条 ADR 要避免的。
- 已是自定义位置的用户不受影响（`archiveDir` 非空，与默认值无关）。
- 权限仍由 `blobs.ensureArchiveDir()` 收紧到 `0700` —— `~/Documents` 下常见的是用户自己建的
  `0755` 目录，所以这一步是必须的，不能只依赖 `mkdir` 的 mode（ADR-0018 已经写明）。
- `scripts/check-capture.ts` 与 `test/unit/paths.test.ts` 的默认值断言同步更新；
  `docs/`（`usage` / `architecture` / `security` / `media-capture`）与 `ai/TASKS.md` 里所有
  引用默认路径的地方一并更新。
- `SECURITY.md` 的资产表同步（它是对外承诺的一部分）。

## ADR-0024

**决定**：更换保存位置时，**索引的清单在执行的那一刻才解析**（不沿用计划里的快照），并且**不覆盖目标位置里已有的同名索引**；回滚的清单取自**目标目录本身**，而不是计划。

**状态**：已生效（补充 [ADR-0019](#adr-0019) 的实现细节，不取代其中任何一条）

**背景**：v1.0.1 的"换保存位置"在最常见的一条路径上**必然**失败：

```
启动 → 本地界面打开归档视图（archive:list / archive:stats）→ 索引连接建立，
       `.index.sqlite-wal` / `-shm` 出现
     → 用户点「更改…」，此刻算出迁移计划（两个附属文件进了 entries）
     → 用户确认 → 执行的第一步 closeArchiveStore()（ADR-0019 理由 3）做 checkpoint，
       并把那两个附属文件删掉
     → 迁移照计划去 rename 一个已经不存在的名字 → ENOENT
     → 记成 write-failed，界面说"磁盘可能已满，或该位置不可写" —— 而两者都不是
```

日志里只剩 `{"failure":"write-failed","reason":"Error"}`：fs 错误的 `name` 恒为 `Error`，真正有信息量的 errno 在 `code` 上。**索引连接是应用自身在启动时打开的**，所以这不是边角情形，而是"改了保存位置就报错"。

**理由**：

1. **计划是一份会被下一步动作作废的快照，而"作废"恰恰是设计要求的。** 只能以其中一份为准：目录内容不会骗人，计划会。
2. **索引必须按执行时的实际情况搬。** 迁移窗口里索引可能被重开（用户切到「归档」标签页，或恰好有一次接管写入）：新出现的 `-wal` 不搬走，就在旧目录里留下一个删不掉、也没人引用的残留；反过来，若源目录里出现的是一个新建的**空库**，绝不能拿它覆盖已经搬到新位置的真库 —— ADR-0019 明确不做索引合并，两害相权取其轻。
3. **回滚的清单只能取自目标目录。** 执行阶段搬过去的东西里，索引按执行时解析、收尾的多轮扫描还会补搬迟到的正文，它们都不在计划里。用计划回滚会留下"回滚成功，但新位置还留着我们搬过去的文件" —— 那正是界面上"请核对两处"要防的事，把它报成成功是这条路径上最坏的一种缺陷。

**被否决的替代方案**：

- **把关闭连接提到算计划之前**：只在"用户确认之前没人再打开索引"时成立，而确认框是异步的、可以停很久。它把分叉从"必然"缩小到"偶然"，仍然要靠运气。
- **给索引连接加一把"迁移期间禁止重开"的锁**：能彻底消除窗口，但 `archiveStore()` 的每个调用点（界面、接管写入）都会拿到一个新的失败态，而它们的失败路径各不相同。收益是一个很窄的窗口，代价是一条新的全局状态。
- **照计划搬，把 ENOENT 当作"跳过"**：等于把"迁移成功"的定义交给一个 errno —— 文件到底少没少，不该由错误码来回答。
- **失败原因改用 `error.message`**：message 里带完整路径（`ENOENT: no such file or directory, rename '/home/…'`），会同时进入界面与日志（G-3）。用 errno 既能落到用户能行动的那一层，也不泄露路径。

**影响**：

- `MigrationPlan.entries` 里的索引部分不再是一份可执行的清单，只是计划时的快照（用于确认框的文件数与回滚兜底）；执行阶段以源目录**当时**的内容为准。
- 写入失败的原因改为报 errno（`ENOSPC` / `EACCES` / `ENOENT` / `EXDEV`…），界面与日志共用 `failureReason()`（后来提到 `src/main/errors.ts`，见 [ADR-0026](#adr-0026) 的影响一节）；`relocate.ts` 的两处失败报告一并改用它。
- 回滚只搬归档自己的名字（内容哈希 / `.index.sqlite*` / `.part-*`）—— 目标目录在计划时被验证为空，但"理论上为空"不能拿来搬用户的东西。
- 一个残留情形被**有意保留**：迁移窗口里若旧目录被重开出一个空库，它既不覆盖新位置、也不被搬走，于是旧目录不会被删除（`rmdir` 非空即失败）。这比"用空库盖掉真库"安全；界面本来就会提示用户核对两处。

## ADR-0025

**决定**：本地界面从"一扇窗口 + 两个标签页（归档 / 设置）"拆成**两扇独立窗口**：**「文件列表」**（原「归档」）与**「设置」**。两扇窗口各自是一个独立的渲染入口（`files.html` / `settings.html`），可以分别单独打开；托盘右键菜单相应改为 `显示聊天` / `文件列表` / `设置` / `退出`。接管健康标签只挂在**设置**窗口。

**状态**：已生效

**背景**：今天只有一个 `createLocalWindow()`：它加载 `index.html`，顶栏两个标签按钮用 `hidden` 属性切显隐（`main.ts` 的 `mountTabs()`），托盘的「归档」指向它 —— 用户要看设置，得先进这扇窗口再点一次标签。把两个功能绑在一扇窗口上带来三件事：

1. **入口不够直。** 托盘只能给"看文件"一个入口；"改设置"没有自己的入口，而它恰恰是用户遇到问题时会去找的地方（"文件存到哪了""图标怎么换"）。
2. **两个功能的生命周期完全不同。** 看文件是高频、希望一键带出来；改设置是低频、改完就走。绑在一起意味着一扇窗口要同时承担两种"什么时候该刷新"的逻辑（`mountTabs` 里那一段"切回来时刷新"就是它的代价）。
3. **布局上它们没有共享的东西。** 文件列表窗口里只有搜索/刷新/列表/页脚；设置窗口里只有设置项。标签栏是唯一把它们连起来的部件。

**理由**：

1. **两个 HTML 入口，而不是"一个入口 + 参数"。** 每扇窗口加载的东西就是它自己要显示的东西。若共用一份 HTML、用 `hash` / 查询参数决定显示哪一半，渲染层就必须维护"我是谁"的分支 —— 而这个分支写错的表现是"窗口显示了错的内容"，离线测试抓不到，只有真实点击才能发现。代价是 `electron.vite.config.ts` 的 renderer 必须**显式声明两个入口**，否则漏掉的那个不会报错、只在运行期白屏；因此 `test/e2e/bundle-smoke.test.ts` 对**两个** HTML 都断言"存在、无内联脚本（CSP 只允许 `self`）"。
2. **一扇窗口一个名字。** 标题为 `WaaChat — 文件列表` / `WaaChat — 设置`：X11 的任务栏与窗口列表靠它区分两扇窗口。它不影响 `app_id` / `StartupWMClass` / `.desktop`（仍由 `app.setDesktopName()` 与 electron-builder 决定，见 [ADR-0020](#adr-0020)）。
3. **"归档"是概念，「文件列表」只是窗口名。** 索引、目录、迁移、`archive/` 模块、`archive:*` 通道、`Settings.archiveDir` 描述的都是**数据**，一律不改名。判断标准：面向用户的"这扇窗口叫什么"要改，描述数据本身的"归档"保留（详见 [ADR-0023](#adr-0023) 对目录名的取舍）。
4. **托盘入口逐个直达。** 「文件列表」与「设置」分别打开对应窗口并带到前台；`tray.on('click')`（StatusNotifierItem 的 Activate）仍指向**聊天**窗口 —— 它是保底入口，理由见 `integration/tray.ts` 的注释。
5. **健康标签只挂设置窗口。** 这条与 `views/health.ts` 原有的"状态必须一直可见、不该藏进设置页深处"有张力，是一次**有代价**的取舍：从托盘打开的第一扇窗口是文件列表，那条状态因此在默认路径上不再可见。选它的理由：文件列表窗口的职责就是"看文件"，状态标签在那里只是装饰；而设置窗口本来就承载"应用当前的行为是什么"（图标生效范围、迁移进度、缓存开关），状态标签与它们属于同一类信息。若将来证明可见性更重要，回到"两扇都挂"只需多挂一次 `mountHealthView()`，代价是把推送目标改回两扇窗口。

**被否决的替代方案**：

- **保留标签页，只给托盘加一个「设置」入口**：两项都打开同一扇窗口，用户仍然无法同时看列表与设置 —— "拆开"这件事没有发生。
- **共用一份 HTML，用参数决定显示哪一半**：见理由 1。省一份 HTML，换来一个只能在真实点击下暴露的分支。
- **把健康状态单列一扇窗口**：几个字的状态不值得一扇窗口。
- **懒创建窗口**（托盘第一次点击时才建）：省一点内存，代价是首帧变慢，且 `archive:migration` / `capture:health-changed` 都要多一个"窗口还没建"的分支 —— 这两处恰恰是最不该静默失败的地方。
- **健康标签两扇都挂**：可见性最好，但要在以"文件列表"为主题的窗口里展示应用级状态，收益与代价不成比例。这条留在理由 5 里作为可回退的方向。
- **保留 `getLocalWindow()` 这个名字，让它返回文件列表窗口**：名字会变成谎话（"本地"现在有两扇），而调用方（对话框父窗口、推送目标）恰恰需要区分是哪一扇。
- **把"归档"这个词全量改成"文件列表"**：会波及模块名、IPC 通道、设置项、目录名与文档里所有"归档迁移 / 归档目录"，而它们描述的是数据。
- **改用 `BrowserView` / 单窗口内嵌两个 `<webview>`**：为一个两页界面引入一套容器模型，且 `webview` 与 `preload`/沙箱的边界都要重新论证 —— 与 [INV-1](#adr-0002) 的结构性保证相比，收益为零。

**影响**：

- `src/renderer/`：`index.html` + `main.ts` 换成 `files.html` + `files.ts` 与 `settings.html` + `settings.ts`；两个入口共用的 `fatal()`（装配失败的兜底提示）提到独立模块；样式里删掉 `nav` / `section[hidden]` 两组规则。
- `electron.vite.config.ts`：renderer 单入口 → 双入口；`test/e2e/bundle-smoke.test.ts` 的产物断言同步覆盖两个 HTML。
- `src/main/window.ts`：`createLocalWindow()` / `getLocalWindow()` → `createFilesWindow()` / `createSettingsWindow()` + 两个 getter（沿用"点名而不是遍历猜测"的纪律）；两扇窗口共用一个内部构造器，`preload` / `contextIsolation` / `sandbox` / `nodeIntegration` / 会话分区 / `hideOnClose` 逐项不变；承载上游页面的窗口**仍然不挂 preload**。
- `src/main/integration/tray.ts`：`TrayWindows` 变为 `{ files, settings, main }`；菜单四项；托盘图标刷新路径不变（仍走 `getTray()?.setImage()`，见 [ADR-0022](#adr-0022)）。
- `src/main/ipc/index.ts`：对话框父窗口与推送目标按窗口归属 —— 迁移确认框 / 选择保存目录 / 选择图标图片 / `archive:migration` 进度 / `capture:health-changed` 全部归**设置**窗口；"没有窗口时退化为无父对话框"的分支保留。
- 文档：`docs/usage.md`（指向窗口的说法与托盘菜单）、`docs/README.md` 的目录树与 `main.ts` / `index.html` 描述、`CHANGELOG.md` 同步。
- `ai/CONVENTIONS.md` 第 9 节的 `scope` 列表补 `ui`：此前窗口 / 托盘 / 渲染层的改动没有贴切的 scope（`ipc` 与 `capture` 都不准），只能挑一个勉强的。

## ADR-0026

**决定**：

1. `enableCiphertextCache`（密文磁盘缓存）的**默认值改为关闭** —— 新装的用户不再默认在本地留一份密文副本。
2. **每次启动**在会话建立之前做一次**状态对账**（`capture/cache-files.ts` 的 `reconcileCiphertextCache()`）：
   - **关闭** → 清空 `cache/` 里的条目（纯派生数据，[ADR-0008](#adr-0008) 的原话是"可随时安全删除"）；
   - **开启** → **保留**可命中的条目（"关掉又开回来"不该让用户重新下载一遍），只清掉不可能命中的残留（正文与元信息缺一半）。
3. 开关仍然**必须重启才生效**（`RESTART_REQUIRED_SETTINGS`）。本次没有改这一点，补的是"重启之后先做什么"。

**状态**：已生效

**背景**：缓存当前默认**开启**，而且只增不减 —— 容量上限与淘汰还停在 `capture/protocol.ts` 的 `TODO(M3)`。这意味着一个刚装上应用的用户，第一次点开一个文件就在 `~/.local/share/waachat/cache/` 里留下一份密文副本；他对这件事既没有选择也没有被提示。

而"关掉它"在今天是不完整的：设置写下去了，下次启动协议层不再挂载，但**磁盘上那份缓存还在**。设置说"不要在本机留密文"，目录里躺着的却是几十上百 MB 密文 —— 这既是事实与设置不一致，也让 `docs/security.md` 里那句"密文缓存……可被长期留存分析"继续成立。应用也没有任何地方能删它（[ADR-0008](#adr-0008) 只说不提供清空**登录态**的入口；`cache/` 是随时可删的，但今天连一个删它的操作都没有）。

**理由**：

1. **默认值要选"更不需要解释"的那一边。** 默认开启要解释的是"你为什么在我的磁盘上放密文"；默认关闭要解释的是"为什么第二次打开还要联网" —— 后者一句话就说完，而且状态标签上就写着"密文缓存：关"。前者是隐私问题，后者是性能问题，可容忍度不同。在淘汰策略还没实现的当下，让一个无上限、只增不减的目录成为默认行为尤其不合适。
2. **"转换"只能是"保留或失效"，不存在第三种。** 缓存条目只有两种命运：能命中的（正文 + 元信息成对、版本相符）与不可能命中的。密文不能重新编码（那要解密，[INV-3](#adr-0002)），也不能降级成别的格式让页面继续读。因此"把已有文件转成新状态"在这里落地为：**关闭时清掉**（新状态就是"没有缓存"），**开启时保留可命中的、只清不可能命中的**。
3. **对账的判据是"目录 vs 当前设置"，不是"上次是什么"。** 于是它幂等、无状态、每次启动都能跑，不需要多一份持久化状态（见替代方案里的 marker 文件）。
4. **"关 → 开"必须不丢已有缓存。** 这才是真正的兼容性诉求：用户试着关掉、发现变慢、又开回来，不该为此把几百 MB 重新下载一遍。
5. **对账必须早于会话建立。** 那一刻没有任何请求在飞，因此不会把"正在写"的条目当残留删掉 —— `persist()` 先写正文、后写元信息，两者之间进程被杀留下的正是"缺一半"。

**被否决的替代方案**：

- **顺手把老用户设置里的 `true` 改写成 `false`**：默认值是"没有选择时用什么"，而 `true` 是用户自己选过的。替用户改一个他没动过的开关，与"改一个默认值"是两件性质不同的事。代价是老用户继续保持开启 —— 那是他的选择，与"默认关闭"并存是正常的。
- **用 marker 文件记住"上次生效值"，只在变化时对账**：多一份可能与现实不符的持久状态（崩溃、手工删除、目录被清），而它唯一的作用是省一次 `readdir`。关闭分支在空目录上的代价几乎为零。
- **启动时把版本不符的旧条目也清掉**（读一遍所有 `.meta.json`）：缓存上限 2 GiB、条目可能上万，那是一次全量同步 IO，会推迟第一扇窗口出现；而版本不符的条目会在同一个 URL 再次请求时被**原地覆盖**（键不变，写的是同一个文件名），本来就自愈。
- **只改默认值，不做对账**：正是今天的问题 —— 设置与磁盘不一致。
- **关闭时把目录本身也删掉**：空目录（`0700`）不是隐私问题，重新开启时 `attachCiphertextCache()` 本来就会 `mkdir`；保留它让"这个目录为什么在这儿"只有一个解释（应用的数据目录之一）。
- **把清理结果弹给用户、或塞进状态标签**：删的是纯派生数据，且是用户自己关掉开关的必然结果。为一次静默且正确的行为弹窗，是把噪音当透明。日志里留一条 `capture: ciphertext cache reconciled`（含条目数与字节数）足够排查。
- **把开关做成热切换**（`protocol.unhandle`）：会话生命周期里 scheme 的注册是一次性的，理由见 `shared/types.ts` 的 `RESTART_REQUIRED_SETTINGS`。本次不改。
- **顺手把容量上限与淘汰一起做了**（`TODO(M3)`）：那是独立的一件事（要定淘汰策略、要同步自己的文档）。默认关闭已经让"无上限"不再落在默认路径上，两件事不该压在一个改动里。

**影响**：

- `src/shared/types.ts`：默认值改为 `false`。新装用户第一次启动**不会创建 `cache/`** —— 那个目录只有 `attachCiphertextCache()` 会建。
- 新模块 `src/main/capture/cache-files.ts`：条目形态（`<sha256>.bin` + `<sha256>.meta.json`、`CACHE_VERSION`）、残留判定（纯函数 `orphanEntries()`）、对账（`reconcileCiphertextCache()`）。它**不导入 electron**，因此可单测、也能被离线自检引用；`capture/protocol.ts` 改为从这里取常量，它自己只剩"拦截请求"。
- `src/main/session.ts`：接管点 B 的分支之前加一次对账（早于任何窗口与请求）。
- `src/main/errors.ts`：`failureReason()` 从 `archive/migrate.ts` 提出来（现在三处共用：迁移对账、设置落盘失败、缓存对账），[ADR-0024](#adr-0024) 影响一节里对它的定位随之更正。
- `capture/headers.ts` 的白名单一变，仍然**必须**提升 `CACHE_VERSION`（`ai/TASKS.md` 的要求不变，只是常量换了文件）。
- `scripts/check-capture.ts`：新增两条断言锁住"默认关闭"与"在重启生效名单里"—— 这两条约定都属于"改动了没人会立刻发现"的那一类。
- 界面：开关那行的提示补上"关闭会清掉已有缓存、开启则保留"；`密文缓存：关` 成为默认配置下的常见形态（视觉上没有变化，它本来就是中性色）。
- 文档：`usage.md`（默认值、对账行为、目录图）、`security.md`（`cache/` 的默认归属）、`CHANGELOG.md`。

## ADR-0027

**决定**：`enableCiphertextCache` 的切换不再是一个"改完等重启"的复选框，而是一次**事务式维护流程**：

1. 用户在设置窗口拨动开关 → 主进程先算规模（多少项、多少字节），再弹**确认框**写明后果；取消则一切不变。
2. 确认后，设置窗口**整个切成维护界面**（设置列表不再渲染）：显示目标状态、当前阶段、进度与字节数，并写明"转换期间不能进行其他操作"。
3. **文件状态转换**（沿用 [ADR-0026](#adr-0026) 的两种命运，但加了可回滚性）：
   - **关闭**：把缓存条目**重命名进 `cache/.staging/`**（同目录、同文件系统 → 原子、不复制、不占空间），全部搬完才算转换成功；提交后再删暂存区。
   - **开启**：清掉不可能命中的残留（正文与元信息缺一半）。
4. **全部转换成功才提交设置**（写 `settings.json`）。提交那一刻立即生效：协议层跟着注册或注销（见理由 1）。
5. 失败即回退：任何一步出错，已搬走的条目从暂存区搬回原位、设置一个字节都不写；提交之后才失败的**清理**不回退（状态已经切过去了，剩下的文件在下次启动时清掉，见"影响"）。
6. 切换期间**不允许其他操作**：确认框是模态的，设置列表在维护期间根本不渲染，主进程另有一道"切换进行中"的闸门兜底（任何设置写入都会被拒）。

**状态**：已生效（细化 [ADR-0026](#adr-0026)：启动对账保留，但角色收窄为"崩溃恢复的兜底"；**取代**该设置此前"必须重启才生效"的规定）

**背景**：ADR-0026 把"转换"放在**下次启动**，于是这个开关的语义是"改了 → 重启 → 生效"。那条路有两个问题：

1. **中间态会自我推翻。** 设置提交为"关闭"之后、重启之前，协议层还挂着（注册是会话级一次性的，见 `shared/types.ts` 的 `RESTART_REQUIRED_SETTINGS`），于是它会把刚清干净的缓存**重新写回来** —— 用户明明关掉了、也看到了转换完成，磁盘上却又长出文件。这正是"状态不一致"。
2. **用户看不到转换，也无法参与。** 清掉几百 MB 是在启动过程里静默发生的：没有确认、没有进度，用户对此唯一的线索是磁盘空间变了。

**理由**：

1. **要"提交才生效"，就只能在提交时把运行时状态一起换掉。** 因此这次顺带把协议层从"启动时决定、之后再不改"改成"随设置注册/注销"：实测（Electron 44）`ses.protocol.handle('https', …)` → `unhandle('https')` → 再 `handle` 同一个 scheme 全部可行，且**未挂处理器时请求真的回到网络栈**（探针里 `fetch#2` 得到 `ERR_NAME_NOT_RESOLVED`，说明中间没有我们的直通路径）。这条证据很重要：它让"关闭"意味着**完全不拦截任何流量**，保住了"不接管时与原生内核无差别"的姿态 —— 若改成"启动时无条件注册、每次请求按设置判定"，那么默认配置（关闭）下每一字节流量都会经过我们的直通路径，等于把整个应用的网络正确性栓在一段与功能无关的代码上。
2. **回滚要求"转换"必须是可逆的搬运，而不是删除。** 需求写明"任一文件转换失败或流程被中断 → 回退到切换前的原始状态"。对删除来说这是**做不到的**：删掉的文件回不来。因此关闭方向的转换改成"搬进同目录的暂存区"，提交之后再真正删除。代价是多一趟重命名，换来的是一句真话："失败时你的缓存还在"。
3. **"中断"的回退只能发生在下次启动 —— 必须说清楚。** 进程被 kill 时没有任何代码在跑，当场回退是不可能的。因此判据交给**已提交的设置**：启动时若发现暂存区，且设置说"开启"（说明那次切换没走完）→ 搬回去；若设置说"关闭"（说明提交已经发生、只剩收尾）→ 删掉。这也是 ADR-0026 那次启动对账的自然延伸，两件事合并成一次"恢复 + 对账"。
4. **确认框用原生模态框，而不是自绘。** 它天然挡住被承载窗口的一切点击（`showBox` 已经是归档迁移的做法），而"切换期间不能操作"这条要求靠一个自绘遮罩还要额外论证。代价是文案受原生对话框排版限制（写成几行短句）。
5. **维护界面放在设置窗口里换一屏，而不是新开窗口。** 它从属于"设置"这件事（[ADR-0025](#adr-0025) 把窗口职责分开了：文件列表管看文件、设置管"应用当前的行为"）。换一屏还有一个额外好处：维护期间设置列表**根本不存在**，"不能进行其他操作"是结构上的事实，不是靠禁用属性维持的。

**被否决的替代方案**：

- **直接删除，失败就说"已删除的部分无法恢复"**：不满足需求里"回退到切换前的原始状态"。缓存是派生数据、删了确实只影响速度，但"回退"这条要求本身是关于"按下开关之后发生的事有没有确定性"，不该因为数据不值钱就放弃。
- **复制到暂存区再删原文件**：同文件系统内 `rename` 已经足够，复制要读写一遍全部字节（可能几百 MB），换不来任何安全性。
- **把暂存区放到 `XDG_CACHE_HOME` 或 `/tmp` 下**：跨文件系统会让 `rename` 失败并退化成复制；放在缓存目录内部则永远同文件系统，也不会被用户的"清缓存"工具只扫走一半。
- **保留"重启后生效"，只把转换搬到维护界面**：提交之后、重启之前协议层仍会把缓存写回来（背景第 1 点），维护界面刚宣布"已清掉"就又被推翻。
- **"关闭立即生效、开启仍需重启"的混合语义**：技术上都成立，但用户无法从界面上分辨自己在哪一种情况里，且要写出一句既不骗人又不啰嗦的提示几乎不可能。宁可在两个方向上都做成即时生效。
- **启动时无条件注册协议层、按设置实时判定**：见理由 1 后半段 —— 代价是把默认关闭时的全部网络流量都纳入我们的直通路径。
- **切换期间允许改其他设置**：需求明确禁止。维护界面换一屏已经挡住了界面侧，主进程再加一道闸门是为了挡住"界面还没画出来就被点到了"这类窗口（以及将来可能出现的新调用方）。
- **不做"清理"阶段（提交后把暂存区留到下次启动）**：会让"转换完成"之后磁盘空间仍然没有释放（而这恰好是用户最容易检查的一点）。做，但**不允许它回退**，因为它不影响已经提交的状态。

**影响**：

- `src/shared/types.ts`：新增 `CacheConversionPhase` / `CacheConversionProgress` / `CacheSwitchFailure` / `CacheSwitchResult`；`RESTART_REQUIRED_SETTINGS` **变成空列表**（机制保留 —— 界面的徽标与 `ai/CONVENTIONS.md` 的解释都指向它，将来可能有别的项进来）。
- `src/main/capture/cache-files.ts`：新增 `STAGING_DIR_NAME`、`planCacheConversion()`、`convertCache()`（带 `afterEntry` 钩子，与 `archive/migrate.ts` 同款，便于注入失败）、`purgeStaging()`、`recoverStaging()`；`reconcileCiphertextCache()` 先做暂存区恢复再对账。
- 新模块 `src/main/capture/cache-switch.ts`：编排"转换 → 提交 → 收尾"，与 `archive/relocate.ts` 同一个模式（数据在文件系统、状态在 `settings.json`，两者没有共同提交点，只能规定一个方向：先转换、再落设置、失败搬回）。
- `src/main/capture/protocol.ts`：新增 `detachCiphertextCache()`（`unhandle` + 把"当前是否生效"的状态标签置回关闭）。
- IPC：新增 `settings:switch-ciphertext-cache`（一次切换）与 `settings:cache-conversion`（进度推送）；`settings:set` **拒绝**这个键（与 `archiveDir` 同一条理由：它必须伴随真实的数据转换，单独改它只会得到一个半截状态）。
- 自检（`scripts/check-capture.ts`）：原来那句"在重启生效名单里"改成断言它**不在**名单里，并断言暂存区名不会被当成缓存条目。
- 文档：`usage.md` 第 5 节这一行、`media-capture.md` 第 2 节、`docs/README.md` 的目录树、`CHANGELOG.md`。
- 一个**有意保留**的边界：提交之后若清理失败，暂存区会留到下次启动（日志记条数，成功提示里也会提一句）。它不影响状态正确性，只影响磁盘空间 —— 让"已经切过去的设置"因为一次删不掉而回退，是更坏的选择。
- 另一个**已知且不在本次范围内**的边界：`settings.json` 的写入不是原子的（与本次改动无关，归档迁移同样依赖它）。写一半的配置文件会被 `coerce` 逐字段回落到默认值，因此极端情况下"提交是否已发生"会有歧义；要根治得另开一次改动（临时文件 + `rename`）。

## ADR-0028

**决定**：

1. `enableCiphertextCache`（密文磁盘缓存）的**默认值改回开启** —— 新装用户默认启用接管点 B。
2. 它的切换**不再有确认框，也不再有维护界面**：拨动开关即开始一次**静默转换**。转换 → 提交 → 收尾的次序与回退语义**不变**（[ADR-0027](#adr-0027)），界面只在转换期间禁用开关自己、并在结束后显示一行结果（成功 / 失败 + 是否已回退）。

**状态**：已生效（**取代** [ADR-0026](#adr-0026) 的默认值决定，与 [ADR-0027](#adr-0027) 的"确认 + 维护界面"那一半；两者的其余部分保留）

**背景**：ADR-0026 / ADR-0027 的出发点是把"本机磁盘上有一份密文"当成一件需要用户点头的事：默认关闭；开启时先弹确认框写明要处理多少文件、再用一整屏维护界面显示转换过程。

这个出发点与项目自己写下的资产分类不一致。`security.md` 第 2 节把密文缓存与归档明文并列时，给它的是"危害较低（仍是密文），但可被长期留存分析" —— 缓存里的字节是**上游已经加密好的那一份**，本应用不解析 `mediaKey`、不做任何解密（[INV-3](#adr-0007)），它单独泄露不构成通信内容泄露，与归档目录里那份**解密后的明文**不是一个量级。为它配一套"要确认、要看着进度、期间连别的设置都不能改"的仪式，是把两件事当成了一件事。

**理由**：

1. **默认值要选"更省事又说得清"的那一边。** 默认开启省下的是一次网络往返（同一个文件第二次打开不再联网），需要解释的只有"本地那份是什么" —— 答案是"上游的密文，本应用不解密、也不存密钥"，而这句话就写在开关旁边（`settings.ts` 的 `TOGGLES` hint）。ADR-0026 认为"为什么第二次打开还要联网"不需要解释，但它同样需要解释，而且解释完用户还得自己去把开关打开 —— 净成本更高。
2. **确认框在这里没有可拦的东西。** ADR-0027 给它的两条理由是"这是一次真实的文件处理"与"期间不能被别的操作打扰"。但两个方向都不删用户数据：关闭只是**搬运**进 `cache/.staging/`（失败可回滚），开启只清**永远命不中的残留**。确认框拦下的不是危险动作，而是一次必然发生、且失败可回退的动作 —— 代价是每一次拨动都要多点一次。
3. **维护界面的代价大于收益。** 换一整屏是为了让"这期间不能进行其他操作"成为结构上的事实（ADR-0027 理由 5）。但转换通常只是同目录内的 `rename` 与删除，规模是"几十上百 MB / 上千个文件"，用户来不及看到进度就已经结束了；而代价是**每次拨动都要丢掉一次设置列表的上下文**。改成一行的进行态 + 结束后的结果行之后，"进行中"仍然可见（开关自己被禁用），但不值一整屏。
4. **事务与回退一条都不放弃。** 去掉的是"仪式"，不是"确定性"：提交前失败仍把搬走的条目搬回原位、设置一个字节都不写；提交后只剩余清理且不回退；中断由下次启动按**已提交的设置**收尾（ADR-0027 理由 2 / 3 原样成立）。失败仍然要**说出来**（结果行）—— "允许失效，不允许静默失效"。
5. **老用户的值不替他们改写。** `settings.json` 里已经存下的 `false` 一律保留。这与 ADR-0026 拒绝把老用户的 `true` 改写掉是同一条理由：默认值是"没有选择时用什么"，而写进文件的值按"用户的值"对待。**代价要如实记下**：因为 `saveSettings()` 会写出完整对象，任何动过一次设置的老用户文件里都有一个 `false`，所以本次默认值的改变**只对从未落过盘的新装用户生效**。

**被否决的替代方案**：

- **只改默认值，确认框与维护界面照旧**：默认开启意味着这个开关会被人拨动（想省磁盘的用户第一件事就是关掉它），于是**每一次**关闭都要先弹一个框。把最常发生的一次交互配上最重的仪式，正是这次要修的问题本身。
- **去掉确认框，保留维护界面**：进度界面存在的前提是"用户需要看到过程"。转换的规模（理由 3）不支持这个前提，保留它只会让每次拨动都闪一屏。
- **把它并进 `settings:set`，连 `switch-ciphertext-cache` 通道一起删掉**：通道存在是有理由的 —— 它必须在**落设置的同一次调用里**把协议层挂上或摘掉（ADR-0027 理由 1），而 `settings:set` 是一条只写 `settings.json` 的通用路径。合并的结果是把一条"会碰运行时状态"的操作藏进一条"看起来只写配置"的路径里。保留专用通道，只删掉它的界面仪式。
- **默认开启，但不在界面上说明存的是什么**：那就退化成 ADR-0026 担心的那种"用户不知情"。开关旁边的 hint 与 `security.md` 的资产表是这次改动的**前提**，不是可选装饰。
- **顺手把容量上限与淘汰一起做了**（仍是 `TODO(M3)`）：默认开启让"只增不减"重新落回默认路径，这确实提高了那件事的优先级 —— 但它是独立的一次改动（要定淘汰策略、要同步自己的文档），不该压在这里。

**影响**：

- `src/shared/types.ts`：`DEFAULT_SETTINGS.enableCiphertextCache` 改为 `true`；删除 `CacheConversionPhase` / `CacheConversionProgress`（没有进度界面，也就没有进度推送）。
- IPC：`settings:switch-ciphertext-cache` 保留（事务编排与"切换进行中"的闸门不变），但去掉确认框与进度推送；删除 `settings:cache-conversion` 通道、preload 的 `onCacheConversion()` 与 `bridge` 里的对应声明。`settings:set` 仍然**拒绝**这个键（理由不变：它必须伴随一次真实的文件转换）。
- `src/main/capture/cache-switch.ts`：`switchCiphertextCache()` 去掉 `onProgress` 参数。`cache-files.ts` 的 `planCacheConversion()` / 暂存区与回退逻辑**一律不变**；`convertCache()` 只是不再对外报进度（那一屏没有了，进度就没有去处）—— 它与 `planCacheConversion()` 的分工、`afterEntry` 钩子、失败时的搬回行为都不变。
- `src/shared/cache-conversion.ts`：只剩 `describeCacheSwitchFailure()`；`describeCacheSwitchScope()` 与 `describeCacheConversionProgress()` 随确认框与维护界面一起删。
- `src/renderer/views/settings.ts`：删除维护界面（`maintenanceScreen()`）与整屏切换；开关行在转换期间禁用自己并显示一行进行态，结束后显示结果行。
- `scripts/check-capture.ts`：'默认不开启' 的断言改为 '默认开启'；暂存区那两条断言不变（暂存区仍然存在）。
- 文档：`usage.md`（设置表与该开关的一节）、`architecture.md` 第 3.2 节、`security.md` 的资产表、`media-capture.md` 第 2 节、`ai/TASKS.md`。

## ADR-0029

**决定**：

1. **上游的文档预览页**（`*.whatsapp.net/pdf-viewer/…`）在本应用里**一律不加载**：窗口那一层由 `main/window.ts` 的窗口处理拒绝，子框架那一层由 `capture/pdf.ts` 的 `webRequest.onBeforeRequest` 取消。
2. **任何 `application/pdf` 的响应都不再交给内核的内置阅读器**：我们把它的 `content-type` 降级为 `application/octet-stream`，让它变成一次下载 —— 于是接管点 A（下载事件 → 归档 → `shell.openPath`）接手，文件交给系统默认 PDF 阅读器打开。
3. 这一层**不随任何设置开关**，也不新增设置项：它不在"可选增强"的位置上，而是"文件交给系统应用打开"这条契约在 PDF 上的落实。

**状态**：已生效（有效范围受端到端加密限制，见最后一节"已知限制"）

**背景**：需求是"点开聊天里的 PDF 用系统默认阅读器打开，应用内不要预览"。直觉做法是关掉内核的 PDF 内置阅读器，但 **Electron 44 没有这个开关**。一次性探针（Linux + `xvfb-run`，Electron 44.7）实测：

| 试的东西 | 结果 |
|---|---|
| `webPreferences.plugins: false` / `true` / 不设 | 三者完全一样：PDF 仍被内置阅读器渲染（导航完成、标题变成 PDF 名、**没有**下载事件） |
| `--disable-plugins` / `--disable-extensions` / `--disable-pdf-extension` / `--disable-features=PdfOopif` | 同上，全部无效 |
| `navigator.pdfViewerEnabled` | 恒为 `true`；`navigator.plugins` 里始终有 `PDF Viewer`（连 `--disable-plugins` 也改不动） |
| `webRequest.onHeadersReceived` 把 `application/pdf` 改成 `application/octet-stream` | ✅ 立刻变成下载（`will-download` 拿到 `a.pdf`）；**子框架里的 `<iframe>` / `<embed>` 同样有效** |
| 在 `protocol.handle('https')` 内部返回 `application/octet-stream` | ✅ 同样变成下载 |
| 协议处理器返回 `application/pdf` 时，`webRequest.onHeadersReceived` 改它 | ❌ 改不动，PDF 照旧被渲染 |
| `webRequest.onBeforeRequest` 取消一个会被协议处理器接住的请求 | ✅ 生效（`ERR_BLOCKED_BY_CLIENT`，协议处理器根本不会被调用） |
| `will-navigate` + `preventDefault()` + `contents.downloadURL(blob:…)` | ❌ **进程直接崩**（core dump） |
| `<iframe src=blob:…>` / `<embed src=blob:…>` 的 `will-frame-navigate` | ❌ 不触发 |

于是"取消预览"只能等价于**不让 PDF 到达阅读器**：把它变成下载。

**理由**：

1. **阅读器关不掉，那就断掉它的输入。** 上表最右一列就是结论：改写 MIME 这一条确定有效，且字节与文件名都正确 —— 说明它走的就是接管点 A 的既有路径，不需要第二套下载逻辑。
2. **挡预览页不是"顺手加的"，它和第 2 条是同一件事的两半。** 预览页（`webtp.whatsapp.net/pdf-viewer/`）的唯一作用就是把 PDF 交给内置阅读器渲染（`shared/upstream.ts` 一直是按"上游自有页"放行它的）。留着它，第 2 条就只对"直接指向 PDF 的 URL"有效，而点击文档仍然会渲染出预览面板 —— 两个目标互相打架。
3. **挡请求只能用 `onBeforeRequest`，改写 MIME 只能放在协议处理器内部。** 这两条都是实测逼出来的：密文缓存那一层挂着时（[ADR-0027]）会话里的**所有** https 都由 `protocol.handle('https')` 接住，此时 `onHeadersReceived` 对那份响应无效，而 `onBeforeRequest` 的取消仍然有效。因此分工是"挡 = `onBeforeRequest`（与缓存开关无关，永远挂着）；改写 = 协议处理器内部 + `onHeadersReceived` 兜住缓存摘掉的情形"。
4. **改写只做一次"渲染 → 下载"的降级，不是动页面数据。** 请求一个字节没动、响应体一个字节没动、页面的 JS 与 DOM 一行没碰（[INV-1] 的边界是注入）。这一条必须有意识地记下来，因为 `media-capture.md` 第 6 节把"修改请求内容或注入响应"列为不做的事 —— 本次是那条边界的**一次明确例外**，同一份文档里已经注明适用范围（只改 PDF 响应的 MIME 一个头，且方向只有"降级成下载"）。

**被否决的替代方案**：

- **`plugins: false` / 各种 `--disable-*` 开关**：实测全是安慰剂（见背景表）。写下"已关掉内置预览"而实际没关，比不写更坏 —— 它会让人以后不再怀疑这里。
- **拦 `blob:` 导航改成 `contents.downloadURL(blob)`**：实测会让进程崩溃；而且子框架里的 blob（`<iframe>` / `<embed>`）根本不触发 `will-frame-navigate`，本来就拦不到。这条**也是"已知限制"的来源**：页面自己解密出来的 blob PDF 我们够不着。
- **只挡预览页、不改写 MIME**：那样"直接指向 PDF 的 URL"（聊天里分享的链接、其它上游页面里的 PDF）仍会被阅读器渲染，与决定 2 的目标不一致；而且改写的成本只有一行。
- **把预览页交给系统浏览器打开**：那个地址需要登录态，在别的浏览器里只会得到一个打不开的页面（`shared/upstream.ts` 早就记过这条）。
- **给这一层加一个设置开关**：它不是"可选增强"（对比 [ADR-0026](#adr-0026) 的密文缓存），而是"文件交给系统应用"这条契约的一部分。做成开关等于承认默认配置不满足契约。

**影响**：

- `src/shared/upstream.ts`：新增纯函数 `isDocumentPreviewPage()`（host + `/pdf-viewer/` 路径前缀）；`isUpstreamPage()` 语义不变（预览页仍算"上游自己的页面"，只是我们不再加载它），三个判据共用同一个 host 检查。
- 新模块 `src/main/capture/pdf.ts`：`isPdfResponse()` / `forceDownloadIfPdf()` / `attachPdfHandling(ses)`（`onBeforeRequest` 挡预览页 + `onHeadersReceived` 兜住缓存摘掉时的改写）。它只 `import type` electron，因此可被单测与离线自检引用。
- `src/main/capture/protocol.ts`：唯一的回源出口 `passthrough()` 与缓存命中那条出口都过一遍 `forceDownloadIfPdf()` —— 协议处理器返回的响应是最终响应，只有这里能改（理由 3）。
- `src/main/session.ts`：`attachPdfHandling(ses)`，与两个接管点并列。
- `src/main/window.ts`：窗口处理拒绝文档预览页，记日志，且**不**交给系统浏览器。
- `scripts/check-capture.ts`：新增一节断言锁住两条纯规则（预览页判据、PDF MIME 判据）—— 判据放宽一点点就会静默地让应用内重新出现 PDF 预览，属于"改了没人会立刻发现"的那一类。
- 文档：`media-capture.md`（第 2 / 5 / 6 节）、`usage.md`（常见问题）、`architecture.md`、`roadmap.md`（M1 那条验收项的说明）、`README.md`、`ai/TASKS.md`。

**已知限制（必须与决定一起读）**：

WhatsApp 的媒体是端到端加密的，**PDF 的明文字节只存在于页面内存里**（页面解密后做成 `blob:`），因此：

- 决定 2 的那条改写**不会**为它触发 —— 网络上根本没有 `application/pdf` 的响应（媒体 CDN 上那份是密文，`content-type` 是 `application/octet-stream`，见 [ADR-0015](#adr-0015)）；
- `blob:` 那条路实测拦不住（见替代方案）。

所以本次改动的**可观察结果**是：点击 PDF 不再出现应用内预览；文件要经**上游自己的下载入口**拿到（预览面板或消息上的下载按钮），那一步会走接管点 A，落到系统默认 PDF 阅读器。**"点 PDF 直接弹出系统阅读器"在不注入页面（[INV-1](#adr-0002)）的前提下做不到** —— 这句话写进 `roadmap.md`，而不是留一条永远打不开的验收项。

如果实测发现"点 PDF **什么都没发生**"，说明上游**只**通过预览页给出 PDF（没有独立的下载入口）。这时正确的动作是**回退这一条决定**（`git revert` 本次改动）—— 那意味着这条路线会净损失一个可用功能，而不是把文件换了个应用打开。第二次遇到这种情况时，要么接受"PDF 只能在应用内预览"，要么回到 [ADR-0002](#adr-0002) 重新讨论注入这条边界，不要在这里打补丁。

> ⚠️ **后来修正过**：上面这段"要么全有、要么全无"的处境已经被 [ADR-0030](#adr-0030) 解掉 —— 本 ADR 的两条规则改成由设置 `disablePdfPreview` 控制，**默认关闭**（即默认保持本 ADR 之前的行为）。下面这些决定与实测证据原样保留；只有决定 3（"不随任何设置开关"）被取代。

## ADR-0030

**决定**：新增设置 `disablePdfPreview`（设置页上叫"禁用 PDF 预览"），**默认 `false`**：

- **关闭（默认）** = [ADR-0029](#adr-0029) 的两条规则都不生效：上游的文档预览页照常加载，PDF 在应用内由内核阅读器预览（也就是本 ADR 之前的行为）。
- **开启** = [ADR-0029](#adr-0029) 的两条规则生效：挡掉上游的文档预览页（窗口与子框架两处），并把 `application/pdf` 的响应降级成下载 —— 文件经接管点 A 交给系统默认 PDF 阅读器。

它是**每个请求现读**的普通设置：走 `settings:set`，不需要重启，也**不**进 `RESTART_REQUIRED_SETTINGS`。

**状态**：已生效（**取代** [ADR-0029](#adr-0029) 的决定 3："不随任何设置开关，也不新增设置项"）

**背景**：ADR-0029 把"PDF 一律交给系统应用"做成了**无条件**的规则，并把"给这一层加一个设置开关"列为被否决的替代方案 —— 理由是它不属于"可选增强"，而是"文件交给系统应用打开"这条契约的一部分。

那个理由在**默认关闭**这个约束下不成立。ADR-0029 自己记下了一条限制：媒体是端到端加密的，PDF 的明文只存在于页面内存里（`blob:`），我们既拦不到那个 `blob:`、也关不掉内核阅读器，因此开启之后"触发下载"的那一步必须由**上游自己的下载入口**完成。如果上游**只**通过预览页给出 PDF，开启它就等于**净损失**一个可用功能（点了没反应）—— 而这一点在离线环境里无法预先验证（本机至今没真正接管过文件，见 ADR-0029 的探针记录）。

一个可能净损失功能的改动，不能是所有人的默认行为；它必须是**用户明确选择**的东西。

**理由**：

1. **默认值要选"不会让任何人变差"的那一边。** 默认关闭 = 与 ADR-0029 之前完全一致（应用内预览照旧），没有人会意外地发现 PDF 打不开了；想要系统阅读器的人自己打开，并且是**他**接受了 ADR-0029 记下的那条限制。
2. **契约没有因此松动。** "文件交给系统应用打开"仍然成立 —— 这个开关决定的是 PDF 走不走这条契约（内核 PDF 阅读器是唯一一类"应用自己显示文件"的例外）。契约要求的是"能交给系统应用打开"，而不是"默认替所有用户这么决定"。
3. **代价只是一个复选框，而且它自己解释自己。** 关闭时在做什么、开启后会发生什么、限制在哪里，都写在开关旁边（`renderer/views/settings.ts` 的 `TOGGLES`），比写进文档里指望用户读到更可靠。
4. **两条路线并存，而不是互相推翻。** ADR-0029 的两条规则与"什么都不做"共用同一条代码路径，由一个实时判据分流：没有第二套实现，也不需要为了切回去而 revert 代码。

**被否决的替代方案**：

- **默认开启**：会让没做过选择的用户撞上 ADR-0029 的已知限制（"点 PDF 没反应"），而症状看起来像应用坏了。
- **做成"重启后生效"**：没必要 —— 判据是每个请求现读的，改完立刻生效（与接管层读 `openOnCapture` 同一条纪律）。塞进 `RESTART_REQUIRED_SETTINGS` 只会让界面多一个不成立的"重启后生效"徽标。
- **让用户对"每个 PDF"单独决定**：那需要先判定"这份 PDF 拿不拿得到"，而我们恰恰判定不出来（否则 ADR-0029 就不需要那条限制）。**伪选择比没有选择更坏。**
- **按 MIME / 文件名猜"这个 PDF 拿不拿得到"，猜不到就不拦**：失败模式是静默且随机的（一会儿系统阅读器、一会儿应用内预览），用户既无法理解也无法预测。
- **不回退 ADR-0029，直接把它删掉、回到"只在应用内预览"**：那样"PDF 交给系统阅读器"这条路就永久消失了，而它是有人要的 —— 只是不该是默认。

**影响**：

- `src/shared/types.ts`：新增 `disablePdfPreview: boolean`，默认 `false`；`settings.ts` 的 `coerce()` 逐字段校验会自动覆盖新键（新增设置项不需要改它）。
- `src/main/capture/pdf.ts`：`attachPdfHandling(ses, getSettings)` 把**实时读取函数**注进来（注入读取函数而不是快照，见理由 2 与 `ai/CONVENTIONS.md` 的"设置改了不起作用"那条）；`forceDownloadIfPdf()` 只在开关开着时降级。`capture/protocol.ts` 的调用点不变 —— 判据在函数内部。
- `src/main/session.ts`：把 `getSettings` 传给 `attachPdfHandling()`。
- `src/renderer/views/settings.ts`：`TOGGLES` 增加一行；说明里要同时写清"默认关闭时是什么样"与"开启后受什么限制"。
- `scripts/check-capture.ts`：断言它默认关闭、且不在"重启后生效"名单里 —— 两者都属于"改了没人会立刻发现"的那一类。
- 文档：`usage.md`（设置表 + 常见问题）、`media-capture.md` 第 2 节、`architecture.md` 第 2 / 3.1 节、`README.md`、`roadmap.md`、`ai/TASKS.md`、`docs/README.md` 的源码树。

## ADR-0031

**决定**：

1. **归档正文的文件名 = 净化后的原始文件名**（保留扩展名），例如 `2026年第三季度合同.pdf`。内容哈希**不再是文件名**，它退回到它真正的用途：索引里的**内容身份**。
2. **同名不同内容**（两个对端各发一份 `合同.pdf`）按候选名顺序落盘：
   `原名` → `主干 (8位哈希前缀).扩展名` → `16 位` → `全哈希`。取第一个"不存在、或存在但内容相同"的候选。正常情况就是原名，只有真冲突时才多一小段哈希。
3. **同一份内容只存一份**：哈希相同、名字不同时，新名字建成指向同一份数据的**硬链接**（多一个名字、不多占字节）；哈希相同、名字也相同时丢弃临时文件（去重命中）。
4. 正文落盘后立刻置为**只读**（`0400`）。打开**旧布局**的文件时顺手补上这个权限（懒收紧），而不是启动时对全库做一次 `chmod`。
5. 索引新增 `stored_name`（磁盘上的实际文件名）。旧记录为 `NULL`，读取时回落到 `hash` —— 旧归档照常可用。
6. **删除 `.open/` 影子目录**（硬链接机制）以及配套的 `clearOpenDir()` / `ensureOpenLink()`。

**状态**：已生效（**取代** [ADR-0003](#adr-0003) 中"文件名 = 内容哈希"这一半；内容寻址作为**内容身份**保留）

**背景**：需求是"归档的文件用原文格式存，好直接在文件夹里查看；并设为只读，避免误改"。

现状正好相反：正文叫 `media/9f86d081…`（**没有扩展名**），为了能交给系统应用打开，`integration/open.ts` 还要在 `media/.open/<sha256>/报告.pdf` 造一个硬链接 —— 那份代码的注释自己写着这是"内容寻址带来的一个真实副作用，不是理论问题"。于是用户在文件夹里看到的是一堆哈希名：既认不出文件，也谈不上"直接查看"。

而 [ADR-0003](#adr-0003) 用哈希命名的理由只有一条，但确实很硬：**去重不需要任何判断逻辑**（同一份内容必然同名）。
用户可读的名字与这条性质在今天被强行绑在了一起 —— 本次把它们**拆开**。

**理由**：

1. **哈希值钱的地方是"身份"，不是"显示名"。** 同一份内容只有一个身份（搜索、淘汰、去重都围绕它），这一点不动；但把它同时当作磁盘上的显示名是把两件事混成一件事。拆开之后：身份 = `hash`（索引里），名字 = 原名（磁盘上），两者由 `stored_name` 这一列连起来。
2. **冲突必须有确定的处理方式，不能"覆盖"也不能"报错"。** 同名不同内容在聊天场景里是常态。加一小段哈希后缀既保住可读性又保证唯一，而且是**确定性**的：同一个哈希总能算出同一个名字，因此重复提交同一份内容仍然命中现有的那个名字（不需要扫描目录找空位）。
3. **同一份内容换个名字发来，应当只多一个名字、不多占空间。** 硬链接（一个 inode 两个名字）同时满足"看得到新名字"与"只存一份"。代价是 `usage()` 必须按 **inode** 去重统计 —— `.open/` 时代就已经是这条纪律（当时的注释写着"硬链接与正文共享存储，把它算进来会让统计翻倍"）。
4. **只读是"避免误改"唯一可靠的落点。** 归档是内容寻址的：一份内容对应多条索引记录，文件被就地改一个字，索引里的哈希就与内容不符 —— 后果是"搜索命中，但打开后不是当初那份"。只读把这条不变量变成文件系统的保证，而不是靠用户自觉。**删除与迁移不受影响**（两者只依赖目录的写权限，本 ADR 的"影响"一节逐条记下）。
5. **`.open/` 该消失，而不是继续并存。** 它存在的唯一理由就是正文没有扩展名。正文带上原名之后，"交给系统应用打开"就是归档目录里的那个文件本身。继续留着它等于长期维护一套影子目录（还要每次启动清空），而它唯一的副作用是让人以为归档里有两份东西。
6. **旧归档不搬迁，但必须继续能用。** 见下面的"已知限制"。

**被否决的替代方案**：

- **维持现状（哈希名 + `.open/`）**：目录不可读正是本次要修的问题。
- **直接用原名落盘、同名就覆盖**：在归档里覆盖一份用户可能只有一份的文件，是这类功能里最不可接受的一种失败。
- **浏览器式命名（`原名 (1).pdf`）**：要扫描目录找空位，名字会随目录内容变化（删掉 `(1)` 之后下一个同名文件又变成 `(1)`），同一个哈希在不同时刻可能得到不同的名字 —— 而索引里存着这个名字，失配就是"搜到但打不开"。哈希后缀是确定性的。
- **永远带哈希（`原名.a1b2c3d4.pdf`）**：唯一且确定，但每个文件都拖一段哈希，而用户要的正是"干净的名字"。
- **同一内容换名字时直接再写一份**：磁盘上会出现两份相同字节，而 README 承诺"内容哈希命中，仍只存一份"。
- **把索引里已有的 `name` 当成磁盘名**：`name` 是"打开时的原始文件名"，同一个名字可能对应多份**不同内容**的记录（记录以 `(hash, name)` 为键），它无法唯一确定磁盘上的东西。因此必须单独一列 `stored_name`。
- **启动时对全库做一次 `chmod` 收紧**：上万条目时是一次全量 IO，而收益只落在旧文件上。改成"新写入即只读 + 打开时懒收紧"。
- **旧归档一次性改名（启动时遍历改名 + 改索引）**：文件改名与索引写入**没有共同提交点**（正是 [ADR-0019](#adr-0019) / [ADR-0027](#adr-0027) 反复处理的那类问题），为一批"本机并不存在"的数据引入一条新的半途失败路径并不值得。见"已知限制"。
- **只读用 `0444`**：归档目录本身是 `0700`，`0444` 与 `0400` 在暴露面上没有区别；`0400` 与既有的"仅本人可读"一脉相承。顺带修正一处文档与实现不符：`security.md` 第 2 节一直写着"文件 `0600`"，而**代码里从来没有实现过**（只有目录的 `0700`）—— 本次把它落成 `0400` 并在同一份文档里改正。

**影响**：

- `src/main/archive/naming.ts`：新增纯函数 `archiveNameCandidates(name, hash)`（原名 → 8 位 → 16 位 → 全哈希），复用 `sanitizeFileName` 与"截断保扩展名"的拆法。
- `src/main/archive/blobs.ts`：`commitFromTemp(temp, name, options?)` → 按候选名落盘、同一内容建硬链接、落盘后 `chmod 0400`；新增 `ARCHIVE_FILE_MODE`、`archiveFilePath(storedName)`、`setReadOnly()`、`removeLegacyOpenDir()`；`usage()` 按 inode 去重；删掉 `blobPath(hash)`（旧的哈希布局专用）。
  `options.findStored(hash)` 是**注入**的（`capture/download.ts` 用索引实现），因为 `archive/` 内部方向是 `store → blobs`，反过来 import 会成环。
- `src/main/archive/schema.sql` + `store.ts`：新增 `stored_name`；`record()` 写入它；`toRecord()` 在为空时回落到 `hash`。加列必须自己判断存在性（既有库没有版本号机制，`schema.sql` 是 `IF NOT EXISTS` 风格）。
- `src/shared/types.ts`：`ArchiveRecord` 新增 `storedName`（磁盘上的实际文件名）。
- `src/main/integration/open.ts`：`openPath(hash, storedName)` / `revealPath(hash, storedName)` 直接对归档文件调用 `shell.openPath` / `shell.showItemInFolder`；删除 `openLinkPath()` / `ensureOpenLink()` / `clearOpenDir()`；打开前顺手 `setReadOnly()`。
- `src/main/capture/download.ts`：`commitFromTemp()` 的返回值（`hash` / `storedName` / `bytes`）直接用于索引与打开；删掉 `fileSize()`（它按哈希名 stat）；`clearOpenDir()` → `removeLegacyOpenDir()`。
- `src/main/archive/migrate.ts`：`isOwnEntry()` 的判据从"64 位十六进制"放宽为"非点开头 + 我们已知的点开头前缀"。理由：正文不再有可判定的名字形态，而两个方向的错误不对称 —— **漏搬一个我们自己的文件会让回滚谎报成功**，错搬一个外来文件只是让用户在两个位置都看到它。跨设备复制那条分支在复制后补 `setReadOnly()`（`rename` 保留模式，`copyFile` 不一定）。
- `scripts/check-capture.ts`：新增一节断言锁住命名与只读（第一个候选就是净化后的原名、冲突候选带哈希后缀、模式为 `0400`）。
- 测试：`blobs.test.ts` 重写命名/冲突/硬链接/只读部分；`naming.test.ts` 补候选名；`migrate.test.ts` 补"原文名文件也算归档内容"。
- 文档：`usage.md`（目录图、FAQ"为什么文件是只读的"）、`security.md`（第 2 节的权限与"防误改"）、`architecture.md`（第 3 节的"计算内容哈希 → 命名 → 原子改名"）、`media-capture.md`（第 4 节落盘流程与调试命令）、`roadmap.md`（M2 的"导出时还原原始文件名"不再需要）、`README.md`、`docs/README.md`、`ai/CONTEXT.md`（内容寻址那条）、`ai/TASKS.md`。

**已知限制**：

- **旧归档里的文件仍旧叫哈希名**，不会在启动时被改名：它们照常可以打开、搜索、迁移，只是名字不好看。旧记录 `stored_name` 为空 → 读取时回落到哈希名；打开时顺手把它设成只读。要不要为旧数据做一次改名迁移，等真的有人需要时再另开一次改动（那时才值得为它设计一条带回滚的提交路径）。
- **索引丢失/损坏时，跨名字去重会退化成"再存一份"**：内容身份记录在索引里，索引没了就只剩下磁盘上的名字可看。这是"把身份与名字拆开"的必然代价，而不是实现的疏忽 —— 同样的原因，`evictToFit()` 的实现（M2）必须通过索引拿到 `stored_name` 才能删对文件。

## ADR-0032

**决定**：归档的默认位置更名为 **`~/Documents/WaaChat_files`**（**位置不变，只换名字**）。

设置项（`Settings.archiveDir`）、迁移流程（[ADR-0019](#adr-0019)）、"索引随归档目录"（[ADR-0018](#adr-0018)）、"首次启动自动创建"（[ADR-0021](#adr-0021)）与"归档正文用原文名 + 只读"（[ADR-0031](#adr-0031)）全都不变。

**状态**：已生效（取代 [ADR-0023](#adr-0023) 的**名称**；那条 ADR 关于"放在文档目录下"的理由与其余决定保留）

**背景**：ADR-0023 在"回到 `~/Documents`"的同时选了 `WhatsApp_files` 这个名字，理由是"目录名要回答的是'这些是谁的文件'"，并把它归入**指示性使用** —— 与代码里出现 `web.whatsapp.com` 同类，[INV-4](#adr-0020) 约束的是视觉标识素材，不覆盖数据目录命名。那次它把 `~/Documents/WaaChat_files` 明确列为**被否决的替代方案**（"在用户的文件管理器里不如 `WhatsApp_files` 说得清'这些是什么'"）。

所有者现在要求换成项目名 `WaaChat_files`。这不是在纠正一处违反 —— ADR-0023 的论证本身仍然成立（指示性使用不违反 [INV-4](#adr-0020)）；换的是**在可选的地方选哪一边**。

**理由**：

1. **这是唯一一处把服务方名称写进"我们创建的产物"。** 应用名、包名、可执行名、`appId`、配置目录（`~/.config/waachat`）用的都是项目名（[ADR-0020](#adr-0020) 的收敛结果），只有这个目录例外 —— 而它恰好是**用户唯一会在自己的文件管理器里天天看见**的那一处，也最容易被读成"官方目录 / 官方客户端生成的"。非官方声明（[INV-4](#adr-0020)）是强制义务，而"在不需要它的地方别写服务方名称"是同方向的、成本为零的一步。这不是把声明换成命名，两者互不替代。
2. **ADR-0023 的理由 3 在今天变弱了。** 那条理由是"目录名要回答'这些是谁的文件'"。但 [ADR-0031](#adr-0031) 之后，归档里的**文件本身**带着原文名（`2026年第三季度采购合同.pdf`）—— "这些是什么"由内容回答；目录名要回答的其实是"谁把它归档的"，而那正好是项目名。
3. **代价很小，而且已经被人付过一次。** 名字不如 `WhatsApp_files` 直白，会有人问"WaaChat 是什么"——但那正是他刚安装的那个应用的名字，比一个他没装过的服务名更容易解释。

**被否决的替代方案**：

- **保持 `WhatsApp_files`（ADR-0023 的取舍）**：论证仍然成立，但在"写不写服务方名称"这件事上，能少写一处就少写一处 —— 尤其是写进用户磁盘上、由我们创建的目录名里。
- **`~/Documents/WaaChat`（不带 `_files`）**：与配置目录 `~/.config/waachat` 只差大小写与位置，口头描述时容易混（ADR-0023 已经记过这条）。
- **改默认值的同时把旧默认目录自动搬过来**：ADR-0023 已经否决过一次 —— 迁移必须先经用户确认（[ADR-0019](#adr-0019)），未经确认就替用户搬动数据正是那条 ADR 要避免的。这次同样**不写**。
- **顺手把 `~/.config/waachat` / `~/.local/share/waachat` 也改成 `WaaChat`**：那些是 XDG 目录下的应用标识（[ADR-0020](#adr-0020) 已经定了小写项目名），改名等于让所有用户重新扫码 / 丢缓存；而且它们不面向用户的文件管理器。不碰。

**影响**：

- **从未改过设置的用户会跟着默认值移动**（与 ADR-0023 的影响完全相同，逐字保留那条结论）：`archiveDir` 的空串语义是"用默认位置"，因此应用会去创建并使用 `~/Documents/WaaChat_files`，而旧默认目录里的文件仍在原处、**只是在界面里看不见了**。两条出路：用设置里的「更改…」指回旧目录，或手工把文件搬过来。**不写自动搬迁逻辑**。`docs/usage.md` 的常见问题里加了一条按这个说法写的说明。
- 已是自定义位置的用户不受影响（`archiveDir` 非空，与默认值无关）。
- `src/main/paths.ts`：`ARCHIVE_DIR_NAME` 改为 `WaaChat_files`，并把那段"为什么用服务方名称"的注释改写成指向本 ADR（那条注释原本的理由已经反转，留着它就是**文档与实现不一致**）。
- `src/shared/types.ts` 的 `archiveDir` 注释、`scripts/check-capture.ts` 的默认值断言、`test/unit/paths.test.ts`、`test/unit/blobs.test.ts` 的注释同步。
- 文档：`docs/usage.md`（6 处路径 + 常见问题）、`docs/architecture.md` 的目录树、`docs/media-capture.md` 的调试命令、`docs/security.md` 与 `SECURITY.md` 的资产表、`ai/TASKS.md`。

## ADR-0033

**决定**：

1. 协议层"原样回源"的那一次请求，改用**它所属的分区会话**发出（`ses.fetch`），不再用默认会话（`net.fetch`）。
2. 对**我们自己发起**的请求做**有限重试**：只重试幂等方法（`GET` / `HEAD`）、只重试连接层的错误、最多 3 次尝试（间隔约 300 ms / 900 ms，带抖动）。两个方向都记日志（重试与放弃，**只记 host**）。

**状态**：已生效

**背景**：用户报"网络不稳定导致的经常性握手失败"，贴出的日志是：

```
[2769060:1010/013502.026663:ERROR:net/socket/ssl_client_socket_impl.cc:962] handshake failed;
  returned -1, SSL error code 1, net_error -101
```

`net_error -101` 是 `ERR_CONNECTION_RESET`：TCP 连接在 TLS 握手过程中被对端（或中间设备）**重置**。它不是"证书不对"，也不是"协议谈不拢" —— 是连接本身没了。

面对这类报错，一个应用能做的事只有三种：少发几次请求、失败后重试、以及在失败时**说清楚是谁失败了**。顺着这三条去查代码，发现第一件该修的事与网络无关：`capture/protocol.ts` 的直通路径用的是 `net.fetch`，而 `net.fetch` 走的是**默认会话**；被它接住的请求却属于 `persist:` 分区。也就是说，**同一个请求被从另一个网络上下文里重发了**。

一次性探针（Linux + `xvfb-run`，Electron 44）实测：

| 实验 | 结果 |
|---|---|
| 握手期间连接被 RST | 抛出 `Error`，`message: "net::ERR_CONNECTION_RESET"`（另一种情形是 `ERR_CONNECTION_CLOSED`）；**没有** `code` / `errno` / `cause`，`Object.keys(error)` 为空 |
| 首次连接被重置、第二次正常 | **重试救回来了**：第二次拿到 200；在生产形态下（`protocol.handle('http')` 内、用**同一个 `Request` 对象**重试）页面正常渲染出正文 |
| 响应里的 `Set-Cookie` 落到哪个会话 | `net.fetch` → **默认会话**（分区 0 条 / 默认 1 条）；`ses.fetch` → 分区（1 条 / 0 条） |
| 连接池归属 | `net.fetch` 与分区自己的请求**各用一条连接**（2 条）；`ses.fetch` **复用同一条**（1 条） |

**理由**：

1. **我们不是"另一个客户端"，不能把别人的请求挪到别的会话里重发。** cookie 罐子、代理与证书配置、DNS 缓存、连接池都挂在会话上。上表第三行是最严重的后果：页面自己发请求时带着它的 Cookie，但**响应里的 `Set-Cookie` 从没进过它自己的罐子** —— 而缓存层现在是**默认开启**的（[ADR-0028](#adr-0028)），也就是说**每一个 https 响应**都走过这条路。登录/CSRF 这类状态长期陈旧，症状会像"莫名其妙要重新登录"，没人会怀疑到网络层。
2. **重试是这一层唯一能替用户做的事。** Chromium 不替调用方重试握手失败：那一次请求直接失败，页面表现为资源缺失、媒体打不开。而"网络抖动"正是重试能解决的那一类 —— 上表第二行证明它确实能救回来。
3. **边界必须写死在代码里，不能做成设置。** 只重试幂等请求（`POST` / `PUT` 可能已经被对端处理过，重试等于重复提交）；只重试**连接层**错误（证书错误、4xx/5xx 重试不会改变结论，只会掩盖问题、拖慢失败）；**有上限**（网络被整段阻断时重试必然也失败，有上限才不会把"加载中"变成"一直加载中"）。
4. **只覆盖我们自己发起的请求，并且不把它说成"修复网络"。** 页面的 websocket（`wss://`）与不经过 https 的流量都不在这里；它们由页面自己负责。这一层能做的是少犯自己的错、并且在抖动时多试一次 —— 仅此而已。
5. **失败要能定位到主机。** 探针里那条 Chromium 日志**不含主机名**，用户拿到的信息是"某个握手失败了"。我们补的日志记 `host` 与 `net::ERR_…`，这样"是聊天页面、还是媒体 CDN、还是两者都在失败"才分得清 —— 这正是判断"该找代理"还是"该看我们的代码"的依据（G-1 允许记 host，不允许记完整 URL）。

**被否决的替代方案**：

- **改成"关掉 QUIC / 关掉 HTTP2"之类的启动开关**：用户日志里那条来自 `ssl_client_socket_impl.cc`，是 **TCP+TLS 路径**，不是 QUIC（QUIC 失败会记在 `quic_*` 里）。没有证据支持换协议栈，而这两个开关会实打实地牺牲性能。要用命令行试的余地留着，写进 FAQ，而不是变成默认行为。
- **`--ignore-certificate-errors` 或降低校验**：握手失败与证书无关（上表第一行没有 `ERR_CERT_*`），而这个开关是把中间人当成朋友。
- **重试所有方法**：见理由 3 —— "连接层失败"并不能保证请求没被对端处理过。
- **无上限重试 / 退避到几十秒**：被阻断时会把界面卡在"加载中"，而用户更需要**尽快失败并看到原因**。
- **在 `webRequest` 层做重试**：`onErrorOccurred` 无法重新发起请求；`onBeforeRequest` 里用 `redirectURL` 自指是个把戏，而且会与协议层叠在一起。
- **把重试次数做成设置**：它没有"用户偏好"的成分 —— 3 次尝试（≈1.2 秒上限）对"抖动"与"阻断"两种情况都说得通。真需要时再开（现在只是常量，改一处就够）。
- **把响应体中途断掉也算作可重试**：那时响应**已经交给页面**了，重试等于对外撒谎（页面以为拿到的是完整的）。这条留给页面自己（它知道自己在下载什么）。

**影响**：

- 新模块 `src/main/capture/retry.ts`：`TRANSIENT_NET_ERRORS`（白名单）、`isTransientNetworkError()`、`nextDelayMs()`、`fetchWithRetry()`。**不导入 electron**（fetch 由调用方注入），因此可单测。
- `src/main/capture/protocol.ts`：`passthrough(request, ses)` 改用 `ses.fetch(...)`，外面套 `fetchWithRetry()`；重试与放弃各记一条日志（`host` + `net::ERR_…` + 第几次）。
- `src/main/logger.ts`：`hostOf()` 提上来共用（`capture/pdf.ts` 里原本有一份私有实现）。G-1 的"日志里只许出现 host"因此只有一个落点。
- `scripts/check-capture.ts`：新增断言把判据锁在实测形状上 —— `net::ERR_CONNECTION_RESET` / `ERR_CONNECTION_CLOSED` 可重试，`net::ERR_CERT_AUTHORITY_INVALID` / `net::ERR_ABORTED` / 非 `net::` 的错误不可重试。
- 测试：`test/unit/retry.test.ts`（判据 + 重试次数 + 幂等边界，用注入的假 fetch 与假计时器）。
- 文档：`docs/usage.md` 常见问题（"握手失败/资源加载不出来怎么办"：先看日志里是我们在重试还是已经放弃、代理与 VPN、可以命令行试哪几个开关）、`docs/media-capture.md` 第 3 节（我们发起的请求走哪条路）、`ai/TASKS.md`。

**已知限制（必须与决定一起读）**：

- **网络被整段阻断时（例如按 SNI 重置握手），重试必然也失败。** 这时日志里会出现"放弃"记录，正确的应对是代理 / VPN / 换网络；改这个应用没有用。这条改动**不能**让被阻断的网络变得可用。
- **只覆盖响应交给页面之前**的失败：连接、握手、首字节。响应体中途断掉（大文件下到一半被 RST）不重试，见上。
- **证书类错误永不重试**，理由见替代方案。
- 页面的 websocket 与不使用 https 的流量不在覆盖范围内（理由 4）。

## ADR-0034

**决定**：

1. GLib 的这条报错**不当成我们的缺陷追**，也不为它静默 Chromium 的日志：
   ```
   ERROR:content/browser/browser_main_loop.cc:279] GLib-GObject: ../../../gobject/gsignal.c:2723:
     instance '0xd4c000cbb10' has no handler with id '8345'
   ```
2. **不采用"重建托盘"来刷新托盘图标**（社区为绕开 appindicator 下 `Tray.setImage()` 失效而流行的做法）—— 那正是产生这类 stale handler 的经典模式。代价是接受"某些指示器实现下托盘图标要到下次启动才更新"，并如实在用户文档里说明。
3. **"没有托盘"这件事不可检测**，因此不写"检测不到托盘就换一种行为"的逻辑；改的是**说法**：`tray.ts` 里"缺失时降级为没有托盘"只覆盖"构造失败"这一种情形，用户文档要写清 GNOME 缺 AppIndicator 扩展时的真实处境与两条入口。

**状态**：已生效

**背景**：用户报这条 GLib 报错并要求修复。它来自 GLib 的 `gsignal.c` —— 有人对一个 GObject 实例调了 `g_signal_handler_disconnect()`（或移除 emission hook），而那个 handler id 在这对象上已经不存在了。**发出它的是加载进我们进程的某个 GTK 库/模块**（典型的：Ubuntu 的 `gtk-modules`（`colorreload-gtk-module` / `window-decorations-gtk-module`）、`appmenu` 模块、以及 Linux 托盘用的 `libayatana-appindicator`），只是被 Chromium 的 GLib 日志转发器打成了 ERROR。我们的代码是 JS，不碰 GObject 信号 id。

一次性探针（Linux + `xvfb-run`，Electron 44）按**生产里的用法**跑了一遍，结果：

| 实验（都用生产里的模式） | 结果 |
|---|---|
| 托盘只建一次 + `Tray.setImage()` 刷 3 次（从不重建） | 全程 **0 条** `has no handler with id` |
| 主窗口建一次 + 关闭时 `preventDefault()` + `hide()` | 同上 |
| 另建 3 扇窗口再 `close()`（模拟 dev 模式下"关窗即销毁"） | 同上 |
| 最后 `tray.destroy()` + 窗口 `destroy()` | 同上 |
| 无任何指示器宿主（xvfb 下没有面板）时 `new Tray(icon)` | **成功**（`trayCreated: true`，不抛错） |

最后一行是这次审计真正的收获：它推翻了一句我们一直写在代码与文档里的说法 —— 「缺失时的行为是**降级为没有托盘**」。**`new Tray()` 在没有指示器宿主时照样成功**，于是 `getTray()` 非空、`hideOnClose` 照旧把窗口藏起来，而用户桌面上根本没有那个图标。

**理由**：

1. **这条消息里没有我们的代码。** 追它意味着去读 GLib 的 handler 表与某个模块的源码，而我们既不能改那个模块，也不能从 JS 侧影响它的信号生命周期。把它当成"我们的 bug"只会导致一次不可能成功的排查 —— 更坏的是，找不出原因时很容易转向"把它藏起来"。
2. **不静默日志。** 那几行 ERROR 与网络栈的报错走同一条通道 —— 就在这次会话里，我们刚靠 `capture: retrying… / gave up` 与 `handshake failed` 这类日志把"网络被阻断"与"网络在抖"分开（[ADR-0033](#adr-0033)）。用 `--log-level=3` 之类的手段把 ERROR 全部关掉，等于把真正有用的那部分一起关掉，换来一行噪音。想静音是用户的自由（写进 FAQ），但不做默认。
3. **不重建托盘。** "换图标要重建托盘"这条经验在社区里流传很广，而它对我们只有坏处：我们无法验证 GObject 生命周期（本机没有 appindicator 宿主），而它恰恰会产生这类 stale handler 警告 —— 用一个真实的资源生命周期问题，换一个"图标立刻变"的体验。宁可接受降级，并把它写清楚。
4. **把"不可检测"写下来，比写一段猜的代码有用。** `getBounds().width === 0` 之类的启发式在 appindicator 下不可靠（Electron 自己也不建议依赖它）。既然检测不了，就在文档里给用户**能用的两条入口**：重新运行 `waachat`（单实例锁会把这扇窗口叫回来，`index.ts` 的 `second-instance`）、以及 `Ctrl+Q` 退出（默认菜单提供，不依赖托盘）。

**被否决的替代方案**：

- **默认调低日志级别（`--log-level=3`）把这条盖掉**：见理由 2。它会一起盖掉网络握手失败、`Set-Cookie` 归属这类我们**主动加进去**的诊断信息。
- **换成"重建托盘"来让图标立刻生效**：见理由 3。
- **在启动时探测托盘是否真的可见，不可见就不隐藏窗口**：检测不了（见背景最后一行），写成"探测"其实是写一段在别人机器上乱走的启发式。而且它改变的是**退出行为**（关掉窗口就退出），把一次说法修正变成一次行为变更 —— 那需要单独的证据与决策。
- **干脆不要托盘**（托盘是 GObject 生命周期的来源之一）：托盘在本项目里是"退出入口 + 常驻后台"的必需品（`tray.ts` 头部），去掉它等于换产品行为，而这条噪音根本不值得。
- **去追 GLib / appindicator 的源码并提交补丁**：那是上游的事（而且要复现得有对应的桌面环境）。我们的责任边界是"不制造这类模式"，不是"修好别人的 GObject 生命周期"。

**影响**：

- `src/main/integration/tray.ts`：头部那句"缺失时的行为是降级为没有托盘"改成**实测后的准确说法**（只覆盖构造失败；不可见检测不到，因此关窗后要用 `waachat` 或 `Ctrl+Q`）。
- `src/main/ipc/index.ts` 的 `refreshTrayIcon()`：在 `setImage` 那一行写清**为什么这里不重建托盘**（免得后人照着社区经验"修"成重建，把这条噪音与一个未经验证的生命周期问题一起请回来）。
- `docs/usage.md`：常见问题新增一条（这条 GLib 报错是什么、怎么确认来源模块、什么时候才该担心、想静音的代价）；「托盘图标不显示（GNOME）」一节与「界面与托盘菜单」一节补上"没有可见托盘时的两条入口"；「应用图标」一节与设置表里"窗口与托盘立即生效"的说法收窄到实测范围（托盘那一项在部分指示器实现下可能要下次启动）。
- 测试 / 自检：**没有**变化 —— 这条改的是说法与注释，没有可断言的纯逻辑。探针用完即删，结论记在上面的表里。

**已知限制**：

- 换个桌面环境（或换了 GTK 模块版本）之后，这条噪音可能变成别的样子（例如换一个 `g_signal_handler_disconnect` 的调用点）。它仍然是外部模块的行为，不因此变成我们的问题。
- **托盘图标在 appindicator 下"刷新是否生效"我们从未在真实环境验证过**（本机没有指示器宿主）。文档因此只写"立即生效（GTK status icon 路径）／可能要下次启动（部分指示器实现）"，而不是继续断言"立刻"。这一条留给真机验证：如果它确实不生效，那也是一次**文档与取舍**的修正，而不是去重建托盘。

## ADR-0035

**决定**：把 `persistent-storage` 加进权限白名单（**仅上游源**，与其它几项共用同一条来源判据）。**其余权限继续一律拒绝**，并且不再"顺手"放开任何一个 —— 每一项都要带证据（见下面的取证清单）。

**状态**：已生效

**背景**：用户日志里出现

```
WARN permission denied {"permission":"persistent-storage","fromUpstream":true}
```

上游页面调用了 `navigator.storage.persist()`（Chromium 用 `PERSISTENT_STORAGE` 权限门控它），而白名单里只有 `notifications` / `media` / `clipboard-sanitized-write` / `fullscreen`，于是被拒。

**理由**：

1. **它不是一个"能力"权限，而是一句"别把我的数据淘汰掉"的请求。** 它不授予对任何用户数据或设备的访问 —— 对比 `clipboard-read`（读剪贴板）、`geolocation`（位置）、`media`（摄像头/麦克风）。它影响的只是 Chromium 对本分区里**这个源自己的**存储（IndexedDB / CacheStorage / ServiceWorker 注册）的淘汰策略。把它和摄像头权限并列看待，是把两件性质不同的事当成了一件事。
2. **拒绝它的代价落在本项目的核心承诺上。** 这个分区里存着登录态与消息库，而 [ADR-0008](#adr-0008) 的立场是"登录态是用户资产、绝不代用户清除"。best-effort 存储意味着磁盘紧张时 Chromium**可以**淘汰它 —— 症状是消息历史重新同步，最坏情况要用户**重新扫码**。为了挡一个不存在的风险，去给用户制造一次重新登录，不划算。
3. **来源判据不变，白名单仍然只有五项。** 这次不是"为了少出问题全放开"（那正是 `security.md` T5 的触发条件），而是逐项判断：真会暴露用户东西的那几类继续拒绝。
4. **顺手把白名单从 `session.ts` 提到一个纯模块里。** 在此之前它是"安全关键、但只能靠读代码确认"的状态 —— `session.ts` 顶层导入 electron，离线自检与单测都进不去。提出来之后，**"哪些权限被放行"变成可以被断言的约定**：将来有人放宽它，自检会先变红。

**被否决的替代方案**：

- **允许所有权限**：见 `security.md` T5。
- **`persistent-storage` 不限来源地放行**：来源判据是第二条防线（同一个分区里还有我们自己的本地界面窗口）。不因为一个低危权限就在这上面开口子。
- **不放开，让页面自己处理"被拒绝"**：页面处理不了 —— Electron 里这类权限没有面向用户的界面，拒绝就是最终答案（`persist()` 返回 `false`，页面只能继续用 best-effort）。"让用户自己决定"在这里是一个不存在的选项。
- **用命令行开关或 CDP 给整个分区提前开持久化**：那是绕过权限模型，也就绕过了这个可以评审、可以被断言的落点。
- **顺手把 `display-capture` / `speaker-selection` / `geolocation` 一起放开**："顺手"正是 T5 要防的写法。它们每一个都需要真机证据（见取证清单），没有证据就放开，等于把"未知"当成"安全"。
- **把 `clipboard-read` 一起放开**（"复制粘贴总要吧"）：DOM 的 `paste` 事件不需要它，需要它的是 `navigator.clipboard.read*` —— 那才是真正"静默读用户剪贴板"的能力。保持拒绝。

**影响**：

- 新模块 `src/main/permissions.ts`：`ALLOWED_PERMISSIONS` 与 `isPermissionAllowed(permission, requestingOrigin)`。**不导入 electron**（只 `import type`），因此自检与单测可以直接断言它。
- `src/main/session.ts`：两个处理器（request / check）都改用它 —— 行为与之前一致，只是判据搬了家，现在可测试。
- 测试：`test/unit/permissions.test.ts`（放行项、拒绝项、来源精确比对、未知权限默认拒绝）；`scripts/check-capture.ts` 新增一节断言把几条约定锁住。
- 文档：`docs/security.md` T5 的对策文字与代码对齐（原来只写了"通知与媒体"，实际还有剪贴板写入与全屏，现在多一项）；`docs/usage.md` 新增常见问题（点了某个功能没反应时怎么从日志判断是不是被我们拒了，以及放行/拒绝清单）；`ai/TASKS.md` 记一条纪律。
- **取证清单**（写给将来的自己，不是待办）：下面每一项都**没有**证据表明上游会请求，因此**没有**放开。用户报告"某个功能点了没反应"时，先看日志里有没有对应的 `permission denied`：

  | 权限 | 对应功能 | 症状 | 取证方式 |
  |---|---|---|---|
  | `display-capture` | 通话里共享屏幕 | 点了共享没反应 | 看日志有没有 `permission":"display-capture"`（我们已经用系统选择器处理 `getDisplayMedia`，但权限这一层是否也要放行**没有验证过**） |
  | `speaker-selection` | 通话里选扬声器 | 选不了输出设备 | 同上 |
  | `geolocation` | 发送位置 | 地图不定位 | 同上（真放行时要不要按"仅上游源"再加一道确认，届时单独决定） |
  | `clipboard-read` | 粘贴图片/文本 | 一般不影响（`paste` 事件不需要它） | 同上 |

**已知限制**：

- 白名单是**双向**的，两半都必须对：来源（`isUpstreamOrigin` 精确比对 origin，不是前缀匹配）与类型。只改一半会留下一扇对着第三方页面的窗（`https://web.whatsapp.com@evil.com/` 这类前缀骗术在 `shared/upstream.ts` 里有单测）。
- `persistent-storage` 被允许**不等于**存储一定不会被清：用户磁盘极度紧张、或用户自己清了 profile，Chromium 仍可能回收。它只是把"可以被淘汰"改成"优先保留"。

## ADR-0036

**决定**：**在走 Wayland 的 Ozone 路径时**，于启动最早期（`app.whenReady()` 之前、GPU 进程启动之前）追加
`--disable-features=Vulkan,DefaultANGLEVulkan,VulkanFromANGLE`，并与用户已有的 `--disable-features` **合并**（不覆盖）。
此外：

- **X11 路径一个开关都不动**（Vulkan 在 X11 上可能真的可用）；
- 用户**显式**要求 Vulkan（`--enable-features` 里含 `Vulkan`）时**完全不动** —— 显式选择优先；
- 不强制 `--ozone-platform=x11`。

**状态**：已生效

**背景**：用户启动时看到

```
ERROR:ui/ozone/platform/wayland/gpu/wayland_surface_factory.cc:249]
  '--ozone-platform=wayland' is not compatible with Vulkan.
  Consider switching to '--ozone-platform=x11' or disabling Vulkan
```

这句话是 **Chromium 自己**在说：Wayland 的 surface factory 不支持 Vulkan。核查过的两件事：

- **我们没有传过任何相关开关。** `src/` 里没有一处 `appendSwitch` / `commandLine`；桌面条目的 `Exec` 只有 `<可执行文件> %U`（`buildDesktopEntry`）。也就是说 `--ozone-platform=wayland` 是 Chromium 的 ozone **自动选择**结果（那串字是**生效**平台，不是我们传的），Vulkan 一侧来自 Chromium 自己默认开启的 Vulkan 相关 feature。
- **那三个 feature 名与这行报错串都在二进制里**（`strings` 核对：`Vulkan`、`DefaultANGLEVulkan`、`VulkanFromANGLE`、`is not compatible with Vulkan`），因此关掉它们是有依据的，不是照着猜测写开关。

**理由**：

1. **在 Wayland 上这是一个不可能满足的请求。** Chromium 每次启动都会尝试 Vulkan → 拿不到 surface → 回退到 GL，并在日志里留一行 ERROR。我们做的只是"不再请求它"：**功能上零损失**（那条路径上本来就没有 Vulkan 可用），换来每次启动少一次注定失败的 GPU 初始化、少一行会被当成故障的报错。
2. **不在 X11 上动它。** 同一个二进制在 X11 会话下 Vulkan 可能**真的**可用（X11 的 surface factory 支持它）。因此判据必须是"**生效的**臭氧平台"，而不是"发行版"或"会话类型"。
3. **三个 feature 一起关。** 它们都指向 Vulkan（原生 Vulkan、ANGLE 的 Vulkan 后端、"ANGLE 默认用 Vulkan"），在 Wayland 上它们会落到同一个不支持的 surface factory。**哪一个当前是默认开启的取决于 Chromium 版本，我们没有逐个验证** —— 而"禁用一个本来就没开的 feature"是无害的，这比挑一个来猜更稳。
4. **合并而不是覆盖 `--disable-features`。** `appendSwitch` 是同名开关以最后一次为准，直接写会把用户自己的列表**静默抹掉** —— 那是在改用户的意图，而它不会有任何提示。
5. **用户的显式选择优先。** 有人可能就是要试 `--enable-features=Vulkan`（例如将来的 Chromium 真支持了 Wayland+Vulkan）。我们不去赢这场争论：检测到显式要求就不动作。

**被否决的替代方案**：

- **按 Chromium 那行报错的另一个建议强制 `--ozone-platform=x11`**：会丢掉原生 Wayland（窗口图标靠 `app_id`、缩放与分数缩放），对这个"要看起来像原生应用"的壳是倒退；纯 Wayland 会话下没有 XWayland 时更是直接跑不起来。
- **全平台关掉 Vulkan**：见理由 2。
- **什么都不做，只在文档里解释"这是无害噪音"**：那行描述的是一次**真实的失败尝试**（不是纯提示），而且每次启动都发生 —— 它是确定性的、完全能避免的组合。文档照旧要写（用户在别处也可能看到同类报错），但"不去动它"等于把一个可消除的失败留给用户。
- **`--disable-gpu` / 强制 SwiftShader 软件渲染**：因噎废食 —— 为了消一行日志把整个 GPU 加速关掉。
- **用更底层的 `--disable-vulkan-surface` / `--use-vulkan=…`**：语义更窄也更难解释。我们不是在调 Vulkan 的内部行为，而是决定"在这个平台上不请求它"。
- **把它做成设置项**：用户没有"我想在这台机器上用 Wayland 上的 Vulkan"这个需求（它不成立），能提供的只有"更多的选择"和"更多的解释成本"。

**影响**：

- 新模块 `src/main/linux-gpu.ts`：`usesWaylandOzone()` / `userRequestedVulkan()` / `applyLinuxGpuSwitches()`。纯函数 + 可注入的命令行接口（与 `app.commandLine` 同形），因此能单测，不必真的启动 GPU 进程。
- `src/main/index.ts`：在 `configureLogger()` 之后调用一次（必须在 `ready` 与 GPU 进程启动之前），动过命令行就记一条 `info`。
- 测试：`test/unit/linux-gpu.test.ts`（Wayland 才动、X11 不动、显式开关优先、与已有列表**合并**）；`scripts/check-capture.ts` 新增一节把这四条锁住。
- 文档：`docs/usage.md` 常见问题新增一条（那行是什么、我们做了什么、仍然看到时怎么覆盖）。

**已知限制**：

- **没有在真实 Wayland + GPU 的机器上验证过"关掉之后那行就消失"**（本机是 X11）。可验证的推理是：那行只在 Wayland × Vulkan 的组合下出现，而我们现在在这个组合下不请求 Vulkan。真机确认留给用户。
- 如果将来 Chromium 支持了 Wayland+Vulkan，我们会在 Wayland 上**白关一次**（代价是拿不到 Vulkan 加速）。届时的正确动作是**删掉这个开关**，而不是再加开关绕它 —— 这也是把这条写在这里的原因。
- 只影响**我们自己的进程**：用户从浏览器或别的 Electron 应用里看到的同类报错与本 ADR 无关。
