# 接管机制

本文档描述 `src/main/capture/` 的原理、设计前提与**已知脆弱点**。取舍理由见 [`decisions.md`](decisions.md) ADR-0001 / ADR-0002 / ADR-0007 / ADR-0015 / ADR-0016。

> ⚠️ **这一层正在被移除。** 本文描述的"内核层接管"是 [ADR-0043](decisions.md#adr-0043) 之前的架构。
> 迁移后 `capture/` 的密文缓存与协议层**失去意义**，下载接管改为消费 `whatsapp-web.js` 的媒体事件
> （见 [ADR-0044](decisions.md#adr-0044) 的「影响」清单）。下面的原理与脆弱点仍是**当前代码**的真实结构，
> 但"接管点必须在内核层"这个前提本身已被推翻。

---

## 1. 为什么接管点必须在内核层

从页面内部取数据是最短的路径，但那需要注入，已被 ADR-0002 否决。去掉注入之后，剩下的可用观察面只有**浏览器内核的标准行为**：

| 可用观察面 | 能看到什么 | 稳定性 |
|---|---|---|
| 下载事件（DownloadItem） | 文件名、大小、字节流、最终状态 | 高 —— 任何 `<a download>` 与 blob URL 下载都经过这里 |
| 会话协议层（https 请求） | 请求 URL、响应流 | 高 —— 标准网络栈 |
| 页面内部对象 / DOM / 内部函数 | 一切 | **不可用**，禁止 |
| 解码后的内存缓冲 | 明文 | **不可用**，禁止 |

选择内核层的三个理由：**不注入**（合规）、**不依赖上游内部结构**（可维护）、**不触碰加密**（性质）。

## 2. 两个接管点，以及为什么是两个

它们解决的是两个不同的问题，**不是同一件事的两种实现**：

```
┌─ 接管点 A：下载事件 ─────────────────────────────────────┐
│ 解决：点击文件后"下载到哪、怎么打开"                       │
│ 观察：页面解密完成 → 产生 blob 下载                       │
│ 产出：归档中的一份明文 + 索引记录 + 交给系统打开            │
└──────────────────────────────────────────────────────────┘

┌─ 接管点 B：会话协议层 ───────────────────────────────────┐
│ 解决："同一个文件第二次点击又要联网下载一遍"                │
│ 观察：页面发起对媒体 CDN 的请求                            │
│ 产出：密文磁盘缓存（命中即不联网）                         │
└──────────────────────────────────────────────────────────┘
```

**只有 A 也能用**：文件照样点击即开、照样归档、照样去重。缺的只是"二次点击仍要联网"。

**只有 B 没用**：缓存了密文但页面还是把文件丢进 `~/Downloads`。

**这一层发出去的请求必须是"它自己的"**（[ADR-0033](decisions.md#adr-0033)）：被接住的是 `persist:` 分区里的请求，因此回源用 `ses.fetch`，而不是默认会话的 `net.fetch` —— cookie 罐子、代理与证书配置、连接池都挂在会话上。实测过两条后果：`net.fetch` 会把响应里的 `Set-Cookie` 写进**默认会话**的罐子（页面自己的罐子永远得不到更新），以及两套连接池各开一条连接。

**连接层失败会有限重试**（同一个 ADR）：网络抖动时一次 TLS 握手被重置（`net_error -101`）本来可以靠重试救回来，而 Chromium 不替调用方重试。策略写死在 `capture/retry.ts`：只重试 `GET`/`HEAD`、只重试连接层错误（白名单）、最多 3 次尝试、间隔约 0.3 / 0.9 秒带抖动。重试与放弃各记一条日志（`capture: retrying…` / `capture: gave up on a flaky connection`，带 `host` 与 `net::ERR_…`）。**网络被整段阻断时重试必然也失败** —— 那不是这一层能解决的问题，判断方法见 [`usage.md`](usage.md) 的常见问题。

因此实现顺序是 A → B（见 [`roadmap.md`](roadmap.md)），A 是必须的，B 是质量提升，且 B 可以随时关闭而不影响正确性。它**默认开启**（[ADR-0028](decisions.md#adr-0028)）：缓存里存的是上游已经加密好的那份密文，本应用不参与加解密，因此没有理由把"第二次打开还要联网"留给用户。开关本身是一次**静默的事务式转换**：切协议层 → 转换 → 提交，全部成功才切换，失败或中断回退；提交即生效，**不需要重启**，也没有确认框与进度屏（[ADR-0027](decisions.md#adr-0027) / [ADR-0028](decisions.md#adr-0028)）。关闭时 `cache/` 里不留东西，开启则保留可命中的条目（`capture/cache-files.ts` / `capture/cache-switch.ts`）。

**A 还有一条可选的前提：PDF 也可以走到下载事件。** 内核内置的 PDF 阅读器在 Electron 里**关不掉**
（实测见 [ADR-0029](decisions.md#adr-0029)），因此"让系统阅读器打开 PDF"只能反过来做：上游的文档预览页
被挡掉（窗口与子框架两处），`application/pdf` 的响应被降级成 `application/octet-stream` —— 于是它变成
一次下载，落进上面这条既有路径。

它不是第三个接管点：没有新路径，只是把 A 的输入补齐（`capture/pdf.ts`），而且**默认不生效** —— 由设置
`disablePdfPreview`（「禁用 PDF 预览」）控制（[ADR-0030](decisions.md#adr-0030)）：关着时上游的预览页照常
加载、PDF 在应用内预览；打开后才有上面两条规则。为什么不能反过来"关掉阅读器"、为什么"点 PDF 直接弹出
系统阅读器"做不到、以及打开这个开关要接受什么：见 [ADR-0029](decisions.md#adr-0029) 的实测表与"已知限制"。

> **刻意不做的第三件事**：在明文层再做一次缓存。它需要拿到解密后的缓冲，那只能靠注入。B 已经在密文层解决了同一个问题，且完全不碰加密。

## 3. 幂等键

媒体 URL 形如：

```
https://<media-host>/v/t62.xxxx.../NNNNNN.enc?ccb=11-4&oh=<签名>&oe=<过期时间>&_nc_hot=<提示>
```

| 部分 | 是否参与键 | 理由 |
|---|---|---|
| host | 先按 host 过滤，不匹配直接直通 | 只接管媒体 CDN（`*.cdn.whatsapp.net`，见 [ADR-0015](decisions.md#adr-0015)），不干扰其余流量 |
| pathname | **参与** | 每个媒体对象一个稳定路径，是对象身份的主要来源 |
| `oh` / `oe` / `_nc_hot` 等 | **剔除** | 每次请求都变，含进去缓存永远不命中 |
| 其余查询参数 | 保守参与 | 宁可少命中，不可错命中 |

### 三个必须承认的前提

1. **"剔除签名参数后 pathname 仍然唯一标识对象"是一个实测结论，不是推理结论。**
   在不同版本、不同媒体类型（图片 / 视频 / 文档）上都必须验证。若发现碰撞，必须立即退化为"只做接管点 A"。
2. **宁可漏命中，不可错命中。** 错命中意味着页面拿到一份**属于别的文件**的密文，解密会失败（MAC 校验不过），表现为"文件打不开"——这是比"重新下载一次"严重得多的问题。因此缓存键必须包含足够的区分度。
3. **缓存上限必须存在。** 无上限的密文缓存会无声地吃掉磁盘。超限时应先淘汰，仍不够则退化为直通。

## 4. 落盘的原子性

归档目录里**不允许出现半成品文件**。流程：

```
1. 下载事件给出目标路径 → 指向 archive **根**目录下的临时名（前缀标记，如 .part-<随机>）
2. 下载完成（状态为 completed）
   ├─ 非 completed → 删除临时文件，结束，不做任何索引
   └─ completed →
        3. 计算内容哈希（这份内容的身份，不是文件名 —— ADR-0031）
        4. 目标路径 = <archive>/<年>/<月>/<净化后的原名>；同一个月内同名被占则加一小段哈希
           （年月取自**归档时刻**的本地时间，目录按需创建并 chmod 0700 —— ADR-0037）
        5. 目标已存在且同内容？ → 删除临时文件（去重命中），复用已有文件
           同一份内容已在归档里（可能在上个月的目录里）、只是叫别的名字？
             → 给它挂一个硬链接（不写字节）
        6. 否则 → 原子改名（同一文件系统内 rename）→ chmod 0400（只读）
        7. 写入索引（原名 / 磁盘上的相对路径 / 会话 / 时间 / 大小 / 哈希 / MIME）
        8. shell.openPath(磁盘上的那个文件)
```

要点：

- **第 5 步是去重的全部实现。** 判据是**内容相同**（先比大小，再比哈希），不是"名字相同"—— 名字只决定它**叫什么**（[ADR-0031](decisions.md#adr-0031)），年月目录只决定它**在哪儿**（[ADR-0037](decisions.md#adr-0037)）。文件名上的差异（`报告.pdf` / `报告 (1).pdf`）仍然不产生新的存储。
- **第 5 步和第 6 步都可能一个字节都不写。** 同内容、同名 → 丢弃临时文件；同内容、不同名 → 挂一个硬链接（因此 `usage()` 的占用统计按 inode 去重）。
- **第 6 步必须是 rename 而非 copy**，否则大文件会出现可见的中间态。临时文件与目标必须在同一文件系统 —— 临时文件始终落在归档**根**，而年月目录是它的下级，因此这一条由构造保证。
- **第 6 步落盘之后立刻 chmod 0400**：归档是内容寻址的，就地改写会让索引里的哈希与内容不再相符。删除与迁移不受影响（只依赖目录的写权限）。
- **第 4 步的年月目录与归档目录一样是 `0700`**：里面同样是解密后的明文，权限不能因为多了一层就漏掉。
- **索引写入失败不应阻止打开文件。** 用户的诉求是打开文件；索引是增强。顺序上先保证可用性。
- **启动时清扫**残留的 `.part-*`（进程被 kill 会留下），并清掉旧版本的 `.open/` 影子目录。清扫只看归档根，不必递归。

## 5. 已知脆弱点与判定方法

上游改版是本项目**必然面对**的现实。要求是：允许失效，不允许静默失效。

| 脆弱点 | 症状 | 判定方法 |
|---|---|---|
| 下载不再经由下载事件（例如改为流式播放 / 分片请求） | 文件不落进归档，也没打开 | 复现后看主进程日志有无下载事件；`scripts/check-capture.ts` |
| 缓存键不再稳定 | 每次点击都联网（回到上游原生行为） | 观察二次点击时是否仍有到媒体 CDN 的请求 |
| 媒体 CDN 换到 `cdn.whatsapp.net` 之外的域 | 二次点击仍联网（只是不再落缓存，不报错） | 同上；`scripts/check-capture.ts` 的 host 断言会先变红 |
| 缓存键发生碰撞 | 解密失败、文件打不开（MAC 校验不过） | 直接看是否复现"打开报错"。⚠️ **不要**再用"同一哈希对应多个名字"判断 —— 那在 [ADR-0031](decisions.md#adr-0031) 之后是正常的（同一份内容被转发） |
| 回放的响应头与原响应语义不一致（漏带 COEP / COOP / CSP 之类） | **只在缓存命中时**出现：页面局部坏掉，例如文档预览报 `ERR_BLOCKED_BY_RESPONSE` | `scripts/check-capture.ts` 的响应头断言；改 `capture/headers.ts` 白名单时**必须**提升 `CACHE_VERSION` 让旧条目失效（[ADR-0016](decisions.md#adr-0016)） |
| 上游把 PDF 换到别的路径 / 别的域交给内置阅读器渲染 | 应用内又出现 PDF 预览（**看得见**，但没人会想到是我们放的） | 观察点 PDF 时是否出现应用内预览；`scripts/check-capture.ts` 的预览页判据断言会先变红 |
| 页面拒绝在内置内核中运行 | 出现"浏览器不受支持" | 检查 UA 设置是否被上游新的检测绕过 |
| 权限策略变化（麦克风 / 摄像头 / 通知） | 通话或通知不可用 | 检查权限白名单是否需扩展 |

**把"接管还活着吗"变成可主动检查的问题**，是 `scripts/check-capture.ts` 存在的唯一目的。它不能替代真实点击，但能确认关键约定未被破坏（缓存键推导、归档写入、打开链路）。

## 6. 边界：这些事不会做

以下事项即使在技术上更容易，也不在范围内：

- 解析页面 DOM 或选择器来识别"用户点了哪个文件"
- 从页面内部数据库读取媒体指针（mediaKey、directPath 等）
- 自行解密或校验 MAC
- 自动收发消息、自动下载未点击的文件（预取只针对密文，且可通过设置关闭）
- 修改请求内容或注入响应

> 上面最后一条有一个**明确划定的例外**：把 `application/pdf` 响应的 `content-type` 降级为
> `application/octet-stream`，好让内核不去渲染它而是下载它（[ADR-0029](decisions.md#adr-0029)）。
> 它一个请求都不动、响应体一个字节不动、更不碰页面的 JS 与 DOM —— 方向只有"让内核不能显示"这一种。
> 除这一处之外，任何改写响应或注入的改动仍然需要先追加 ADR 推翻
> [ADR-0001](decisions.md#adr-0001) / [ADR-0002](decisions.md#adr-0002) / [ADR-0007](decisions.md#adr-0007)。

若要突破其中任何一条，需要先追加 ADR 推翻 ADR-0001 / ADR-0002 / ADR-0007。

## 7. 调试

```bash
# 主进程日志，只看接管相关
waachat 2>&1 | grep -iE 'download|capture|cache|archive' | tail -40

# 归档根下的半成品应为 0（进程被 kill 才会留下；临时文件只落在根）
find "$HOME/Documents/WaaChat_files" -maxdepth 1 -name '.part-*' | wc -l

# 正文应当都是只读（0400）—— 列出来的是"可写的正文"，正常为空。
# 注意**不**加 `-maxdepth 1`：正文在 <年>/<月>/ 里（ADR-0037），少一层就什么都查不到
find "$HOME/Documents/WaaChat_files" -type f ! -name '.*' ! -perm 0400

# 索引与文件是否对得上：stored_name 就是打开文件时用的**相对路径**（ADR-0031 / ADR-0037）
sqlite3 "$HOME/Documents/WaaChat_files/.index.sqlite" 'select stored_name, name from files limit 5'
```

> 归档位置可在设置里改（默认 `~/Documents/WaaChat_files`，见 [ADR-0018](decisions.md#adr-0018) /
> [ADR-0023](decisions.md#adr-0023) / [ADR-0032](decisions.md#adr-0032)），索引就在它的内部。
> 上面的路径要跟着换成实际值。

日志里**不得**出现文件名全文、会话名、完整路径（见 [`security.md`](security.md)）。调试需要时用哈希前缀代替。
