# 界面语言：网页版把它记在哪儿、**谁能写它**，以及能不能不注入地改

> 目标：`wa_web_lang_pref` 这条 cookie 改掉就能换网页版的语言，但它**会被改回来**。在动手之前
> 必须先弄清"是谁改回去的" —— 两种来源的手段完全不同，而且其中一种**没有干净的解法**。
>
> **它是评估，不是决定。** 结论被采纳后写进 `decisions.md` 的 ADR；本文按 `docs/research/` 的约定
> **只增不改**。

---

## 0. 结论摘要

| 问题 | 结论 |
|---|---|
| 今天能不能换内嵌页面的语言？ | **能**，而且**不必重启**：我们在会话层把网页版那条偏好 cookie 按设置固定住，改完重载页面即生效（[ADR-0065](../decisions.md#adr-0065)）。`--lang` 保留作"全新 profile / cookie 被清掉"时的兜底（[ADR-0063](../decisions.md#adr-0063)）。 |
| 那为什么（改动之前）"改了设置、重启多少次还是老语言"？ | 因为页面第一次装载时把语言记进了自己的 cookie `wa_web_lang_pref`，**此后它优先于 `navigator.language`** —— 对已经用过的 profile，只改 `--lang` 永远是无效的（§4.2 实测，两个方向都验过）。 |
| 本文要回答什么？ | `wa_web_lang_pref` 能不能当**第二条杠杆** —— 让语言"运行期可换、且不被服务端改回"。 |
| 它被改回来有几种可能？ | **两种**（§2）：A = 网络响应写的（可拦）；B = 页面脚本写的（拦不住，除非注入）。 |
| 有没有"向上游提交语言变更"这条路？ | **不建议**：那要调上游的私有接口、还要把页面的认证凭据取出来用 —— 撞 `AGENTS.md` 第 5 节最后一条与 [INV-2](../decisions.md#adr-0001) 的立场，且上游改版即静默失效（§5）。 |
| 怎么测？ | 两份只读探针（§3）：页面侧 `__waLangPref`（`test/fixtures/probe-lang-pref.js`）+ 主进程侧 `lang probe:` 日志（`src/main/dev-probe-lang.ts`），外加一次零风险的 `?lang=` 手工测试。 |
| 结果 | **待填**（§4）。 |

## 1. 为什么这件事值得单独研究

[ADR-0060](../decisions.md#adr-0060) / [ADR-0063](../decisions.md#adr-0063) 把"换语言"落在了
**表现得像一个普通浏览器**上（改请求头、改应用 locale），代价是**重启**才生效 —— 因为它要改的是
`navigator.language`（启动期开关）。这是 **INV-1 之下唯一成立的做法**，不是保守。

而 ADR-0063 的"已知限制"里挂着一条**至今未确认**的推测：

> **上游仍可能把语言存进页面存储**：那样它只在**首次装载**时跟随我们。

`wa_web_lang_pref` 这条 cookie 的出现，把这条推测变成了一个**可回答**的问题，而且顺带打开第二条
可能的杠杆：如果它**只由服务端写**，我们就能在会话层拦响应头把它固定住，从而做到"运行期可换"。

**⚠️ 但这条杠杆只在一种情况下存在**（§2 的形态 A）。因此本次研究的目的不是"实现它"，
而是**先定性**：它是 A 还是 B。

---

## 2. 判据：两种"被改回来"

| | 形态 A：网络响应写它 | 形态 B：页面脚本写它 |
|---|---|---|
| 机制 | 响应的 `Set-Cookie`（`webRequest.onHeadersReceived` 能看到） | `document.cookie = …`，或从页面存储读回来再写一次 |
| 我们能拦吗 | **能**：在会话层把那条 `Set-Cookie` 过滤掉，再用 `session.cookies.set()` 种我们的值 | **不能**（在 INV-1 下）。要拦只能注入，而注入是被禁止的那一类 |
| 判据之一 | cookie 带 `HttpOnly`（脚本写不出 HttpOnly） | `document.cookie` 里看得见它 |
| 判据之二 | cookie 变化的 `cause` 不是 `explicit` | `cause` 是 `explicit` |

⚠️ **两条判据都要看，而且必须一起看**：`document.cookie` 里看不见它**不等于**它是 HttpOnly ——
也可能是"此刻还没被写过"（页面刚装载时很常见）。只凭页面侧一条就下结论，会得出一个建立在
错误前提上的改动方案。

⚠️ **形态 B 还有一层**：即使服务端是唯一的直接写入者，页面也可能把它**存进页面存储**、之后从
那里写回（ADR-0063 那条推测说的正是这个）。因此 §3 的页面侧探针要**同时**扫存储。

## 3. 怎么测（全部只读）

### 3.1 页面侧：`__waLangPref`

`test/fixtures/probe-lang-pref.js`，开发模式下由 `src/main/dev-probe.ts` 自动装进承载上游页面的
窗口（**只在未打包时**，与媒体元数据探针走**同一处** `executeJavaScript` 调用点 ——
[INV-1](../decisions.md#adr-0057) 的只读例外每多一处都要在源码里看得见）。

它报三件事：

1. `wa_web_lang_pref` 在 `document.cookie` 里**看不看得见**（可见 ⇒ 不是 HttpOnly；不可见 ⇒ 见 §2 的警告）；
2. 页面存储里有没有**疑似语言键**（localStorage / sessionStorage 的键名与规范化后的值；
   IndexedDB 只列**库名** —— 库里是消息内容，不进去读）；
3. `navigator.language` / `navigator.languages` / `Intl` 的取值，与 `--lang` 对照。

```bash
pnpm run dev        # 未打包时才装；装完自动取一次快照
# Ctrl+Shift+I → Console：
__waLangPref.report()          # 整段复制出来
await __waLangPref.refresh()   # 过一会儿（或改了语言之后）再看一次
```

⚠️ **要看"过一会儿"那一次**：服务端把 cookie 改回来多半发生在一次会话同步或一段空闲之后，
页面刚装载完的那一瞬间看不出任何东西。

### 3.2 主进程侧：`lang probe:` 日志

`src/main/dev-probe-lang.ts` 挂在**会话**上（因此必须在创建窗口**之前**装配 —— 要看到页面
第一次请求的响应头），报两件事：

- `lang probe: a response carries the language cookie` —— 哪一条响应发了这条 `Set-Cookie`，
  以及它带了哪些属性（`httpOnly` / `secure` / `sameSite` / `maxAge` …）。这是**形态 A 的直接证据**；
- `lang probe: cookie changed` —— 每次变化的 `cause`：`explicit` = 页面脚本写的（**形态 B**），
  其它取值 = 网络写回来的（**形态 A**）。

它**只观察**：`callback({})` 放行，一个字节都不改。日志纪律同 `docs/security.md`：cookie 值只有
"看起来就是语言码"才原样打出来，其余只报长度；地址只报 `origin + pathname`。

### 3.3 `?lang=` 那一问（零风险，手工）

上游不少网页应用认 URL 上的 `?lang=`。在**普通浏览器**里打开：

```
https://web.whatsapp.com/?lang=ja-JP
```

不登录、不改任何状态。**若登录页变成日语**，这就是最省事的一条杠杆（无需拦任何东西）；若不变，
这一条排除掉。（页面侧探针会顺手报出当前地址里的参数名与 `lang` 的值。）

## 4. 结果

### 4.1 已测：`--lang` 到 `navigator.language` 的映射（Electron 44.7.0，本仓库钉住的那一版）

做法：一个仓库外的临时探针（`xvfb-run` + 隐藏窗口 + `about:blank`），逐个把
`UI_LANGUAGES[].code` 交给 `app.commandLine.appendSwitch('lang', code)`，读 `app.getLocale()` 与
`navigator.language`。

| `--lang=` | `app.getLocale()` | `navigator.language` |
|---|---|---|
| （不设） | `zh-CN` | `zh-CN` |
| `zh-CN` / `zh-TW` / `en-US` / `en-GB` / `pt-BR` | 原样 | **原样** |
| `es-ES` / `ja-JP` / `tr-TR` / `hi-IN` / `vi-VN` / `th-TH` / `id-ID` / `ko-KR` / `fr-FR` / `de-DE` / `it-IT` / `ru-RU` | 基础码（`es` / `ja` / …） | **基础码** |

**结论**：

1. **机制有效**：表里每一个码都真的改变了 `navigator.language`（`navigator.languages` 的第 0 项），
   没有一个是"设了等于没设"。因此"页面没换语言"**不能**再从这一层解释。
2. **区域变体会被规范化成基础码**：`es-ES` → `es`。因此"请求的值 ≠ 生效的值"是**预期内的**，
   判据必须比**基础语言**（`shared/language.ts` 的 `localeMatchesRequest`），否则每次都会报假警报。
3. **`navigator.languages` 的尾巴仍是系统语言**（`['es','zh-CN','zh-CN','zh','zh']`）——
   与 [ADR-0063](../decisions.md#adr-0063) 的已知限制一致，这一条没有杠杆。
4. ⚠️ **附带补上一条诊断**：`--lang` 若给了一个内核不认的码，它会**静默回落到系统 locale** ——
   设置页照常显示用户选的那一种。因此 `main/index.ts` 的 `ready` 日志现在同时记
   `requestedLanguage` 与 `locale`，两者不同属一门语言时再报一条 warn。

### 4.2 已测：登录页**首次装载跟随 `navigator.language`，但 cookie 存在时 cookie 优先**

做法：**全新 profile**（没有 cookie、没有页面存储）加载 `https://web.whatsapp.com/`，
用清过的 Chrome UA；一组不预置 cookie 只换 `--lang`，另一组把 `wa_web_lang_pref` **预置成与
`--lang` 相反**的语言。都不登录。

| 预置 `wa_web_lang_pref` | `--lang`（`navigator.language`） | `<html lang>` | 登录页文案 |
|---|---|---|---|
| （无） | `zh-CN` | `zh-Hans` | 中文（"扫描登录…"） |
| （无） | `es-ES`（`es`） | `es` | 西班牙语（"Escanea para iniciar sesión…"） |
| （无） | `en-US` | `en` | 英语（"Scan to log in…"） |
| **`zh-CN`** | `es-ES`（`es`） | `zh` | **中文** |
| **`es-ES`** | `zh-CN` | `es` | **西班牙语** |

**结论**：

1. **首次装载确实跟随 `navigator.language`** —— [ADR-0063](../decisions.md#adr-0063) 的机制
   在这一步是对的（所以"全新装的应用能换语言"）。
2. **cookie 一旦存在，它优先于 `navigator.language`**（两个方向都验过）。这就是
   "改了设置、重启多少次都还是原来那种语言"的**完整**解释：页面第一次装载时按当时的
   `navigator.language` 把语言记进了自己那条 cookie，此后 `--lang` 再也影响不到它。
   ⇒ **对已经用过的 profile，`--lang` 这一项实际是无效的**（只是没有任何地方能看出来）。
3. **那条 cookie 不是 `HttpOnly`**：三次运行里页面脚本都能在 `document.cookie` 里读到它
   ⇒ 页面自己**能读也能写**它（§2 的形态 B 在可能性之内，不能只靠"拦响应头"解决）。
4. **会话层种下的同域 cookie 能赢过页面自己那条**（预置实验的两个方向都成立）。也就是说
   "在会话层把这条 cookie 固定成设置里的语言"这条路**存在** —— 而且它有个额外好处：
   它**不需要重启**（改完重载页面即可），正好是"改完自动刷新页面"重新有意义的那条路。
   ⚠️ 但它是一次**新的接管类别**：此前我们只**读**请求与事件，现在要**写**页面看得见的状态。
   按 `AGENTS.md` 第 4 节，必须先有 ADR，且要把 [INV-1](../decisions.md#adr-0057) 的边界重划清楚
   —— **已采纳并落地**：[ADR-0065](../decisions.md#adr-0065)（相邻的 §4.4 就是它要用的那张表）。
5. 预置实验里 `document.cookie` 出现了**两条**同名 cookie（作用域不同：一条 host-only、
   一条更宽），也就是说上游自己也在这条名字上写。这解释了"为什么我们种的能赢"（更具体的作用域
   优先），也提醒：**依赖作用域优先级是脆的** —— 上游换一次写法就翻。
6. 页面存储那几条（§3.1 第 2 项）本组实验没有覆盖：全新 profile 里没有可复用的登录态，
   而未登录页不会去读账号级的偏好。

### 4.3 待测：剩下的两问（需要登录 / 需要真机）

| 观测 | 结果 |
|---|---|
| 服务端会不会用 `Set-Cookie` 把它写回来？（`lang probe:` 那几行） | 待测 |
| cookie 每次变化的 `cause` 是 `explicit`（脚本）还是其它（网络） | 待测 |
| 已登录的 profile 里，页面存储有没有语言键 | 待测 |
| `?lang=ja-JP` 是否改变登录页语言（§3.3，零风险但未跑） | 待测 |
| ⇒ 形态 A 还是 B | 待测（§4.2 第 2/3/5 条已经把 B 的可能性抬高了） |

⚠️ 这两问决定"固定 cookie"那条路**要不要持续重申**：若这条 cookie 只由页面自己写一次，
种一次就够；若服务端每次同步都用 `Set-Cookie` 写回，那就得在变化时重申 —— 而重申就是
**与上游抢这条 cookie**，代价与风险完全不同（要在 ADR 里写清"抢输了会怎样"）。
**在拿到数据之前不要加那个监听**，见 [ADR-0065](../decisions.md#adr-0065) 的已知限制。

### 4.4 已测：`UI_LANGUAGES` 每一项对应的**上游写法**

做法：把每一个语言码当 `--lang` 起一个**全新 profile**，加载登录页，读那条 cookie 的**值**与
**作用域**（`session.cookies.get`）。

| 我们的码 | 上游写法 | | 我们的码 | 上游写法 |
|---|---|---|---|---|
| `zh-CN` | `zh_CN` | | `fr-FR` | `fr_FR` |
| `zh-TW` | `zh_TW` | | `de-DE` | `de_DE` |
| **`en-US`** | **`en_GB`** | | `it-IT` | `it_IT` |
| `en-GB` | `en_GB` | | `ru-RU` | `ru_RU` |
| `ja-JP` | `ja_JP` | | `tr-TR` | `tr_TR` |
| `ko-KR` | `ko_KR` | | `id-ID` | `id_ID` |
| **`es-ES`** | **`es_LA`** | | `vi-VN` | `vi_VN` |
| `pt-BR` | `pt_BR` | | `th-TH` | `th_TH` |
| **`ar`** | **`ar_AR`** | | `hi-IN` | `hi_IN` |

**作用域（每一个都一样）**：`domain=.web.whatsapp.com`（**domain 级**，不是 host-only）、
`path=/`、`secure=true`、`httpOnly=false`、非会话 cookie（约 28 天）。

**结论**：

1. 十五项确实是 `-` → `_` 的机械替换，**三处不是** —— 而且那三处是上游在自己清单里为这种语言
   挑的变体，**推不出来**。因此我们写这条 cookie 时只能用这张表（`shared/language.ts` 的
   `pageCode` 列），并由自检守着"不许自己拼"。
2. 写成上游不认的值**不会报错**，只会"好像没变" —— 与 §4.2 的第 2 条症状一样。
3. 预置实验（§4.2）里我们写的是 `zh-CN` / `es-ES`（带连字符），页面**也认**；但这不足以说明
   "随便写都行"：当时页面自己随后又写了一条（`document.cookie` 里出现两条）。用它的写法写、
   用它的作用域写，才是把不确定性去掉的那一步。

⚠️ 最后第二行是**最有信息量的那一问**：它不需要登录。用两个全新 profile 分别以
`--lang=zh-CN` 与 `--lang=es-ES` 加载 `https://web.whatsapp.com/`，比较登录页文案 ——
- 若两者**不同** ⇒ 页面**首次装载**确实跟随我们，那么"重启后仍是中文"只可能是
  **页面自己的持久化偏好**（cookie / 存储）盖住了它 ⇒ 回头看 §2 的形态 A / B；
- 若两者**相同**（都是中文）⇒ 上游挑语言的根本不是 `navigator.language`，
  [ADR-0063](../decisions.md#adr-0063) 的整个机制要重新评估 —— 那时"重启后生效"这句文案
  在设置页里就是一句**不成立**的承诺。

### 4.5 已测：**登录之后**语言由账号决定 —— 我们那条 cookie 会被改回去

（2026-10-11，Electron 44.7.0 / Chromium 152。这一节回答 §4.3 表里的前两问。）

做法：一个**已登录**的 profile（`~/.config/waachat`），跑 [ADR-0065](../decisions.md#adr-0065)
的实现（会话层按设置固定 `wa_web_lang_pref`），主进程侧 `lang probe:` 全程观察。同一次运行里
改了两次设置，因此 `--lang` 也从 `es-ES` 变成 `en-US`（`ready` 那行：`requestedLanguage: es-ES,
locale: es` —— §4.1 的规范化照常发生，`--lang` 本身是生效的）。

| 时刻 | 谁写的 | cookie 值 |
|---|---|---|
| 11:54:27.244 | **我们**（启动固定，日志里 `previous: zh_CN`） | `es_LA` |
| 11:54:28.475 | （同值重写一次，来源未定） | `es_LA` |
| 11:54:29.414 | **页面** | `zh_CN` |
| 11:54:41.420 | **我们**（改设置，日志里 `previous: zh_CN`） | `en_GB` |
| 11:54:43.969 | （同值重写一次，来源未定） | `en_GB` |
| 11:54:44.544 | **页面** | `zh_CN` |
| 11:54:50.494 | （同值重写一次，来源未定） | `zh_CN` |

另一次运行（11:39，同一个 profile）是同一个形状：cookie 由我们在 `11:39:12` **创建**
（`created` 就是那一刻，而且库里**只有一行**，作用域也对），`11:39:33` 被改成 `zh_CN`，
而它的到期时间是**最后一笔写入 + 28 天** —— 我们写的是 **30 天**
（`LANGUAGE_COOKIE_LIFETIME_SECONDS`）⇒ **最后一笔不是我们写的**。（顺带一条判据：这条 cookie
我们与页面写出来的**属性完全一样** —— `domain=.web.whatsapp.com`、`/`、`secure`、
非 `HttpOnly`、`sameSite=unspecified` —— 因此属性也分不出是谁写的，只有**寿命**与**时机**能。）

**判据一：形态 A 被排除。** 整场运行里 `lang probe: a response carries the language cookie`
**一次都没出现**（0 次）。探针只盯 `https://web.whatsapp.com`，而要给 `.web.whatsapp.com`
种 cookie，响应也只能来自这个域 ⇒ 改回去的是**页面这一侧**（§2 的形态 B）。

**判据二：§2 的"看 `cause`"在 Electron 44 上不可用 —— 这一条要按实测改。**
页面的写入打出来是 `overwrite`（`removed: true`）紧接 `inserted`；而**我们自己**在
`11:54:41.421` 那次 `session.cookies.set()` 打出来的是**同一组** `overwrite` + `inserted`。
整场运行里 `explicit` **一次都没出现**（连页面写的也没有）。⇒ 分不出我们与页面。
唯一可用的判据是"**有没有 `Set-Cookie`**"。

**判据三：页面握着它自己的参照物，而且知道我们改过它。** 页面存储里
（`Partitions/waachat/Local Storage/leveldb`）有两个上游自己的键：

- `WALangPhonePref = "zh_CN"` —— 名字直说了：**手机 / 账号**那一边的语言偏好；
- `WALangPrefDidMismatchWithCookie` —— 这一场运行里被写了**三次**：`true`（我们写 `es_LA` 之后）、
  `false`（页面改回 `zh_CN` 之后）、`true`（我们写 `en_GB` 之后）。

⇒ 页面**主动**比较"我这一门语言"与"cookie 里那一门"，不一致就按自己的改回去。这不是偶发，
是**每装载一次修一次**。

**结论**：

1. 我们那次固定对**登录页**成立（§4.2 仍然对），但**一旦登录**，页面会在约 2–3 秒内把 cookie
   改回**账号语言**并按它渲染 —— 用户看到的是"闪一下目标语言，然后变回去"。
2. ⇒ [ADR-0065](../decisions.md#adr-0065) 承诺的"改完点「重新载入页面」即生效"**对已登录的
   账号不成立**；它那条"已知限制 #2"（上游会写回来）被证实，而且比他写的更糟：不是偶尔，
   是每次装载都修。⚠️ §0 结论摘要里"**能**，而且不必重启"那一行因此只对**未登录**的页面成立；
   按本文"只增不改"的约定，§0 原文保留，**以本节为准**。
3. 真源是**账号**（`WALangPhonePref`，来自手机 / 服务端的同步），**不是** `navigator.language`
   —— 实测那一场 `--lang=es-ES` 是生效的（`locale: es`），页面照样用中文渲染。因此"把语言换成
   别的"这件事**不在我们这一层**：只能在账号那一边改。
4. §5 那条"不停写回去"的否决理由因此又硬了一层：抢不到**可见**的结果（渲染跟页面的参照物走），
   只会把那条 cookie 变成拉锯场；而 `WALangPrefDidMismatchWithCookie` 的存在说明上游自己就在
   **检测**这种不一致（它已经有了一整套"参照物 vs cookie"的逻辑，我们不是唯一想动它的人）。
5. §4.2 第 6 条那个悬空的"本组实验没有覆盖"现在有答案了：**账号级的偏好确实会被页面读**，
   而且它就是这条语言的真源。

## 5. 被否决的替代方案

- **调上游的私有接口去"提交语言变更"**：那等于自己实现一段上游协议。要做就得从页面里取出认证
  凭据、在外面重发请求 —— 撞 `AGENTS.md` 第 5 节最后一条（接管逻辑只允许依赖**标准内核行为**）
  与 [INV-2](../decisions.md#adr-0001) 的立场，且上游改版即**静默失效**。**除非**上游自己在网页版
  里提供语言开关（或认 `?lang=`，见 §3.3）—— 那就走它，我们一个字都不用碰。
- **注入脚本去点页面里的语言菜单**：违反 [INV-1](../decisions.md#adr-0057)，且依赖上游 DOM。
- **清掉页面存储让它重新挑一次语言**：连登录态一起清（[ADR-0008](../decisions.md#adr-0008) 的立场：
  绝不代用户清除）。
- **靠"不停把 cookie 改回去"（`cookies.on('changed')` + 立刻 `set()`）**：看着能赢，实际会与上游
  自己的语言选择器**打架**（用户主动改也被秒改回来），而且有竞态。**形态 B 下它同样无效。**

---

## 6. 与既有决定的关系

- 本文**不动** [ADR-0063](../decisions.md#adr-0063) 的结论：`--lang` 仍是启动期那一半，
  "重启后生效"不变。本文要回答的是**要不要再加一条运行期的杠杆**，以及在 INV-1 之下它是否存在。
- 若结论是**形态 A 且值得做**：那是一次**新的接管**（此前我们只**读**请求，没有**改**响应），
  按 `AGENTS.md` 第 4 节必须先追加一条 ADR，再动手。
- 若结论是**形态 B**：这件事到此为止 —— 在 INV-1 之下没有干净的解法，把它写进 ADR-0063 的
  "已知限制"就够了（那正是 §1 引的那条推测的归宿）。

## 7. 收官（[ADR-0066](../decisions.md#adr-0066)）

§4.5 之后这条线走到了终点：**在 WaaChat 这一层没有干净的做法**。三轮尝试（改请求头 → 改启动参数 →
写页面那条 cookie）已经把可行域摸完，而 §4.5 实测证明最后一条也会在几秒内被页面按**账号语言**改回去。
因此 [ADR-0066](../decisions.md#adr-0066) 把「界面语言」这一项**整个撤掉**：

- 设置页只留一句**说明**：「内嵌页面的语言由你的手机版 WhatsApp 决定 —— 请到手机里改」（把真源与
  入口直接告诉用户，而不是留一个按不动的开关）；
- 删掉会话层写 `wa_web_lang_pref` 的整条路（`pinLanguageCookie()` 等），**INV-1 的写入例外随之退休**；
- `--lang` 不再设置；`RELOAD_REQUIRED_SETTINGS` 与「重新载入页面」那条路一并删除。

本文按"只增不改"的约定保留全部原文。⚠️ §0 结论摘要里"**能**，而且不必重启"那一行只对**未登录**的
页面成立，**以 §4.5 为准**（§4.5 早已写明）；§5 的否决理由至此全部落地为代码 —— 探针（§3.2）保留，
它**只读**，是我们看清上游何时改版的眼睛。
