# 早期文件身份：从"点击"到"Blob"的流程，以及能不能用它跳过下载与哈希

> 目标：弄清楚**在流程的哪一刻、我们能拿到一个能唯一标识文件内容的值**，从而在再次遇到同一文件时
> 跳过完整下载与哈希计算。
>
> **它是评估，不是决定。** 结论被采纳后写进 `decisions.md` 的 ADR；本文按 `docs/research/` 的约定
> **只增不改**。

---

## 0. 结论摘要

| 问题 | 结论 |
|---|---|
| 现在有没有 `whatsapp-web.js` 依赖可以"移除"？ | **没有。** 它从未被加入依赖（`package.json` 与 `node_modules` 里都没有）。它只存在于 [ADR-0043](../decisions.md#adr-0043) / [ADR-0044](../decisions.md#adr-0044) 的**决策**里 —— 所以"移除"实际是**推翻那两条决策**（见 §8）。 |
| "早期唯一标识"拿得到吗？ | **有一个干净的首选候选**：`fileSha256` —— **明文**的 SHA-256，是**消息里的字段**，下载前就有。它**恰好等于**归档索引里的 `hash`。 |
| 能跳过完整下载吗？ | **只有走页面内部读取才可能**（点击那一刻）。纯内核/网络层做不到"跳过下载"，最多省掉哈希计算。 |
| 会撞上 INV-3 吗？ | 用 `fileSha256` **不会**（它不是密钥派生的）。但如果客户端侧只暴露 `filehash`（HMAC，key 派生），**会** —— 这是必须先探明的岔路口。 |
| 需要新的 ADR 吗？ | 读页面内部数据不需要（INV-1 已撤销）；**推翻承载方式的决策需要**（§8）。 |

## 1. 完整流程：从点击到 Blob

| # | 步骤 | 发生在哪 | 我们能不能看到 |
|---|---|---|---|
| 1 | 用户点击消息里的文件 → 页面调用自己的 Msg 模型 | 页面 | 需要注入/调试协议（今天看不到） |
| 2 | 由 `directPath` + 签名参数拼出 CDN URL | 页面 | **能看到 URL**（H2） |
| 3 | 取密文：`fetch` / XHR（可能经 ServiceWorker） | 页面 → 网络 | **能看到请求与响应体**（H2） |
| 4 | 解密：HKDF 派生 + AES-CBC（**上游代码**） | 页面 | 看不到（也不该看） |
| 5 | 校验：`HMAC(macKey)` 与 `fileEncSha256`（密文）/ `fileSha256`（明文） | 页面 | 看不到 |
| 6 | 构造 `Blob`，放进页面的内存 blob 缓存 | 页面 | 看不到 |
| 7 | `URL.createObjectURL(blob)` → `blob:` URL | 页面 | 看不到（URL 不透明） |
| 8a | 预览：交给 `<img>` / `<video>` / 文档预览 iframe | 页面 | 不落盘，**与我们无关** |
| 8b | 下载：`<a download>` → 内核下载管理器 → `will-download` | 内核 | **能看到**（H3，即今天的接管点 A） |

两个关键事实：

- **明文 Blob 在第 6 步才存在**；而"能唯一标识内容的那个值"在第 1 步就可用（前提是它存在，见 §3）。
  这就是"早期"的全部意义。
- **H3 拿到的 URL 是不透明的 `blob:`**（见 `src/main/capture/download.ts` 顶部注释与
  `docs/media-capture.md` §2）。所以在 `will-download` 里**无法**从 URL 反推文件身份 —— 这是今天
  "每次都必须完整下载并算哈希"的根本原因。

## 2. 可以挂钩的三个位置

| 挂钩点 | 位置 | 能拿到什么 | 时机 | 能省掉什么 |
|---|---|---|---|---|
| **H1** 点击时刻 | 页面内部（注入 / 调试协议） | 该消息的媒体元数据（字段清单见 §3） | **最早**（下载之前） | 下载 + 解密 + 哈希 + 落盘（**全部**） |
| **H2** 会话协议层 | 内核 `session.protocol.handle('https')`（已有：[ADR-0015](../decisions.md#adr-0015) / [ADR-0016](../decisions.md#adr-0016)） | 请求 URL、响应（密文） | 下载前 | 网络（已实现）；**配合持久化的 URL→hash 映射可省掉哈希** |
| **H3** 下载事件 | 内核 `will-download`（已有：[ADR-0031](../decisions.md#adr-0031) / [ADR-0037](../decisions.md#adr-0037)） | 文件名、MIME、大小、**字节流**、最终状态 | 下载中/后 | 省不掉下载与哈希；URL 是 `blob:`，无法反推身份 |

**推论**：想达到"**跳过完整下载**"，只有 H1 一条路。H2 只能达到"省掉哈希计算"。

## 3. 早期唯一标识的候选与取舍（本文的核心）

| # | 候选 | 来源 | 是否密钥派生 | 与归档 `hash` 的关系 | 能跳过下载 | 判定 |
|---|---|---|---|---|---|---|
| 1 | **`fileSha256`** | 消息字段（明文的 SHA-256） | **否** | **就是同一个值** | 能 | ✅ **首选** |
| 2 | `fileEncSha256` | 消息字段（密文的 SHA-256） | 否 | 不同构（归档里是明文哈希） | 能 | ⚠️ 只能当二级键 |
| 3 | 页面模型里的 `filehash` | 页面对密文做的 HMAC，`macKey` 由 mediaKey 经 HKDF 派生 | **是** | 不同 | 能 | ✗ **与 INV-3 冲突** |
| 4 | `directPath` / URL pathname | 消息 / 请求 | 否（但每次上传不同） | 无 | 能 | ⚠️ 只是"对象 id"，需持久化 URL→hash 映射 |
| 5 | 消息 id（`_serialized`） | 页面模型 | 否 | 无 | 能 | ✗ 同一文件转发到两个会话 = 两个 id ⇒ 漏命中 |
| 6 | `objectId` | 页面模型 | 否 | 无 | 能 | ⚠️ 同 4 |

**证据基础**（wire 层，可核对）：

- `fileSha256` 是**明文**的 SHA-256。依据：`whatsmeow` 的下载实现里，解密**之后**才用它校验 ——
  `else if (len(fileSHA256) != 32 || sha256.Sum256(data) != *(*[32]byte)(fileSHA256))`，
  此时的 `data` 已经过 `Decrypt`。
- `fileEncSha256` 是**密文**的 SHA-256：`if sha256.Sum256(data) != *(*[32]byte)(checksum)`，
  这里的 `data` 含末尾 MAC，是下载到的密文。
- 两者都是 `ImageMessage` / `VideoMessage` / `AudioMessage` / `DocumentMessage` / `StickerMessage`
  的**消息字段**，因此接收方在下载前就持有。
- 候选 3 是密钥派生的：`macKey` 来自 `hkdf.SHA256(mediaKey, nil, appInfo, 112)` 的后 32 字节
  （`getMediaKeys`）。

**所以这条路线的成败，只取决于一个可验证的问题**：WA Web 的**客户端侧**媒体模型，有没有把
`fileSha256` 留在手里？（wire 层有 ≠ 客户端模型暴露。）

## 4. 先做探针（缺一不可）

⚠️ 探针**只读元数据**：只列字段名与长度/类型，**不读 `mediaKey`、不做任何解密、不发请求**。

> **探针本体：[`../../test/fixtures/probe-media-metadata.js`](../../test/fixtures/probe-media-metadata.js)。**
> 它必须自包含才能粘贴，所以放在 `test/fixtures/` 而不是 `src/`（它的宿主是浏览器）。
> 用法：`pnpm run dev` → 聊天窗口 `Ctrl+Shift+I` → Console → 粘贴整个文件。
> 两条关键性质 ——「绝不打印值」与「必须走原型链上的 getter」—— 由
> [`../../test/unit/probe-media-metadata.test.ts`](../../test/unit/probe-media-metadata.test.ts)
> 常驻守着。

**P1 — 客户端模型有没有这些字段。** 在一条含媒体的消息上，于页面上下文里枚举媒体对象的键名：

```js
// 只列键名，不取值（避免把密钥读进内存）
Object.keys(msg.mediaData ?? msg.mediaObject ?? {})
```

- 判定：出现 `fileSha256`（或同名等价物）→ 走**方案 B**（可跳过下载）。
- 只出现 `filehash` → 走**方案 A**，或必须先就 INV-3 立一条 ADR（§8）。

**P2 — 它标识的是"内容"还是"对象"。** 把同一份文件在**两个不同会话**里各发一次，比较取值。
内容型 ⇒ 相同；对象型 ⇒ 不同。这一步决定它能不能当去重键。

**P3 — 转发/改名。** 同一文件转发后文件名会变（`报告.pdf` → `报告 (1).pdf` 之类）。确认键不受文件名影响。

**P4 — 四类媒体都要覆盖**：图片 / 视频 / 文档 / 语音（外加贴纸）。wire 层五类都有 `fileSha256`，
客户端侧逐类复查。

## 5. 实现思路

### 方案 B（首选）：点击即查，命中就短路

```
点击 → 读该消息的媒体元数据（只读 {sha256, size, mime, name}）
      → archiveStore().byHash(sha256)
         ├─ 命中且磁盘文件在 → shell.openPath(已有文件) + 让这次下载作废
         └─ 未命中 → 走今天既有路径（will-download → 归档）
                     并且：把 sha256 直接当内容哈希用（省掉一次全量 SHA-256）
```

四个组件：

1. **只读探针桥**（页面侧）：回答"当前这条消息的媒体元数据是什么"。
2. **命中判定**（主进程）：`byHash(hash)` + `existsSync(archiveFilePath(...))` —— 这两个函数今天就有。
3. **短路动作**：打开本地文件，并作废这次下载（见 §7 第 11 条：**先让下载正常结束再丢弃临时文件**，
   比抢着 `cancel()` 安全）。
4. **回退**：任何不确定（字段缺失、映射缺失、大小不符）一律走完整路径。

### 方案 A（次优，不需要注入）：URL → 内容哈希 的持久化映射

在 H2（`protocol.handle`）里拿到 URL，查一张 `early_key → hash` 的持久化映射；写这张表的时机是
**H3 落盘完成时**（那时我们知道 URL 与最终哈希的对应）。

- 能省掉：**一次全量 SHA-256**（改查表）。
- 省不掉：下载（页面仍要取字节、解密、构造 Blob、触发 `will-download`）。
- 必须保留校验：命中映射时仍应比对大小；错命中会导致"索引里记着错误的哈希"，比多算一次哈希严重得多。

## 7. 潜在限制与注意事项

1. **"点击关联"是这条路线最脆的一环。** 把"用户点了哪条消息"与"这次下载"绑起来，必须依赖页面的
   DOM / 内部事件 → 上游改版即失效，与 `docs/media-capture.md` §5 那张脆弱点表同类。
   要求照旧：**允许失效，不允许静默失效**。
2. **短路会改变用户可见行为。** 今天"点击 → 落盘 + 打开"；短路后"点击 → 直接打开已有文件"，
   **不再产生新归档条目、不更新 `opened_at`、不新增文件名**。这是行为变更，必须写进 `usage.md`，
   否则会被当成 bug。
3. **信任 `fileSha256` 的代价。** 它由发送方/服务方提供。不再本地校验就意味着**信任对方声明**。
   建议：短路时信任、但至少比一次大小；或对"首次归档"保留一次真实哈希校验。
4. **INV-3 的红线要划在"字段"上。** 允许 `fileSha256`；`mediaData.filehash` 与 `mediaKey` 仍在禁列 ——
   现有的 `cryptoGuards`（`eslint.config.mjs`，作用于 `src/**`）已经会拦 `mediaKey` / `filehash`
   这两个标识符。**新代码必须避开它们**，否则 lint 直接红。这是好事：说明守卫在工作。
5. **必须能处理"拿不到"**：客户端侧不暴露 / 媒体未加密（`mediaKey == nil`）/ 旧消息与部分转发消息
   缺字段 —— 三种情况都要无条件回退。
6. **`fileEncSha256` 不能当主键**：它是密文哈希，与归档里的明文哈希不同构。
7. **URL 派生键的三个既有前提照旧适用**（`docs/media-capture.md` §3）：pathname 唯一性必须**实测**；
   宁可漏命中，不可错命中；缓存上限必须存在。
8. **ServiceWorker 与分片**：媒体请求是否可能绕过 `protocol.handle`、视频是否走 Range 分片，都要实测。
   （今天的密文缓存依赖 H2 能拦到，说明主路径可拦；但视频分片本来就不进缓存。）
9. **预览路径与我们无关。** 图片/视频的**预览**不落盘，因此短路对它没有意义（本来也没参与）；
   短路只对"会落盘"的那条路径有意义 —— 而那条路径今天就有一次全量落盘。
10. **对视频/大文件收益最大，也最容易踩分片问题** —— 这正是最需要它的场景，优先级要分开评估。
11. **不要为了短路而抢着 `cancel()`。** `item.cancel()` 与"是否已写了字节"的时序必须实测；
    更安全的做法是**让下载照常完成，然后丢弃临时文件**，只在确定命中时才取消。
12. **日志纪律不变**：`fileSha256` 是哈希，可以进日志；**文件名、会话名、完整路径仍然禁入日志**
    （`docs/security.md`）。

## 8. 与现有 ADR 的关系（必须一起处理）

| 约束 / 决策 | 本方案的影响 |
|---|---|
| **INV-1**（已由 ADR-0043 撤销） | 读页面内部数据**不需要新 ADR** —— 但它今天是"撤销后没人用"，本方案是**第一次真正用它**，应在新 ADR 里把"只读元数据"这条纪律写下来 |
| **INV-2**（已由 ADR-0043 撤销） | 本方案**不使用**协议库：协议与解密仍由页面承担。因此"不重实现协议"这条**实践**不变 |
| **INV-3**（未撤销） | 用 `fileSha256` **不需要**动它。**唯一**需要放宽的情形是 P1 表明客户端侧只有 `filehash` |

| **ADR-0044**（承载方式：独立 Chromium） | **与自建客户端冲突**：自建客户端要么回到"Electron 承载网页版"，要么自己拉起一个 Chromium 并注入。**需要一条新 ADR 取代它** |
| **ADR-0045**（INV-3 加固） | 继续有效，且是本方案的安全网 |

`whatsapp-web.js` 从未进入 `package.json`，所以**没有要执行的依赖移除动作**；要动的是决策文档。

## 9. 一句话总结

"跳过下载"这件事的唯一钥匙是**下载之前就知道内容哈希**；而同时满足"下载前可得 + 与归档键同构 +
不碰密钥"的字段只有一个：`fileSha256`（明文哈希）。它不在网络层，只在页面内部 —— 所以这条路线的
成败，取决于一个**今天就能验证**的问题：**WA Web 的客户端模型，有没有把它留在手里。**

## 10. 实测结论（2026-10-10）：钥匙就是 `filehash`，它就是明文 SHA-256

> 本节是**追加**（本文件只增不改）。它**推翻 §3 候选 3** 的判定，也**取代**本文件第 8 节
> "P1 表明客户端只有 `filehash` 家族 ⇒ 必须先就 INV-3 表态"这条推论。采纳后的决定见
> [`decisions.md` ADR-0047](../decisions.md#adr-0047)。

**怎么测的**：开发模式启动应用（`--remoteDebuggingPort`），用 CDP 在**真实已登录的会话**里求值；
把页面上每条媒体消息的候选字段读出来，再和**磁盘上已归档文件**的明文 SHA-256 直接比对。

| 观测 | 结果 |
|---|---|
| 样本 | 252 条消息，其中 **26 条带媒体**（image 15 / video 2 / interactive 3 / ptt 1 / document 5） |
| `filehash` | **26/26 存在**，26 个**互不相同**，全部 44 字符 = **base64 的 32 字节** |
| `fileSha256` / `fileEncSha256` | **一处都没有**（与 §3 之前的 P1 一致） |
| `encFilehash` | 26/26 存在，与明文哈希**零命中** ⇒ 它是**密文**那一侧 |
| 与归档对账（决定性一步） | `sha256("DZ2602 freight cost.xlsx")` = `b13369b9…b77` → base64 `sTNpud/Ewu06s8xShz+epGdyp1QxJrPAPuEGJBoZi3c=`，与页面 `msg.filehash` **逐字节相同**；`INVOICE SELLADO.pdf` 同理（`JDaBgl0…9M=`） |

**所以**：

1. **`filehash` = 文件内容的明文 SHA-256**（base64）。**不是** §3 候选 3 说的"对密文做的 HMAC"。
   归档索引里的 `hash` 就是这个值的 hex 形式 —— 只需一次 base64→hex。
2. **它在点击之前就在模型上**：这 26 条媒体一条都没点过，字段已经在了。
3. **因此它不撞 INV-3**：我们完全可以自己对同一份明文算出同样的值（归档里的 `hash` 就是这么来的），
   读它既不解析密钥、也不实现解密。

**顺带实测掉的两个"看似可行"的做法**（真机数据）：

- **消息 ID**：`msg.id` 是 `{fromMe, remote, id, $1}`，**`_serialized` 在客户端模型上是 `undefined`**
  （那是 `whatsapp-web.js` 自己拼的）；而且 msgId 是"消息"身份，同一文件转发到别的会话就是另一条消息
  ⇒ 必然漏命中（§3 候选 5）。
- **DOM / React Fiber 选择器**：当前页面上 `.message-in` / `.message-out` 命中 **0** 个，
  `[data-icon="download"]` / `[data-testid="btn-download"]` 也是 **0** 个。

**仍然成立的限制**：`filehash` 由对端/服务方给出（§7 第 3 条）——命中时至少比一次大小，
**绝不用它直接写索引**；图片/视频在客户端模型里**没有文件名**（实测 5/5 文档有、15/15 图片无），
所以"按文件名 + 字节数"的关联主要覆盖会带文件名的媒体。
