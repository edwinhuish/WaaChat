# 路线图

用**可验证的验收标准**描述每个阶段，而不是用功能清单。一个阶段没达成验收标准就不算完成。

优先级顺序来自 [ADR-0001](decisions.md#adr-0001)：先保证"点击即开"（接管点 A），再做"零网络"（接管点 B）。

> ⚠️ **阶段划分所依据的 [ADR-0001](decisions.md#adr-0001) 已由 [ADR-0043](decisions.md#adr-0043) 取代。**
> 因此下表里"接管点 A / 接管点 B"这两个里程碑**不再是**项目的实现路径。它们保留在此作为历史记录与
> 已验收事实的索引；新的阶段划分要等集成设计落地后另行补充，本文不预写。

## M0 · 仓库骨架与打包链路

**目标**：在没有任何接管功能的情况下，能产出一个**装得上、图标正确、沙箱可用**的空壳。

**验收标准**

- [x] `pnpm run check` 通过（lint + 格式 + 类型检查 + 单测 + 离线接管自检）
- [x] `pnpm run verify` 通过，并在干净容器里：
  - [x] `sudo apt install ./dist/*.deb` 成功，应用能启动
  - [x] `./dist/*.AppImage` 在**未安装 libfuse2** 的系统上直接运行
  - [x] 应用图标出现在应用菜单且**不是**通用占位图标
  - [x] 已固定的启动器图标与运行中的窗口**合并为一个**（不是两个）
- [x] 扫码能链接设备，能看到会话列表
- [x] 打 `v*` 标签后 GitHub Release 自动产出 deb + AppImage + `SHA256SUMS.txt`

**状态**：✅ 已实现（2026-10-10 记录）。验收方式逐条留痕，免得下次只剩一个勾：

- **两条命令级验收**：`pnpm run check` 在本机通过；`pnpm run verify`（构建 deb + AppImage 并实际
  解包断言）在 CI 的干净容器里通过 —— 最近三次 `ci.yml` 都是 success。
- **发布链路**：`v1.0.0`–`v1.0.3` 四个 `v*` 标签由 `release.yml` 自动发布；`v1.0.3` 的 Release 里
  带着 `waachat_1.0.3_amd64.deb`、`WaaChat-1.0.3.AppImage` 与 `SHA256SUMS.txt`。
- **安装与运行**：本机装的是 `waachat 1.0.3`（deb），日常都在用它（扫码登录、归档、密文缓存
  都跑在这上面）。
- **哪些是自动断言的**：`scripts/verify-package.sh` 覆盖的是"包层面就能看出错"的那几件 ——
  `.desktop` 条目文件名必须等于 `app_id`（GNOME 按它找同名文件，找不到就显示通用占位图标）、
  `StartupWMClass` 必须等于 `app_id`（不一致则 Dock 显示占位图标、启动器与窗口不合并）、
  AppImage 不依赖 libfuse2、deb 里 apparmor profile 与带 setuid 的 `chrome-sandbox` 都在。
  装完之后**肉眼**才能确认的那两件（菜单里显示的确实是我们的图标、任务栏合并为一个）由人工看过；
  自动化只能保证"包里的东西是对的"—— [ADR-0020](decisions.md#adr-0020) 把这条说得很直白：
  身份标识漏对齐一处的症状就是"构建全绿、运行时静默失效"，而它只有 `pnpm run verify` 抓得到
  （图标的三个落点见 [ADR-0023](decisions.md#adr-0023)）。

**为什么先做这个**：桌面集成的坑（`StartupWMClass`、沙箱、FUSE）与业务逻辑无关，但它们的症状会被误认为是业务 bug。先把地基验好。

## M1 · 接管点 A：点击即开

**目标**：核心需求达成。**这是项目成立的标志。**

**验收标准**

- [ ] 在聊天里点击一个 PDF，系统默认阅读器**直接弹出**，无需任何手动步骤
  > ⚠️ 这一条在**只能观察内核事件**的前提下做不到（当时给出的理由是 **[INV-1](../ai/INVARIANTS.md)**，
  > 该约束已由 [ADR-0043](decisions.md#adr-0043) 撤销 —— 但结论本身仍然成立），理由与实测见
  > [ADR-0029](decisions.md#adr-0029)：PDF 的明文只存在于页面内存里（端到端加密，页面解密后做成 `blob:`），
  > 我们既拦不到那个 `blob:`，也关不掉内核内置阅读器。
  > 已经做到的是"打开**禁用 PDF 预览**之后，应用内不再出现 PDF 预览 + PDF 一律走下载 → 系统阅读器"
  > （[ADR-0030](decisions.md#adr-0030)）——触发下载的那一下得由上游自己的下载入口完成，所以这一条
  > 按原样保留为**未达成**，而不是改成一句看起来完成了的话。
- [ ] `~/Downloads` 中**没有**出现该文件
- [ ] 归档目录里出现该文件，且索引中有记录
- [ ] 同一个文件转发到另一个会话后再点击：归档目录中**文件数不增加**（哈希命中）
- [ ] 首次点击到文件打开的耗时在合理范围内（不应出现"先下载完再等"的观感割裂）
- [ ] 接管失效时（人为构造）**有明确提示**，而不是静默退回原生下载
- [ ] 索引中"有记录"的文件在磁盘上**全部存在**（无悬空记录）

**说明**：此时二次打开仍会联网（接管点 B 未做），这是已知且可接受的。

## M2 · 归档层

**目标**：归档从"能存"变成"能用"。

**验收标准**

- [ ] 「文件列表」窗口可按文件名搜索（FTS5），能定位到较早前打开的文件
- [ ] 搜索结果能一键交给系统应用打开
- [ ] 支持批量导出到用户指定目录（正文已经是原文名，导出就是复制 —— 见 [ADR-0031](decisions.md#adr-0031)）
- [x] 设置了大小上限后，超限淘汰按最久未访问优先删**内容**（全部磁盘名 + 同一次操作里的索引记录），**不留悬空记录**，且不碰索引不认识的文件（[ADR-0048](decisions.md#adr-0048)）
- [ ] 单测覆盖：内容寻址、去重、淘汰边界、FTS 查询

## M3 · 接管点 B：二次打开零网络

**目标**：消灭"每次点击都重新下载"。

**验收标准**

- [ ] 第二次点击同一个文件后，**断开网络**再点击仍能打开
- [ ] 二次点击期间无新的 CDN 请求（可用抓包或连接观察验证）
- [ ] 缓存上限生效，超限时**退化为直通**而不是报错
- [ ] 缓存键的稳定性在**三种媒体类型**（图片 / 视频 / 文档）上分别实测通过
- [ ] 关闭此功能的开关存在，关闭后行为与 M1 完全一致

**这一步最容易出错**，风险与判定方法见 [`media-capture.md`](media-capture.md) 第 3、5 节。

**"缓存上限生效"这一条**现状与实现要点（免得每次都要重新查一遍）：

- **现状**：`Settings.cacheMaxBytes` 与 `LIMITS.cacheBytes` 都**没有任何读者**；`capture/protocol.ts`
  的拦截器只做"命中回放 / 未命中落盘"，落盘不看总量；`reconcileCiphertextCache()` 的判据是
  那个开关（关闭→清空、开启→只清驻留），与容量无关。也就是说**整个容量控制不存在**，
  界面上那句"尚未生效"是如实的（文案由 `shared/size-limit.ts` 按当前值算出来）。
- **缺"最后访问时间"**：条目元信息只有 `storedAt`（写入时刻）。要做"最久未使用优先淘汰"，
  先得在**命中时留痕**（更新 `mtime` 或写回 meta）—— 这是读路径上的写放大，策略要先定。
- **没有总量统计**：`usage()` 只算归档；`ArchiveStats.cacheBytes` 在 `archive/store.ts` 里是
  **写死的 0**，而且界面上从未显示（文件列表窗口的页脚只写"N 个文件，占用 X"）。实现淘汰
  等于同时要把"现在占了多少"做出来 —— 否则用户没有判断依据，也没法验证淘汰是否生效。
- **必须与"退化为直通"一起做**（`media-capture.md` 第 3 节把它列为前提）：超限时不能报错、
  不能把请求卡住，否则症状会从"占磁盘"变成"文件打不开"。
- 归档那一侧的淘汰**已经落地**（[ADR-0048](decisions.md#adr-0048)）：`archive/store.ts` 的
  `enforceLimit()` 把 `blobs.evictToFit()` 与 `deleteByHashes()` 收在**同一次调用**里 ——
  分开做会留下"搜得到但打不开"的悬空记录。缓存这一侧要实现时，照抄的正是这个形状
  （以及"只删索引认识的东西"这条边界）。

## M4 · 打磨与扩展

**目标**：从"能用"到"愿意日常用"。

**候选内容**（按预期价值排序，未承诺）

- 后台预取文档（可开关，按网络环境自动判断）
- 多账号（每账号独立分区与归档）
- arm64 构建（`ubuntu-24.04-arm` runner）
- AUR 包
- 归档的**按会话**浏览（需要先解决元信息来源的问题，见 `architecture.md` 第 7 节）。
  **按时间**那一半已经落地：正文按归档时刻分层到 `<账号>/files/2026-10/`（[ADR-0039](decisions.md#adr-0039)，
  月份是单层 `2026-10`；[ADR-0037](decisions.md#adr-0037) 的 `<年>/<月>/` 是它取代的上一版）——
  层次里只有**账号与月份**，会话维度不在其中，因为会话标签本就不可靠。
- 自定义打开规则（按扩展名指定应用，绕过系统 MIME 关联）

## 明确不做

以下不在路线图内，且不是"暂时没排期"：

| 不做 | 理由 |
|---|---|
| 消息内容归档 / 导出聊天记录 | 需要读取页面内部数据库，违反 [INV-1](../ai/INVARIANTS.md) |
| 免扫码登录 / 凭据迁移 | 属于账号安全敏感地带，且会引入新的凭据管理风险 |
| 通话功能增强 | 上游提供什么就是什么（[ADR-0001](decisions.md#adr-0001)） |
| 自动收发消息、机器人、群发 | 行为特征是被限制的主要触发因素，见 [`DISCLAIMER.md`](../DISCLAIMER.md) |
| Windows / macOS 版本 | 目标平台是 Linux；其他平台各有官方客户端 |
| 移动端 | 同上 |
