# 路线图

用**可验证的验收标准**描述每个阶段，而不是用功能清单。一个阶段没达成验收标准就不算完成。

优先级顺序来自 [ADR-0001](decisions.md#adr-0001)：先保证"点击即开"（接管点 A），再做"零网络"（接管点 B）。

> 阶段划分依据 [ADR-0001](decisions.md#adr-0001)（"Chromium 内核壳 + 内核层接管"）：它曾被
> [ADR-0043](decisions.md#adr-0043) 取代，现已由 [ADR-0057](decisions.md#adr-0057) 恢复 ——
> 下表里"接管点 A / 接管点 B"因此**仍是**项目的实现路径。

## 状态总览

| 阶段 | 内容 | 状态 |
|---|---|---|
| M0 | 仓库骨架与打包链路 | ✅ 已实现（逐条留痕） |
| M1 | 接管点 A：点击即开 | 🟡 代码已实现（「PDF 预览」一条例外，见该节）；未逐条留痕 |
| M2 | 归档层：去重、搜索、淘汰 | 🟡 代码已实现（缺「批量导出」，见该节）；未逐条留痕 |
| M3 | 接管点 B：二次打开零网络 | 🟡 代码已实现（缓存、开关、容量控制）；端到端验收未做 |
| M4 | 打磨：预取、多账号、渠道扩展 | 🟡 部分落地：「多账号」已实现（[ADR-0062](decisions.md#adr-0062)）；预取与渠道扩展未开始 |

> **符号的含义**（这三档不是"完成度百分比"）：
>
> - **✅** = 验收标准**逐条留痕**：像 M0 那样写下"怎么验的、谁验的、证据在哪"。
> - **🟡** = **代码已实现**，有单测、自检或 ADR 里的实测记录支持，但**没有**逐条验收留痕。
>   各节里未勾选的验收标准请按原样读 —— 它们大多属于"要真人点一次才知道"的那一类
>   （耗时观感、断网仍能打开、三种媒体类型分别实测）。
> - **⬜** = 未开始。
>
> 勾选只发生在**有人真的验过、并留下证据**之后。宁可留一个空的勾，也不改一句"看起来完成了"
> 的话 —— 这是 [ADR-0029](decisions.md#adr-0029) 把"点 PDF 直接弹出系统阅读器"按原样留成
> **未达成**的同一条纪律。把三行的状态从"未开始"改掉，是因为那与事实相反：这三块的主体
> 代码今天都在跑（M0 那节记录的那次安装、扫码、归档、缓存，用的就是它）。

## M0 · 仓库骨架与打包链路

**目标**：在没有任何接管功能的情况下，能产出一个**装得上、图标正确、沙箱可用**的空壳。

**验收标准**

- [x] `pnpm run check` 通过（lint + 格式 + 类型检查 + 单测 + 离线接管自检）
- [x] `pnpm run verify` 通过，并在干净容器里：
  - [x] `sudo apt install ./dist/*.deb` 成功，应用能启动
  - [x] `./dist/*.AppImage` 在**未安装 libfuse2** 的系统上直接运行
  - [x] 应用图标出现在应用菜单且**不是**通用占位图标
  - [x] 已固定的启动器图标与运行中的窗口**合并为一个**（不是两个）
- [x] 扫码能链接设备，能看到会话列表
- [x] 打 `v*` 标签后 GitHub Release 自动产出 deb + AppImage + `SHA256SUMS.txt`

**状态**：✅ 已实现（2026-10-10 记录）。验收方式逐条留痕，免得下次只剩一个勾：

- **两条命令级验收**：`pnpm run check` 在本机通过；`pnpm run verify`（构建 deb + AppImage 并实际
  解包断言）在 CI 的干净容器里通过 —— 最近三次 `ci.yml` 都是 success。
- **发布链路**：`v1.0.0`–`v1.0.3` 四个 `v*` 标签由 `release.yml` 自动发布；`v1.0.3` 的 Release 里
  带着 `waachat_1.0.3_amd64.deb`、`WaaChat-1.0.3.AppImage` 与 `SHA256SUMS.txt`。
- **安装与运行**：本机装的是 `waachat 1.0.3`（deb），日常都在用它（扫码登录、归档、密文缓存
  都跑在这上面）。
- **哪些是自动断言的**：`scripts/verify-package.sh` 覆盖的是"包层面就能看出错"的那几件 ——
  `.desktop` 条目文件名必须等于 `app_id`（GNOME 按它找同名文件，找不到就显示通用占位图标）、
  `StartupWMClass` 必须等于 `app_id`（不一致则 Dock 显示占位图标、启动器与窗口不合并）、
  AppImage 不依赖 libfuse2、deb 里 apparmor profile 与带 setuid 的 `chrome-sandbox` 都在。
  装完之后**肉眼**才能确认的那两件（菜单里显示的确实是我们的图标、任务栏合并为一个）由人工看过；
  自动化只能保证"包里的东西是对的"—— [ADR-0020](decisions.md#adr-0020) 把这条说得很直白：
  身份标识漏对齐一处的症状就是"构建全绿、运行时静默失效"，而它只有 `pnpm run verify` 抓得到
  （图标的三个落点见 [ADR-0023](decisions.md#adr-0023)）。

**为什么先做这个**：桌面集成的坑（`StartupWMClass`、沙箱、FUSE）与业务逻辑无关，但它们的症状会被误认为是业务 bug。先把地基验好。

## M1 · 接管点 A：点击即开

**目标**：核心需求达成。**这是项目成立的标志。**

**验收标准**

- [ ] 在聊天里点击一个 PDF，系统默认阅读器**直接弹出**，无需任何手动步骤
  > ⚠️ 这一条**一直没做到**。理由与实测见 [ADR-0029](decisions.md#adr-0029)：PDF 的明文只存在于页面
  > 内存里（端到端加密，页面解密后做成 `blob:`），我们既拦不到那个 `blob:`，也关不掉内核内置阅读器。
  > 曾经有过一条折中路径（挡掉预览页 + 把 `application/pdf` 降级成下载，由设置
  > 「禁用 PDF 预览」控制），它**已由 [ADR-0051](decisions.md#adr-0051) 整体移除** —— 那条路径
  > 挡得住内容、挡不住上游那个预览面板，用户得到的是"点了 PDF 一直转圈"。
  > 现在点 PDF 就是在应用内预览（上游自己的预览页），要落到系统阅读器只有一条路：用消息上的
  > 「下载」。因此这一条按原样保留为**未达成**，而不是改成一句看起来完成了的话。
- [ ] `~/Downloads` 中**没有**出现该文件
- [ ] 归档目录里出现该文件，且索引中有记录
- [ ] 同一个文件转发到另一个会话后再点击：归档目录中**文件数不增加**（哈希命中）
- [ ] 首次点击到文件打开的耗时在合理范围内（不应出现"先下载完再等"的观感割裂）
- [ ] 接管失效时（人为构造）**有明确提示**，而不是静默退回原生下载
- [ ] 索引中"有记录"的文件在磁盘上**全部存在**（无悬空记录）

**状态**：🟡 代码已实现，验收未逐条留痕。主路径（点击 → 落进归档 → 交给系统应用打开）
在 M0 记录的那次日常使用里一直在跑，归档、去重与索引一致性有单测覆盖；**唯一明确未达成**
的是上面那条 PDF（原因见 [ADR-0029](decisions.md#adr-0029)）。"首次点击到打开的耗时"属于
要真人点一次才能勾的那类。

**说明**：此时二次打开仍会联网（接管点 B 未做），这是已知且可接受的。

## M2 · 归档层

**目标**：归档从"能存"变成"能用"。

**验收标准**

- [x] 「文件列表」窗口可按文件名搜索（FTS5），能定位到较早前打开的文件
- [x] 搜索结果能一键交给系统应用打开
- [x] 支持批量导出到用户指定目录（正文已经是原文名，导出就是复制 —— 见 [ADR-0031](decisions.md#adr-0031)）
- [x] 能批量删掉不想留的文件：确认后删除，且**同一份内容被别的消息引用时不动那些名字**（[ADR-0053](decisions.md#adr-0053)）
- [x] 设置了大小上限后，超限淘汰按最久未访问优先删**内容**（全部磁盘名 + 同一次操作里的索引记录），**不留悬空记录**，且不碰索引不认识的文件（[ADR-0048](decisions.md#adr-0048)）
- [x] 单测覆盖：内容寻址、去重、淘汰边界、FTS 查询

**状态**：✅ 已完成。**去重**（硬链接，占用按 inode 计）、**搜索**（FTS5，文件列表窗口那个
带防抖的搜索框）、**淘汰**（[ADR-0048](decisions.md#adr-0048)）与**批量导出 / 批量删除**
（[ADR-0050](decisions.md#adr-0050) / [ADR-0053](decisions.md#adr-0053)：每行复选框 + 工具条上的
「导出…」「删除…」）都已落地。

## M3 · 接管点 B：二次打开零网络

**目标**：消灭"每次点击都重新下载"。

**验收标准**

- [ ] 第二次点击同一个文件后，**断开网络**再点击仍能打开
- [ ] 二次点击期间无新的 CDN 请求（可用抓包或连接观察验证）
- [x] 缓存上限生效，超限时**退化为直通**而不是报错（[ADR-0049](decisions.md#adr-0049)；单测覆盖，端到端待随下面三条一起实测）
- [ ] 缓存键的稳定性在**三种媒体类型**（图片 / 视频 / 文档）上分别实测通过
- [ ] 关闭此功能的开关存在，关闭后行为与 M1 完全一致

**状态**：🟡 缓存本身（[ADR-0026](decisions.md#adr-0026) / [ADR-0027](decisions.md#adr-0027) /
[ADR-0028](decisions.md#adr-0028)）、开关与**容量控制**（[ADR-0049](decisions.md#adr-0049)）
都已实现并有单测。**未做**的是上面第 1、2、4 条那三条**端到端验收**（断网仍能打开、
二次点击无新 CDN 请求、三种媒体类型分别实测）—— 它们要真人断网或抓包点一次，不能靠单测替代。

**这一步最容易出错**，风险与判定方法见 [`media-capture.md`](media-capture.md) 第 3、5 节。

**"缓存上限生效"这一条**是 M3 里唯一**已经落地**的一块（[ADR-0049](decisions.md#adr-0049)），
要点如下（免得每次都要重新查一遍）：

- **最后访问时间 = 正文的 `mtime`**：命中时就地更新（`touchCacheEntry()`）。刻意不节流 ——
  一次命中最少也要读几 KB，而更新 mtime 只是一次 syscall，成本被它盖过。这是"最久未用优先
  淘汰"**唯一**的输入。
- **总量统计做出来了**：`capture/cache-files.ts` 的 `cacheUsage()` 只算**成对条目**
  （`.bin` + `.meta.json`），由 IPC 层组合进 `ArchiveStats.cacheBytes` —— `archive/` 不得
  import `capture/`，因此两份统计在 `ipc/index.ts` 汇合。文件列表窗口的页脚显示它。
- **淘汰在写入成功之后**，并用进程内的字节计数器节流（间隔 = `clamp(上限/16, 8 MiB, 64 MiB)`）：
  算总量要 readdir + 每个条目 stat 一次，几万条时不能每个请求都做。启动对账之后、以及
  改动这个上限设置时也各跑一次。
- **退化为直通**（上面第 3 条前提）：**一份本身就超过上限的内容不落盘**。理由不是省空间，
  而是顺序 —— 淘汰按 LRU 排序，最新写下的那份永远排最后，一旦只剩它一个，它会先把整个
  缓存清空、再删掉自己。超限只降级（少一份缓存）、不报错，也绝不把请求卡住。
- **只删我们写的两样东西**：`.bin` 与 `.meta.json`。不认识的扩展名、目录、符号链接
  **一个都不碰** —— 与对账、切换同一条纪律。
- 归档那一侧的淘汰**也已经落地**（[ADR-0048](decisions.md#adr-0048)）：`archive/store.ts` 的
  `enforceLimit()` 把 `blobs.evictToFit()` 与 `deleteByHashes()` 收在**同一次调用**里 ——
  分开做会留下"搜得到但打不开"的悬空记录。两侧共享的是同一条纪律：**只删我们写的东西**。

## M4 · 打磨与扩展

**目标**：从"能用"到"愿意日常用"。

**候选内容**（按预期价值排序，未承诺）

- 后台预取文档（可开关，按网络环境自动判断）
- 多账号（每账号独立分区与归档）—— **已落地**（[ADR-0062](decisions.md#adr-0062)）：实现成"多实例"（`--instance <名>`，
  一个实例一份 profile + 归档 + 缓存 + 设置），而不是"一个进程内多个账号"。剩余的边角：命名实例的启动器条目与
  开机自启仍归属默认实例，要做"每个实例一个桌面身份"得连带动打包身份的四处同源声明（`docs/packaging.md` 第 2 节）
- arm64 构建（`ubuntu-24.04-arm` runner）
- AUR 包
- 归档的**按会话**浏览：**落盘这一半已经落地** —— 正文按它来自哪个会话分层到
  `<账号>/<会话ID>/files/`（[ADR-0055](decisions.md#adr-0055)，会话ID 取自页面模型
  `msg.id.remote`；拿不到则 `unknown-chat`），**在文件管理器里就等同于"按会话"**。
  仍缺的是**界面里**的会话维度（列表、筛选、按会话分组）——那要先解决元信息来源的问题
  （见 `architecture.md` 第 7 节），与会话标签是否可靠无关。
  （[ADR-0052](decisions.md#adr-0052) 的 `<账号>/<消息ID>/files/`、[ADR-0039](decisions.md#adr-0039)
  的 `<账号>/files/<年-月>/` 与 [ADR-0037](decisions.md#adr-0037) 的 `<年>/<月>/` 是它取代的
  历史布局，仍可读、可迁移。）
- 自定义打开规则（按扩展名指定应用，绕过系统 MIME 关联）

## 明确不做

以下不在路线图内，且不是"暂时没排期"：

| 不做 | 理由 |
|---|---|
| 消息内容归档 / 导出聊天记录 | 超出本项目范围：归档只保存"你打开过的文件"。INV-1 的只读例外只放行单个元数据字段，不覆盖"遍历会话与消息"（见 [`architecture.md`](architecture.md) 第 7 节） |
| 免扫码登录 / 凭据迁移 | 属于账号安全敏感地带，且会引入新的凭据管理风险 |
| 通话功能增强 | 上游提供什么就是什么（[ADR-0001](decisions.md#adr-0001)） |
| 自动收发消息、机器人、群发 | 行为特征是被限制的主要触发因素，见 [`DISCLAIMER.md`](../DISCLAIMER.md) |
| Windows / macOS 版本 | 目标平台是 Linux；其他平台各有官方客户端 |
| 移动端 | 同上 |
