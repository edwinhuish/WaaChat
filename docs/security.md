# 威胁模型与实现对策

根目录的 [`SECURITY.md`](../SECURITY.md) 是对外的**报告流程与边界声明**；本文是对内的**实现依据**。
改动任何落盘路径、IPC 通道、权限白名单或日志内容之前，先读这里。

---

## 1. 信任边界

```
不可信                          │  可信（有权限）
────────────────────────────────┼──────────────────────────────
远程网页内容                     │  Electron 主进程
（随时可能变化、可能被投毒）      │  （独占文件系统与系统调用）
                                │
远程 → 主进程的通道              │  本地渲染进程
只有"事件被观察"这一个方向       │  （自有代码，但仍不直连文件系统）
                                │
                                │  preload 桥
                                │  （白名单、只读）
```

**核心命题**：远程世界可以**被观察**，但不能**发起动作**。

## 2. 资产与保护目标

| 资产 | 位置 | 泄露后果 | 保护手段 |
|---|---|---|---|
| 设备登录凭据 | 会话分区（`~/.config/waachat/`） | 他人可无感读取全部会话，无需手机确认 | 目录权限；**绝不提供清除入口**（ADR-0008） |
| 解密后的媒体明文 | 归档目录（默认 `~/Documents/WhatsApp_files`，可在设置里改） | 通信内容泄露，且不受端到端加密保护 | 目录 `0700`（已存在但更宽时启动会收紧，见 ADR-0018）、文件 `0600`；不写日志；可选退出时清除 |
| 归档索引 | `<归档目录>/.index.sqlite` | 泄露"谁在何时传过什么文件"这类元数据 | 同目录权限 |
| 密文缓存 | `cache/`（默认不开启，见 ADR-0026） | 危害较低（仍是密文），但可被长期留存分析 | 可随时删除；不参与任何"永久保留"承诺；关掉缓存的**下次启动**会清空它（`capture/cache-files.ts` 的对账） |
| IPC 通道 | 运行期 | 越权触发本地动作 | 通道白名单 + 来源校验 |
| 自定义应用图标 | `~/.config/waachat/custom-icon.png` | **不敏感**（用户自己挑的一张图片），影响面只有外观 | 文件 `0600`；读不出来就删掉并回到默认图标（ADR-0022） |
| 用户级启动器条目 | `~/.local/share/applications/<appId>.desktop` | 不敏感；被改写只影响启动器里的显示 | 只在带 `X-WaaChat-Managed=true` 标记时才写、才删，否则报错放弃（ADR-0022） |

`cache/` 里除了密文正文，还为每条正文存一份 `.meta.json`（`capture/protocol.ts`）：其中只有
**响应头白名单**（`capture/headers.ts`，见 ADR-0016）—— 目的是回放时让响应语义与回源一致。
白名单是显式列举而非黑名单，正是因为 `set-cookie` 这类凭据一旦漏进去，就与上表"仍是密文"
的声明冲突（`headers.ts` 的模块注释记着这条理由）。

**更换保存位置**（ADR-0019）时：目标目录会被创建或收紧为 `0700`；跨文件系统的迁移是
"复制到临时名 → 删除源"，因此那一小段时间里明文**同时存在**于两个位置，两处都必须是
`0700`。迁移失败会回滚，但回滚只做搬运、不删数据 —— 宁可留下两份，也不替用户删掉
可能是唯一副本的文件。

**更换应用图标**（ADR-0022）新增两处写入，都比归档轻：`~/.config/waachat/custom-icon.png`（`0600`）
与上面那份用户级启动器条目。解码与裁剪发生在渲染进程，但**送进主进程的只有 PNG 字节**：落盘位置、
文件名与权限全由主进程决定，主进程还会用 `nativeImage` 自己再解一次，确认它确实是一张 512×512 的图。
因此 T2 的判据（"路径必须由主进程产生"）没有被削弱 —— 界面连一个路径都构造不出来。

**明确不防的**：已取得本机用户权限的攻击者、root、内存取证、被植入的恶意软件、物理接触。
归档目录的权限防的是**同机其他用户**与**粗心的同步工具**，不是防这些。
需要更强保护时应依赖全盘加密或把目录放在加密卷 —— 那是用户的选择，不是本项目的承诺。

## 3. threat 清单

### T1 · 远程内容通过注入通道触达本地能力

**最严重的一类。**

- 触发条件：有人为了"方便"让 preload 直连页面世界，或暴露一个"能执行本地操作"的 IPC 方法给页面。
- 后果：远程页面（或被投毒的上游资源）可以读写用户文件系统、发起任意本地操作。
- 对策：
  - [INV-1](../ai/INVARIANTS.md) 由 ESLint 强制，禁止注入类 API。
  - preload 遵循**单向**原则：只允许"主进程推数据 / 渲染进程读数据"，不提供"页面 → 本地副作用"的调用。
  - 评审 preload 改动时只问一个问题：**这会不会给远程内容带来一个新的本地副作用？** 会就拒。
  - 主进程侧的通道注册必须校验 `event.senderFrame`，拒绝来自远程页面的调用。

### T2 · IPC 通道被本地渲染进程越权调用

- 触发条件：渲染进程按"通道名 + 任意参数"直接驱动主进程的操作（如"删除任意路径"）。
- 后果：渲染进程一旦被 XSS 或第三方脚本影响，即可操作任意文件。
- 对策：
  - 通道**按语义设计**，不按参数设计。不做 `fs:readAny(path)` 这种通用通道，只做 `archive:open(jobId)`。
  - 所有路径参数必须是**主进程自己产生的标识符**，不能是渲染进程传进来的路径字符串。
  - 提交类通道连参数都尽量不要：`appicon:set` 收的是**值**（PNG 字节）而不是路径，
    位置由主进程自己拼（ADR-0022）。"能传值"与"能传能力"的区别就是这一条的分界。

### T3 · 符号链接与临时文件竞态

- 触发条件：归档目录可被其他进程写入；临时文件使用可预测的名字。
- 后果：写到非预期位置，或本地提权（若应用以更高权限运行）。
- 对策：临时文件使用随机名；最终写入用 `rename` 而非跟随链接的写操作；不跟随归档目录内的符号链接。

### T4 · 日志与崩溃信息泄露敏感内容

- 触发条件：为便于调试把文件名、完整路径、会话名写进日志。
- 后果：日志被同步到云端或被他人读到，等于泄露通信内容与社交关系。
- 对策（**强制**）：
  - 日志中**不得**出现：媒体文件名全文、会话名、消息内容、完整绝对路径中的用户名部分、任何 token。
  - 允许出现：内容哈希前缀、MIME 类型、字节数、相对目录名。
  - 崩溃报告同理。默认关闭自动上报。

### T5 · 权限白名单过宽

- 触发条件：为了"少出问题"直接允许所有权限请求。
- 后果：任何来源的内容都能取用摄像头 / 麦克风 / 通知。
- 对策：权限按来源与类型**双向白名单**，只允许来自上游页面源的通知与媒体设备请求；默认拒绝其余一切。

### T6 · 供应链

- 触发条件：依赖被投毒，或 CI 权限过大导致可发布恶意产物。
- 对策：
  - CI 的 `GITHUB_TOKEN` 权限最小化（`contents: read`），只有发布工作流需要 `write`。
  - 依赖更新走 Dependabot，**原生依赖与 Electron 主版本升级需要人工评审并跑 `pnpm run verify`**（见 `dependabot.yml` 里的 ignore 规则）。
  - 发布产物附 SHA-256；发布工作流同时归档产物。

### T7 · 用户误解归档的加密属性

- 触发条件：用户以为"端到端加密"覆盖了本地归档。
- 后果：把归档目录放进同步盘，实质泄露全部通信文件。
- 对策：`usage.md` 与首次运行的提示中必须明确说明；`DISCLAIMER.md` 第 3 节是对外承诺。

## 4. 与合规的关系

安全与合规在本项目里是同一件事的两面：

- 不注入（INV-1）既是合规要求，也是 T1 的根治手段。
- 不经手加密（INV-3）使"我们自己的加密实现有缺陷"这一整类问题不存在。
- 不做协议重实现（INV-2）使"凭据管理逻辑写错"的风险面大幅缩小。

因此[硬约束](../ai/INVARIANTS.md)的每一次松动都**同时**是安全评审的议题，必须走 ADR。
