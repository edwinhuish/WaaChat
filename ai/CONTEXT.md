## 1. 这个项目为什么存在

### 问题

该消息服务**没有官方 Linux 桌面客户端**。Linux 用户唯一的第一方途径是网页版，而网页版在"打开聊天里的文件"这件事上有三个结构性缺陷：

1. **每次都要走完整下载流程**：点击 → 浏览器下载到 `~/Downloads` → 用户自己去翻 → 手动双击。
2. **没有任何"已打开过"的概念**：同一个文件再点一次，还是重新下载一遍，还会多出 `报告 (1).pdf` 这样的副本。
3. **媒体链接会过期**：CDN 上的链接带有有效期签名，服务端副本也可能被回收。**链接一过期，那个文件就永远打不开了。**

第 3 点是不可逆的 —— 它是一个已经发生的损失，而不是体验问题。

### 为什么网页版解决不了

网页版把媒体存成 `blob:` URL，它只活在当前页面的内存会话里；页面内的数据库存的是"媒体指针"（解密密钥与 CDN 路径），**不是一个能交给外部应用打开的文件**。而且浏览器不给页面写任意文件、拉起外部应用的能力。

所以这是一个**平台能力边界**问题：要解决它，必须有一个**进程外的、能写文件、能调用系统打开方式**的宿主进程 —— 也就是一个桌面客户端。

### 关键的外部事实

该服务商的**自家 Windows 客户端**在 2025-11 从原生实现（WinUI/UWP）**退回 Chromium 容器**，直接加载网页版，代价是内存占用显著上升。这说明"用浏览器内核承载网页版"是官方自己在用的形态，其取舍是维护成本。

立项时我们做的事在技术形态上与之相同，只多了一层：**在内核层接管"下载文件"这一个动作**。
[ADR-0043](../docs/decisions.md#adr-0043) 曾计划改由网页版驱动库承载会话与媒体，那条路线已由
[ADR-0057](../docs/decisions.md#adr-0057) 放弃 —— 因此"只多一层"正是**现行**形态。

## 2. 术语表

| 术语 | 含义 |
|---|---|
| **上游** | 被承载的网页版聊天应用。因为命名约束（[INV-4](INVARIANTS.md)），文档中不直呼其名 |
| **承载 / 壳** | 用 Chromium 内核加载并显示上游页面 |
| **内核层** | Chromium 提供的能力面（下载管理器、网络栈、会话），与"页面内 JS"相对 |
| **接管点 A** | 观察下载事件，把"下载"变成"归档 + 打开" |
| **接管点 B** | 拦截会话对媒体 CDN 的请求，做**密文**磁盘缓存，使二次打开零网络 |
| **文档预览页** | 上游用来把 PDF 交给浏览器**内核**渲染的页面（`*.whatsapp.net/pdf-viewer/`）。本应用**照常加载**它 —— 曾经有一条"挡掉它、把 PDF 改走下载"的路径（ADR-0029/0030/0041），已由 ADR-0051 整体移除 |
| **媒体指针** | 页面内部数据库里指向一个媒体的记录（解密密钥 + CDN 路径）。**本项目不读取它** |
| **密文 / 明文** | 传输与 CDN 存储态是密文；页面解密后是明文。归档存的是明文，缓存存的是密文 |
| **归档** | 用户打开过的文件在本地的持久副本：落在 `<账号>/<会话ID>/files/` 里（账号来自页面记下的 WID / `wa_ul` cookie，见 ADR-0039；会话ID 是页面上的会话 JID，按内容哈希只读反查 `msg.id.remote`，拿不到回落 `unknown-chat`，见 ADR-0055 —— 其前身是 ADR-0052 的消息ID 第二级，老目录继续可读、可迁移），磁盘名是原文名（同一个会话内冲突时带一小段哈希后缀）、权限只读；内容身份是哈希（ADR-0031）；设置了「归档大小上限」时超限按**最久未访问优先**淘汰（ADR-0048）；用户也可以在「文件列表」里**按行**批量删除（ADR-0053）—— 与淘汰的区别：淘汰按**内容**、目的是腾空间；删除按**行**、删掉一行未必释放字节；删掉某个会话的最后一份正文后，那一层空目录会被一并收掉（ADR-0054） |
| **内容寻址** | 用内容的哈希作为**内容身份**（不是文件名）。同一内容只存一份字节，可以有多个名字（硬链接），因此天然去重；**淘汰也以它为**单位（删一份内容 = 删它的全部名字 + 索引记录，ADR-0048） |
| **幂等键** | 由媒体 URL 推导出的稳定标识，用于密文缓存。必须剔除会过期的签名参数 |
| **签名参数** | URL 上会随每次请求变化的字段（有效期、签名等）。参与缓存键会导致永不命中 |
| **降级** | 接管失效时退回上游原生行为。**必须可见**，不允许静默 |
| **app_id / StartupWMClass / .desktop 文件名** | 桌面环境用来把窗口与启动器条目关联起来的标识。GNOME 按窗口的 `app_id` 去找**同名** `.desktop`；`app_id` 同时是文件名词干与 `StartupWMClass` 的值。四处（含 electron-builder 的 `linux.syncDesktopName`）不一致会导致图标显示异常 |
| **用户级启动器条目** | `~/.local/share/applications/<app_id>.desktop`。XDG 的查找顺序让它优先于系统目录里的同名条目 —— "换应用图标"能生效靠的就是这个机制（ADR-0022）。只认带 `X-WaaChat-Managed=true` 标记的那份，其余视为用户自己的文件，不碰 |
| **实例** | 一份完全独立的本地状态：一个 Chromium profile（登录态）、一份设置、一份归档、一份缓存。由 `--profile <名>` 选择（v1.0.8–v1.1.1 叫 `--instance`，见 ADR-0076），不带参数就是**默认实例**（沿用改动之前的全部路径）。隔离的唯一杠杆是启动时按实例 `app.setPath('userData'/'sessionData')`（ADR-0062）；单实例锁因此自动变成"每实例一把"（锁文件在 `userData` 里）。**实例名不是安全边界**，只是目录名 |
| **窗口标题 / 托盘菜单** | 区分"哪一份数据"的界面落点：默认实例就是应用名，命名实例带 `（<实例名>）` 后缀。GNOME 的 appindicator 不显示托盘 tooltip，因此命名实例在菜单第一行自报家门。⚠️ 标题的**归属权**在 `main/unread.ts`：页面标题只是一份输入（未读数的来源），我们拦下 `page-title-updated` 自己写标题 —— 否则上游的 `WhatsApp` 会把实例名盖掉（[ADR-0080](decisions.md#adr-0080)） |
| **未读徽标** | 托盘图标右下角的红色数字（上限 `99+`）、以及窗口标题里那句 `— N 条未读`（[ADR-0080](decisions.md#adr-0080)）。数据源只有一个：页面标题里的 `(N)` 前缀 —— 因此**"读不到"（`null`）与"没有未读"是两件事**，而前者绝不显示成 0。徽标是手写点阵画进 `nativeImage` 位图的（Linux 上没有别的落点：`app.setBadgeCount()` 只对 Unity 有效） |
| **主题** | 设置里那一项（浅色 / 深色 / 跟随系统，[ADR-0078](decisions.md#adr-0078)），取值与 Electron 的 `nativeTheme.themeSource` 同形。它落到三处，而**三处各自能到什么程度不一样**：我们自己两扇窗口的样式（走 `prefers-color-scheme`，立即跟随）、三扇窗口的底色（`BrowserWindow.backgroundColor`，内核不会自己更新，由 `main/theme.ts` 订阅系统主题变化）、以及内嵌页面**在它自己的主题设为"跟随系统"时**。判据（合法取值、窗口底色）在 `shared/theme.ts`，落到 Electron 上的那一步在 `main/theme.ts` |
| **界面缩放** | 设置里那一个倍数（`1` = 100%，[ADR-0079](decisions.md#adr-0079)），`shared/zoom.ts` 定档位与收敛。它有**两个入口**（设置页、应用菜单），两者都必须把同一件事做完：写设置 → 三扇窗口跟上 → 通知设置页那一行。窗口那一步在 `window.ts`（建窗口时设一次、每次加载之后再设一次），菜单那一步在 `main/zoom.ts` |
| **应用菜单** | 我们自己装的那份菜单（`main/menu.ts`，[ADR-0077](decisions.md#adr-0077)），替换 Electron 自带的英文默认菜单。菜单栏默认隐藏（`autoHideMenuBar`），按 `Alt` 可见，但**快捷键一直生效** —— 因此"Ctrl+Q 能不能退出"由它决定。它也是唯一"始终存在"的窗口入口：托盘在不显示它的桌面环境上**检测不到**（[ADR-0034](decisions.md#adr-0034)） |

## 3. 项目的价值集中在哪里

```
src/main/capture/     ← 接管（项目的核心机制）
src/main/archive/     ← 归档（项目的核心价值）
```

其余目录（窗口、会话、IPC、系统集成、渲染界面、打包配置）都是**脚手架**：它们的存在是为了让上面两处能跑起来。

评审代码时，注意力应该按这个比例分配。改动脚手架的文件通常风险低，改动 `capture/` 与 `archive/` 的文件需要考虑失效模式。


- **想推翻某个设计** → 先读 `docs/decisions.md` 里对应的 ADR，再决定是提 ADR 还是放弃。

- **想知道背景** → `docs/decisions.md`（立项期的三条技术路线对比与被否决的理由见 ADR-0001；一次短暂转向与其回退见 ADR-0043 / ADR-0057）。

## 5. 平台环境假设

| 项 | 假设 |
|---|---|
| 目标平台 | Linux 桌面，主要面向 GNOME / Wayland，但不应破坏 X11 与其它桌面 |
| 会话类型 | Wayland 优先；Ozone 平台相关设置需同时照顾两种会话 |
| 桌面集成 | 打开文件走系统 MIME 关联（`xdg-open` / 门户），不自己维护关联表 |
| 托盘 | Ayatana AppIndicator；GNOME 下需要对应扩展，缺失时只能降级为"无托盘" |
| 应用图标 | 三个落点、生效时机不同：窗口（`setIcon`，X11 立即 / **Wayland 无效**）、托盘（立即）、启动器条目（要等桌面刷新或重新登录）。见 ADR-0022 |
| 权限模型 | 归档目录（含 `<账号>/<会话ID>/files/` 子目录，见 ADR-0052 / ADR-0055）与缓存目录（`<账号>/<年-月>/`）`0700` / 文件 `0400`（只读，见 ADR-0031 / ADR-0039）；登录态目录**绝不清除** |
| 分发 | deb + AppImage，均为 x64；AppImage 必须在 Linux 上构建 |

## 6. 已知的不确定性

写代码时要为这些留出余地：

1. **上游会改。** 页面实现变了，接管可能失效。要求是**允许失效、不允许静默失效**。
2. **幂等键的唯一性未经验证。** "剔除签名参数后路径仍唯一标识对象"是待实测的假设，不是结论。碰撞的后果比漏命中严重得多。
3. **原生模块。** `better-sqlite3` 是 Node-API（N-API）模块，Node 与 Electron 共用同一份
   `prebuilds/*.node`，无需按 ABI 重建（见 [packaging.md](../docs/packaging.md)）。
   若将来验证 `node:sqlite` 可用且支持 FTS5，可去掉这个依赖（见 [ADR-0003](../docs/decisions.md#adr-0003)）。
